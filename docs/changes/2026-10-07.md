## v1.43（2026-10-07）

**RESOLVE_SECRET 展示长度 64→44 字符（hex 改 base64，熵与安全性不变）**：`gen-resolve-keys.bat` 生成的随机 Secret 仍是 **32 字节（256 位）**，仅把编码由 64 字符十六进制改为 **44 字符标准 base64**（node `randomBytes(32).toString('base64')`）。依据：`resolve-core` 的 `SECRET` 是把环境变量值的**原始字符串字节**直接喂给 HKDF（`option_env!("RESOLVE_SECRET").as_bytes()`，见 `crates/resolve-core/src/lib.rs`），全链路从不做 hex/base64 解码，故呈现编码可自由替换，客户端构建与服务端加密两侧字符串逐字节一致即可，加解密代码零改动；`+ / =` 在环境变量 / JSON / stdin 通道均安全。bat 头部注释同步说明这一点，行尾维持 CRLF / 无 BOM / 纯 ASCII。**验证（2026-10-07）**：实跑 bat 输出 44 字符 Secret；以含 `+/=` 的该值经编译期注入跑 `cargo test -p resolve-core`，往返用例 `e2e_sign_encrypt_roundtrip` 通过；3 个固定密文向量用例（默认 Secret 预制）在任何自定义 Secret 下均失败——用普通 ASCII Secret 对照同样失败 3 个，确认与编码无关；不带该环境变量时全仓 **153 通过 / 6 ignored** 维持全绿

## v1.45（2026-10-07）

**TXT 密文紧凑化（v3 格式）+ 解密端兼容全部三代格式 + RESOLVE_SECRET 用法答疑补文档**：

- **Q1「encrypt 要不要指定 RESOLVE_SECRET」**：它**不是命令行参数**，而是 `resolve-core` 的编译期常量（`option_env!("RESOLVE_SECRET")`）。客户端构建注入了自定义 Secret 时，加密前必须在**同一 shell** 先设好再 `cargo run`（实测 cargo 经 dep-info 自动追踪该 env，设置/改值/取消都会重编 resolve-core，无需 clean）；不设则两端统一回落内置默认串，自定义 Secret 加密的密文在默认包里必然解密失败。Python 工具为运行时读同名 env。已在 `resolve-tool` 模块头、`webview-app/AGENTS.md` 动态解析小节、`scripts/gen-resolve-keys.bat` 头注释与尾部「下一步」补齐两种 shell（cmd / PowerShell）的设置指引（纯提示，不落盘）。
- **Q2「密文太长，缩短」**：旧 Payload 尾部有一段 `0x00 ‖ 随机盐(8B)` 纯冗余——12B 随机 Nonce 已是 GCM nonce 且同时充当 HKDF salt，足以保证每次密文与派生密钥均不同。v3 删除这 9 字节：`Payload = URL ‖ 0x00 ‖ ts(8B) ‖ ttl(8B)`。实测同一 URL（`https://user:pass@host`，22 字符）密文 **188 → 176 字符**（恒定短 12 个 base64 字符，长度公式有单测钉死），连跑两次密文不同、解密一致。Python `tools/encrypt_url.py` 同步只发 v3（本机无 Python，静态对齐同一格式）。
- **三代格式解密全兼容（关键）**：`parse_payload` 按 URL 分隔符后的尾部定长分派——v3=16B、v2（2026-09-03 ttl 版沿用至 v1.44）=25B、v1（2026-09-03 首发无 ttl）=17B；v1 无显式 ttl，沿用其首发时固定 **±48h** 防重放窗口（`git show 8d38ee2:src/resolve.rs` 核实，非凭记忆），安全语义不放松。3 个 v2 固定向量（默认 Secret 的 baidu/bilibili/example 旧密文）继续可解。

## v1.49（2026-10-07）

**TXT 密文升级为 v4「按天」格式：签发时间与 TTL 均改为天，尾部 16B → 4B**（使用者明确指令；协议格式变更，旧密文需重签）：

- 动机：v3 尾部为 UNIX 秒级时间戳 8B + 秒级 TTL 8B（16B），但业务上不需要秒级精度。v4 以 **2026-01-01（UTC）为基准日**，签发日 `d` = 距基准日的天数、TTL 单位也为天，各占 **u16（2B 大端）**：`Payload = URL ‖ 0x00 ‖ d(2B) ‖ ttl_d(2B)`，尾部固定 4B。
- 为何用 u16 而非 u16 以下：今天（2026-10-07）已是基准日后第 **279** 天，1 字节（≤255）即刻溢出；u16 上界 65535，签发日可覆盖至约 2205 年、TTL 最长约 179 年。取舍：TTL 最小粒度由秒变为 **1 天**。
- 长度收益：固定开销 109B → **97B**（Nonce12 + 分隔/字段 5 + 签名64 + tag16）。22 字符 URL：raw 131B → 119B，base64 **176 → 160 字符**（−16）。
- `resolve-core`：新增常量 `BASE_UNIX_DAY = 20454`（2026-01-01 的 UNIX 日）、公开 `current_unix_day()`；`current_day` 改算「UNIX 日 − 基准日」；`sign_and_encrypt*` 校验签发日 / TTL 均 ≤ 65535，超界明确报错；`DecryptedRecord` 字段改为 `sign_day` / `ttl_days`；`parse_payload_parts` 尾部固定 4B，v3/v2/v1（16B/25B/17B 尾）一律按「Payload 尾部结构异常」拒绝——**v4-only，不做向后兼容**（与 v1.46 收敛策略一致）。HKDF/Nonce/GCM 信封不变。
- `resolve-tool`：`--ttl` → **`--ttl-days`**、常量更名 `DEFAULT_TTL_DAYS`、`ParsedArgs.ttl_days`；`decrypt` 输出改为「签发日期（`YYYY-MM-DD`，Howard Hinnant 民用日算法，不引 chrono）+ TTL 天数」，过期退出码 1 语义保留；删除秒级 `human_duration`。
- Python `tools/encrypt_url.py` 同步：`--ttl-days`、`DEFAULT_TTL_DAYS`、`BASE_DATE`、2B 大端 Payload、范围校验（>65535 报错）；`.github/workflows/resolve-keys.yml` 输入 `ttl` → `ttl_days`（描述/校验/cargo 命令/产物说明，新增 65535 上限校验）；`scripts/gen-resolve-keys.bat` 两处示例命令、`src/resolve.rs` ignored 用例注释同步。
- 固定向量已用现存 `txttest_keys/private_key.pem` 重签 5 条 v4（baidu×3 / bilibili / example，均第 279 天、ttl_days=0），替换测试中的 v3 向量。
