## v1.52（2026-10-08）

**修复 Tauri 多页签两个缺陷：首次打开约 30s 卡顿、新标签页落回首页**（使用者真机反馈，附截图：标签栏单个 tab「webview-app」停在加载层）：

- **现象**：`tabs_enabled=true` 的产物里，①首个标签页首次打开极慢（停在「加载中…／正在准备应用环境…」，约 30s 后才出内容）；②网页里 `target="_blank"` / `window.open()` 打开的新标签页一律落在**入口地址（首页）**，而非链接指向的指定页面。
- **根因 1（首次打开极慢）——多页签路径无人为首个 tab 启动 bootstrap**：`src/lib.rs` 的多页签 setup 只调用 `tabs::spawn_tab(...)`，**没有**启动 `bootstrap::bootstrap_for_label`；而 `tabs.rs::navigate_tab` 在导航缓存 `navigation` 为 `None`（首屏未就绪）时走的是「后台轮询等缓存」分支，**没有任何路径去拉起 bootstrap**。于是首个 tab 只能空等 **30s 轮询超时**后才回落完整 bootstrap，用户侧即「首次打开很慢」。该回归系提交 `57164d56`（2026-09-27 第六轮审计）把原本「直接调 `bootstrap_for_label`」改成「只等缓存」时引入，未同步补回触发点。
- **根因 2（新 tab 落回首页）——跨域弹窗在直连模式下被丢弃**：`tabs.rs::resolve_popup_url_for` 对**跨域外部链接**仅在本地反向代理模式（`use_local_proxy=true`）下放行目标地址，否则返回 `None` → 新 tab 回落入口地址。用户的配置（`tests/json/osfipin.mark.json`：书签管理器，**无 userinfo、无代理**＝直连）里外站书签正是跨域，故全部落到首页。**附带缺陷**：`navigate_tab` 的轮询回调把弹窗落点 `start` 硬编码成 `None`，即使缓存就绪也会丢弃目标地址。
- **修复（`src/tabs.rs`，最小改动）**：
  1. `TabManager` 新增 `bootstrap_started: AtomicBool`：区分「缓存为空」的两种含义——首次置位者（`swap` 返回 `false`）由本次建窗**直接启动完整 bootstrap**；非首次者（已有 bootstrap 在途，如首屏就绪前的极早期 `window.open`）**只轮询等缓存**，避免两个 bootstrap 互相 `abort` 掉在用代理。单次翻转、不复位（bootstrap 失败时后续等待方靠 30s 超时回落，等价旧行为）。
  2. 轮询分支保留 `start`：回调由 `navigate_tab(&a, &l, None)` 改为 `navigate_tab(&a, &l, s)`，弹窗落点不再丢失。
  3. `resolve_popup_url_for` 的跨域分支改为**无条件打开目标地址**（与 Electron 壳 `setWindowOpenHandler → spawnTab(opened)` 行为对齐）。凭据不泄漏：直连模式下 Authorization 注入与 401 自动应答受 `bootstrap::is_upstream_request` 主机白名单约束，外域请求拿不到入口账号密码；本地反向代理也只对固定上游注入凭据。同步更新 `resolve_popup_url` / `resolve_popup_url_for` 的规则文档注释。
- **测试**：主 crate 102 → **103**（①新增静态回归 `first_tab_triggers_bootstrap_and_poll_keeps_start`：断言生产代码段包含 `bootstrap_for_label(app.clone(), label.to_string())` 且不含 `navigate_tab(&a, &l, None)`；②`popup_cross_domain_plain_mode_returns_none` 改写为 `popup_cross_domain_plain_mode_opens_external`，断言非代理模式跨域返回 `Some("https://other.com/x")`、同源仍拼回入口）。工作区 **176 通过 / 6 ignored**（resolve-core 19 + resolve-tool 22 + w2a-proxy 32 + 主 crate 103；较 v1.51 的 175 +1）。
- **门禁（2026-10-08 实跑）**：`cargo fmt --all -- --check` 0 diff、`cargo clippy --workspace --all-targets -- -D warnings` 0 告警、`cargo test --all` **176 通过 / 6 ignored**。

## v1.53（2026-10-08）

**顶部通栏收归 Windows 专属、Android 端显式忽略多页签**（使用者反馈：「顶部通栏属于 Windows 专属，安卓端不应该有；安卓端应该忽略多标签功能」）：

- **现象**：Android 端出现自绘「顶部通栏」（38px，含后退/前进/设置/最小化/最大化/关闭按钮）——与系统标题栏叠成双标题栏，且加载层被 `window.__web2appChromeH=38` 顶开、顶部多出一条空白。
- **根因（顶部通栏泄漏）**：真实页面上的 `decorations(false)` 与 `titlebar.js` 注入本就在 `lib.rs::build_main_window` 的 `#[cfg(windows)]` 块内；但**启动页**（主窗口首个文档 `splash://localhost/`）走的是另一条路径——`loading.rs::splash_html()` **无条件**内联 `titlebar.js`，绕过了平台门控，于是在 Android 启动页上把自绘通栏渲染了出来。
- **修复（最小改动）**：
  1. `src/loading.rs::splash_html`：`let titlebar_js = if cfg!(windows) { TITLEBAR_JS } else { "" };`，非 Windows 把标题栏占位符替换为**空串**（占位符仍照常消费——模板与 `splash_template_has_no_token_in_comments` 均按「恰好出现一次」约束，不能直接删占位符）。`cfg!` 两支都会编译，`TITLEBAR_JS` 在非 Windows 仍被引用，无死代码告警。
  2. `src/config.rs::TABS_ENABLED`：由 `env_bool!("TABS_ENABLED", false)` 改为 `cfg!(windows) && env_bool!("TABS_ENABLED", false)`，非 Windows **恒为 false** —— 即便打包链路误注入 `TABS_ENABLED=true`，Android 也不会启用多页签（`mod tabs` 本就是 `#[cfg(windows)]`，此为语义显式化）。
  3. `.github/workflows/release.yml` Android job 的 `TABS_ENABLED` 补注释，说明该值在 Android 端被忽略。
- **测试**：`splash_html_inlines_script_and_title` 改为**平台感知**——Windows 断言启动页含 `__web2app_titlebar__`；非 Windows 断言**不含**。工作区仍 **176 通过 / 6 ignored**（主 crate 103，无新增用例）。

- **文档**：`webview-app/AGENTS.md`「自绘标题栏」特性行补「顶部通栏为 Windows 专属，Android 不注入、启动页也不内联」；`tabs_enabled` 小节补「非 Windows 恒为 false（v1.53 起）」。

## v1.55（2026-10-08）

**修复多页签两个真机缺陷：点齿轮设置页空白、页签标题被广告 iframe 污染**（使用者反馈并附截图：点 bilibili 书签后第二个 tab 标题显示「Leader Iframe」；点标签栏齿轮弹出纯白无边框窗）：

- **缺陷一：设置页打不开（620×600 纯白窗）**
  - **根因**：标签栏齿轮走 IPC 命令 `open_settings`，而 tauri 2.11.5 在主线程 `on_message` 里**同步派发** invoke；`settings::open_settings_window` 又在该调用栈内联执行 `WebviewWindowBuilder::build()`——等于「IPC 事件派发期间再创建窗口 + 新 WebView2 环境」→ **嵌套事件循环**，新 WebView2 controller 的初始化消息永远得不到分发：Win32 窗口建出来了（任务栏有「设置 - Mark」），但 `settings://` 协议从不被请求、页面永不渲染。运行时取证证据：同样调 `open_settings_window`，经后台线程 + `run_on_main_thread` 的自动开窗路径能正常渲染深色面板，而齿轮 IPC 路径截到全白窗且日志中无任何协议请求。
  - **修复（`src/settings.rs`，最小改动）**：`open_settings_window` 改为只做「切后台线程 → `run_on_main_thread` 排队到下一个事件循环轮次」，真正的聚焦/建窗逻辑下沉到 `open_settings_window_on_main`。三条调用路径（齿轮 IPC、`web2app:open-settings` 事件、Shift+F1 全局快捷键——全部运行在主线程回调栈内）统一受益；与 `webview_hooks.rs` NewWindowRequested 的既有延迟建窗模式同构（该处理注释早已写明「回调里直接建窗会嵌套事件循环卡死」；且主线程上直接调 `run_on_main_thread` 会被同步内联执行，必须先 `spawn`）。另把建窗失败由 `let _` 静默吞掉改为 `dlog!` 留痕。
- **缺陷二：页签标题显示「Leader Iframe」**
  - **根因**：Tauri 的 `initialization_script` 对应 WebView2 `ICoreWebView2::AddScriptToExecuteOnDocumentCreated`，该 API **没有 frame 过滤器**——`tab_title.js` 与注入的 label/token 会进入**每一个 iframe**（含跨域广告 frame），各 frame 的脚本各自读自己的 `document.title` 并以同一份 label/token 上报。真机取证（点 bilibili 书签）标题序列为：`哔哩哔哩…` → `Cross Origin Local Storage` → `Leader Iframe` → `cm.bilibili.com`，其中后三个均为页面内嵌广告/存储框架的文档标题；使用者截图显示 tab 内容始终是正常 bilibili 首页，仅标签文字被污染。（Electron 壳无此问题：`page-title-updated` 只反映主框架标题；且 Electron 不注入 `tab_title.js`。）
  - **修复（最小改动）**：①`src/tab_title.js` 在读 label/token 之前先 `if (window.self !== window.top) return;`，只允许主框架上报标题（`window.top` 身份比较不受同源策略限制，跨域 frame 也能正确判断）；②`src/tabs.rs` 注入 `__web2appTabLabel` / `__web2appTabToken` 时同样加主框架门控，避免一次性防伪令牌白暴露给第三方跨域 frame。取证中另观察到游客态下 bilibili 主框架会自行跳转到 `cm.bilibili.com/?spm_id_from=…`（B 站自身营销跳转，Chrome/Edge 游客态同样发生，登录态不跳）——属站点行为，主框架如实反映其标题即可，不在本次修复范围。
  - **测试**：新增静态契约测试 `contract_tests::tab_title_script_runs_in_top_frame_only`，断言 tab_title.js 含 `window.self !== window.top` 早退守卫、tabs.rs 的两处令牌注入都带 `window.self === window.top` 门控且注入本身未被误删。主 crate 104 → **105**，工作区 **178 通过 / 6 ignored**。
- **真机验证（2026-10-08，无 CDP 注入）**：多页签配置（`TABS_ENABLED=true` / 入口书签管理器 / `TITLE=Mark`）实跑——齿轮 IPC 开窗后 PrintWindow 截到完整深色设置面板（快捷键/托盘/清缓存/保存齐全）；修复后日志中子框架标题（`Cross Origin Local Storage` / `Leader Iframe`）不再出现。
- **门禁（2026-10-08 实跑）**：`cargo fmt --all` 0 diff、`cargo clippy --workspace --all-targets`（默认配置与 `TABS_ENABLED=true` 交付配置各一遍）0 告警、`cargo test --workspace` **178 通过 / 6 ignored**。
- **交付提示**：两个修复都在 Rust/注入脚本侧，`tabs_enabled=true` 的 Tauri 包需重新打包生效；Electron 壳无需改动。

## v1.58（2026-10-08）

**修复 Electron 多页签切换不即时：标签栏与内容视图要等页面加载完成才跳过去**（使用者反馈：「electron 多标签页切换时标签不会立刻显示切换过来，等待页面加载完成后标签页 UI 才会显示以及切换；Tauri 无此问题」）：

- **根因（`electron-app/src/main/tabs.ts`）**：`spawnTab` 把 `activate(label)` 放在 `await this.onSpawn(...)` **之后**，而 `onSpawn`（index.ts）内部 `await view.webContents.loadURL(...)`——该 Promise 等整页 `did-finish-load` 才 resolve。于是整个加载期间：①新页签不进标签栏、激活态不翻转（`pushToShell` 在 `activate` 里）；②新视图 `addChildView` 后**默认可见且位于子视图栈顶**，旧页签被盖住却仍是「激活」；③用户此时点别的页签把加载视图隐藏，加载一结束又被这句迟到的 `activate` **拽回**新页签（即感知上的「切不过去」）。Tauri 侧 `spawn_tab_with_target` 本就是 `visible(false)` 建窗 → `navigate_tab` 发起导航（不等待）→ **立刻** `activate_tab`，故无此问题。
- **修复（最小改动，对齐 Tauri 时序）**：`spawnTab` 在 `addChildView + setBounds` 之后、调用 `onSpawn` **之前**立即 `activate(label)`（旧页签同步隐藏、标签栏立即推送）；`onSpawn` 只负责挂钩子 + 发起导航，加载在新页签激活状态下进行。spawn 失败时新增激活态回滚：恢复旧激活页签，首签失败（无旧页签）则推空列表，由既有失败遮罩（`shell-overlay.ts`）接管。
- **测试（页签断言组 33 → 39，含反向对照）**：`probe-server.ts` 新增夹具 `/slow.html?ms=NNN`（先发响应头让导航提交、body 延迟下发，制造确定性「加载中」窗口）；`probe-tabs.ts` 新增 **P10b** 6 条：spawnTab 同步返回时新页签已激活、标签栏 active 在加载窗口内翻转（且独立于 active 取期望值，防与自身比较假绿）、加载中仅新视图可见（双视图叠放回归）、加载中切回旧页签立即生效、慢页加载完后激活态不被拽回、收尾关闭。反向对照：把 `activate` 挪回 `await` 之后（旧时序）时其中 **4 条如期 FAIL**（35/39），恢复修复后 **39/39** 全绿；`tsc --noEmit` 双工程通过、纯函数单测 **51/51**。
- **说明**：默认探针组 138 条本次未改（P10b 在 `--tabs` 页签组）；本地实跑时默认组既有的「sidecar 启动并完成握手」1 条失败在改动前的干净工作区同样复现，属既有环境问题，与本次无关。
