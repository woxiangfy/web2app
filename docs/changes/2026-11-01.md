# 2026-11-01 · CI「Build Android APK」失败：注入的 Kotlin DSL 用了 `java.io.File`

> 时点快照：记录 2026-11-01 的 CI 失败与修复。

## 1. 现象（CI 日志摘录）

```
e: file:///home/runner/work/web2app/web2app/webview-app/gen/android/app/build.gradle.kts:108:26: Unresolved reference 'io'.

* What went wrong:
Script compilation errors:

  Line 017: android {
            ^ 'fun Project.android(configure: Action<BaseAppModuleExtension>): Unit' is deprecated. ...

  Line 108: val w2aScriptsDir = java.io.File(w2aRepoRoot, ".github/scripts")
                                     ^ Unresolved reference 'io'.

2 errors
BUILD FAILED in 1m 54s
       Error failed to build APK: Failed to assemble APK with ...
```

关键点：Rust 侧是**成功**的（`Finished release profile in 5m 20s`，`.so` 已 symlink 进
`jniLibs/arm64-v8a`），失败点在 **gradle 配置期**——脚本编译不过 ⇒ 连 `app` 子工程的任务图都建不起来
⇒ **零产物**。这与 2026-10-28 记录的三类可疑点中的第 3 类（「gradle 配置期失败：`inject-gradle-patch-task.py`
那 79 行 Kotlin DSL 从未被编译过，10-16 加入且 job 是 continue-on-error」）**完全对上**。

## 2. 根因

`.github/scripts/inject-gradle-patch-task.py` 的注入模板里写了：

```kotlin
val w2aScriptsDir = java.io.File(w2aRepoRoot, ".github/scripts")
```

在 `build.gradle.kts` 里 **`java` 不是包名**：Gradle 会为已应用插件的扩展生成**类型安全访问器**
（`val Project.java: JavaPluginExtension`，AGP 会应用 java-base）。于是 `java.io` 被解析成
「访问器 `java` 的成员 `io`」⇒ `Unresolved reference 'io'`。

列号也吻合：`val w2aScriptsDir = ` 之后 `java` 占 21–24 列、`.` 是 25 列、**`io` 正好从 26 列开始**，
与日志 `108:26` 一致。

该行 2026-10-16（提交 `e588845`「1016d1」）随脚本新建引入；由于 android job 是
`continue-on-error: true`（见 `build-custom.yml` 的 `android:` 作业头），作业红了但**整轮 workflow 仍是绿的**
⇒ 从 10-16 到 11-01 一直没人被通知。

## 3. 修复

`w2aRepoRoot` 本身已经是 `File`（`rootProject.projectDir.parentFile.parentFile`），直接派生即可，
既避开访问器遮蔽，也不需要 `java.io.*` 的隐式导入：

```kotlin
val w2aRepoRoot = rootProject.projectDir.parentFile.parentFile
// ⚠️ 必须用 File#resolve，禁止写 java.io.File(...)：...
val w2aScriptsDir = w2aRepoRoot.resolve(".github/scripts")
```

同时给 `--selftest` 补三层守卫（匹配前**剥掉 `//` 行注释**——注入块自己的注释里就带着那个反例字符串，
不剥注释就是「针被注释满足」）：

```python
code_only = "\n".join(ln for ln in content.splitlines() if not ln.lstrip().startswith("//"))
assert "java.io." not in code_only, ...                                  # 禁 java.* 包前缀
assert 'w2aRepoRoot.resolve(".github/scripts")' in code_only, ...        # 必须 File#resolve 派生
# 语法跳闸：{} / () 必须配平（手工改这段模板最容易掉一行 }）
```

| 项 | 结果 |
| --- | --- |
| `python .github/scripts/inject-gradle-patch-task.py --selftest` | 通过 ✓ |
| 反向对照：把 `resolve` 行改回 `java.io.File(...)` 再跑自测 | **FAILED**（`AssertionError: Kotlin DSL 里 java 是扩展访问器`）✓ |
| 还原后 `sha256sum` | `e7f7cf61…` 与改前逐字节相同 ✓ |
| 注入产物目视（临时 gen 目录） | `val w2aScriptsDir = w2aRepoRoot.resolve(".github/scripts")`，`workingDir = w2aScriptsDir` ✓ |

⚠️ **本机做不了的**：真 gradle 编译（无 Android SDK / NDK / gradle wrapper 离线可用，已确认本机无
`java` / `gradle` / `~/.gradle` / Android Studio / SDK）⇒ 「脚本能编译」这一层只能等下一轮 CI 复核。
若仍失败，用现成的二分开关 `W2A_SKIP_GRADLE_PATCH=1`（默认关）跑一轮：
APK 出来了就说明**还在注入块**里，否则在下游。

## 5. 复检（同日第二轮）：把「下一轮不该再炸」逐条取证

1. **CI 日志的诊断是完整的** —— kotlinc 会在一次编译里列出**所有**解析/类型错误，而这份日志只有
   2 条诊断：`w:` 第 17 行的 legacy DSL 弃用（不是错误）+ `e:` 第 108 行的 `Unresolved reference 'io'`。
   ⇒ 模板部分（含 `set-android-apk-name.py` 注入的 `base { archivesName.set(...) }`）与注入块
   **除该行外的其余语句**（`tasks.register<Exec>` / `tasks.names` / `afterEvaluate` /
   `tasks.named(...).configure`）在真 AGP 9 环境下**已经通过脚本编译**。
2. **gradle 要执行的那三条命令实跑通过** —— 按 Exec 任务的方式（cwd = `.github/scripts`、
   只传 `--gen-root <绝对路径>`）跑 extras / schemes / fullscreen，**连跑两轮**全部 `exit 0`；
   已打过补丁时正确打印「已包含…跳过」（幂等，正是 wry build.rs 覆盖后重放的前提）。
3. **重放产物的 Kt 源文件括号配平** —— 9 个 `.kt`（MainActivity 239 行 / RustWebViewClient 160 /
   RustWebChromeClient 592 等）`{}`/`()`/`[]` 全部配平，0 个不配对。
4. **全仓再无「gradle 脚本里的 `java.*` 包前缀」** —— `grep -rn "java\."` 只剩两处
   `import java.util.UUID` / `import java.util.*`，那是 `.kt` 文件里的**导入语句**（`java` 在导入位置
   是包名，不受访问器遮蔽影响）。
5. **新增第三条守卫：括号配平**（见上）。反向对照：把 `afterEvaluate {` 改成 `afterEvaluate {{`
   ⇒ `AssertionError: 注入块括号不配平：{=14 }=13`；还原后 `sha256sum` = `c14f3654…` 逐字节相同。

⚠️ 仍然**没法本地验**的只有一处：`gen/android` 里 `.kt` 源码（模板 + 我们补丁）的**真 Kotlin 编译**。
这一层没有 JDK/SDK 就无从复现；但它的失败形态是 `e: ...MainActivity.kt:行:列`，会被现有
「Build Android APK」步骤的 `grep -E '^e: '` 摘录直接指到行号，不会再像本次这样只剩一句 `BUILD FAILED`。

## 6. 同日第三轮：「还是失败」的那份日志其实不是这个提交的

用户第二次贴来 `android-build-2.log`，失败点与第一次**逐字相同**（`build.gradle.kts:108:26`
`Unresolved reference 'io'`、报错文本里的 `java.io.File(w2aRepoRoot, ".github/scripts")` 原文，
甚至耗时也一样：`Finished release profile in 5m 20s` / `BUILD FAILED in 1m 54s`）。取证：

| 判据 | 事实 |
| --- | --- |
| `git rev-parse HEAD` / `origin/main` / `git ls-remote origin main` | 三者都是 `72217f6`，工作区干净 |
| `git show HEAD:.github/scripts/inject-gradle-patch-task.py \| grep w2aScriptsDir` | `94: val w2aScriptsDir = w2aRepoRoot.resolve(".github/scripts")` |
| 全仓 `grep -rn "java\.io\.File(w2aRepoRoot"` | 只剩本轮新加的**注释/文档**里的反例字符串，脚本里已无 |
| `gen/android` 是否可能残留旧文件 | 否 —— `gen/` 无缓存、每次 `install-android-sdk.sh` 现 init，注入脚本无「跳过」可能 |

⇒ **那份日志来自不含该修复的运行**（旧 run 的 "Re-run"/旧 artifact 都会这样；`build-custom.yml` 是
`workflow_dispatch`，`Re-run` 会复放**原始提交**）。而日志自身不含任何能自证「我是哪个提交」的信息，
所以只能靠猜 —— 这才是要修的东西。

### 6.1 连带改动：CI 加「注入结果校验」步骤（两个 workflow，逐字对齐）

紧跟「注入 gradle task」，在 `build-custom.yml` / `release.yml` 各加一步（早 5 分钟失败 + 自证提交）：

```bash
echo "commit=${{ github.sha }}"
echo "ref=${{ github.ref }}  event=${{ github.event_name }}  run=${{ github.run_id }}"
grep -n 'val w2aScriptsDir' gen/android/app/build.gradle.kts
grep -q '= java\.io\.File(w2aRepoRoot' "$f" && exit 1   # 旧写法立刻红在这里
```

⚠️ 判据**不能**写 `grep java.io.` —— 注入块的注释里就带着这个反例字符串（会假红）。

本地正反验证（复刻同一条 bash，跑在重放产物上）：
新版产物 → `注入校验通过`；把该行改回旧写法 → `::error::注入块仍是旧版…` 且 `exit 1`；
注释含反例但代码是 `resolve` → 通过（不误报）。`check-workflows.py`：7 workflow / **117** 片段通过。

## 6b. 同日第四轮：`Working directory ... does not exist`（`java.io` 修好后暴露出来的**真错**）

### 6b.1 现象

第三轮的修复生效了（`Unresolved reference 'io'` 不再出现，注入块整段编译通过、任务正常注册），
但 Rust 编译完、`patchWryUniversalReleaseStep0` 一执行就炸：

```
Execution failed for task ':app:patchWryUniversalReleaseStep0'
> Working directory '/home/runner/work/web2app/web2app/webview-app/.github/scripts' does not exist.
```

### 6b.2 根因

注入块用 `parentFile` **数层数**推导仓库根：

```kotlin
val w2aRepoRoot = rootProject.projectDir.parentFile.parentFile   // ← 少上一级
val w2aScriptsDir = w2aRepoRoot.resolve(".github/scripts")
```

`rootProject.projectDir` 是 `<repo>/webview-app/gen/android` ⇒ 两次 `parentFile` 只到
`<repo>/webview-app`，再拼 `.github/scripts` 就是 `webview-app/.github/scripts`（不存在）。
**到仓库根是三级**（gen/android → gen → webview-app → `<repo>`）。
脚本注释里那句「`.parentFile.parentFile = 仓库根`」本身就是错的 —— 缺陷是**按错误注释写出来的**。

⚠️ 之所以能活到执行期：**Exec 的 `workingDir` 只在执行期校验**，配置期一路绿灯 ⇒ 先白等
3m57s 的 Rust 编译 + 3m23s 的 gradle，最后只丢一句「目录不存在」，看不出是路径算错。

### 6b.3 修复

1. **不再数层数**：从 `projectDir` 逐级向上找第一个含 `patch-android-extras.py` 的
   `.github/scripts`（`generateSequence(...).map{}.firstOrNull{}`）；
2. **兜底**：注入器自己的 `__file__` 就在 `.github/scripts` 里 ⇒ 把它的绝对路径（`as_posix()`）
   固化成字面量，`takeIf { it.isDirectory }`；
3. **两者皆无** ⇒ 配置期直接 `throw org.gradle.api.GradleException(...)`（1 分钟红，附排查提示），
   不再拖到执行期。

### 6b.4 验证

| 反向对照 ×2 | 改回 `parentFile.parentFile` → FAILED（正是新守卫）；去掉 `absoluteFile` → FAILED；两次还原后 `sha256 = c57268ab…` 与改前逐字节相同 |
| selftest 场景 | 从「`<tmp>/gen/android`（只上两级就到顶）」改成**真实布局** `<tmp>/repo/webview-app/gen/android` —— 旧场景正好把这个缺陷放过去了 |

Build 步骤的 `grep -E '^e: '` 会把它拖进主日志，不会再只剩一句 `BUILD FAILED`。

## 7. 遗留 / 建议（未本次执行）

1. `android` 作业的 `continue-on-error: true` 是「静默失败」的根源：建议至少把失败**升级为 workflow 级
   warning/失败**，或加一步「APK 不存在就 `exit 1`」的自检（`add-android-apk-selfcheck`）。
2. `Line 017: android {` 那条 deprecated 提示是 tauri-cli 模板自身的 legacy DSL（项目 `gradle.properties`
   里 `android.newDsl=false`，AGP 9 起默认 `true`，10.0 移除）——**本次未处理**，它不是失败原因；等 tauri-cli
   升级模板时自然消失。
3. 顺带记录的编译警告（非失败）：`src/lib.rs:131 unused variable: app`（`show_float_window` 在非 Windows
   目标上不使用 `app`）。

# 2026-11-01 · workflow 运行记录 / 构建物保留策略：构建物 1 天、运行记录 3 天

> 需求：workflows 运行记录不需要长期保存 —— 构建物保留 1 天即可，运行记录保留 3 天。

## 8. 处理方案

GitHub 侧有两类「保留」，机制不同，分开处理：

| 对象 | 机制 | 处理 |
| --- | --- | --- |
| 构建物（artifact） | `upload-artifact` 的 `retention-days`，不写则取仓库默认（90 天） | 全部上传步骤统一 `retention-days: 1` |
| 运行记录（Actions 页 run 条目 + 日志） | **不会自动删除**（日志过期后条目仍留在列表里变空壳） | 新增 `cleanup-runs.yml` 每天定时删除 3 天前的 run |

### 8.1 构建物保留 1 天

6 个 workflow 里全部 17 处 `actions/upload-artifact` 一律补 `retention-days: 1`：
`build-custom.yml`（5）、`resolve-keys.yml`（3）、`electron-ci.yml`（3）、
`electron-build-custom.yml`（3，其中 2 处原写 3）、`release.yml`（2）、`generate-signing-key.yml`（1）。

⚠️ **含签名材料的 artifact 同样只留 1 天**（`android-signing-key` / `resolve-keys` / `resolve-all`）：
跑完当天必须下载保存，尤其一次性 CI keystore（否则下次覆盖升级时无密钥可续签）。

### 8.2 运行记录保留 3 天（新增 `.github/workflows/cleanup-runs.yml`）

- 触发：每天 18:23 UTC（≈ 北京时间次日 02:23，错峰）+ `workflow_dispatch` 手动补跑；
- 范围：全仓所有 workflow 的 run，只删 `created_at` 早于 3 天前、且 `status == completed` 的
  （排队 / 运行中的一律不动）；删除 run 会连带删掉其日志与残余 artifact，一次清理到位；
- 权限：`DELETE /repos/{repo}/actions/runs/{id}` 需要 `actions: write`，故显式声明
  `permissions: actions: write` + `contents: read`（GITHUB_TOKEN 默认最小权限）；
- 失败策略：单条删除失败只 `::warning::` 不中断（避免一条卡死记录堵住整轮），但只要有失败就 job 标红；
- 本 workflow 自己的 run 同样只活 3 天，不留永久垃圾。

补充：仓库 Settings → Actions → 「Artifact and log retention」可以顺手调低，但**不是必须** ——
artifact 已被 `retention-days: 1` 显式覆盖，日志/记录由 cleanup-runs 删 run 时一并清掉。
