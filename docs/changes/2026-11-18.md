## Electron 壳补上「网页登录账号密码保存 + 自动填充」（自研；订正 2026-10-09 的错误结论）

### 起因

使用者反馈：「账号密码保存功能之前记得有去做，刚才验证发现没有这个功能 electron。先分析。」

分析结论：**该功能只做过 Tauri 壳，Electron 从未实现**。`docs/changes/2026-10-09.md` v1.59 的
「Electron 侧无需改动（Chromium 默认已支持，实测行为一致）」是**错误前提**，且当时并没有 Electron
侧实测记录：

- Tauri：`webview-app/src/webview_hooks.rs` 在每个 webview 上 `SetIsPasswordAutosaveEnabled(true)`
  （Settings4），另有静态守卫与真机记录；
- Electron：全仓库 `password|autofill|credential` 只命中 **HTTP Basic 鉴权**（`app-ipc.ts` 的
  `app.on('login')`）与 URL userinfo；注入清单、两个 preload、`electron-app/docs/` 均无保存密码痕迹。

根因是架构差异，不是开关默认值：Electron 只嵌入 Chromium 的 **content 层**，密码管理器 / 自动填充 UI
属于 **Chrome 浏览器层**（`chrome/browser/password_manager`），未编译进 Electron，也没有 API /
`--enable-features` 能打开（`electron.d.ts` 里 password 只出现在 HTTP auth、客户端证书、`safeStorage`
注释中）。**唯一可行路径是自研。**

### 实现

**主进程**

- `src/main/credentials-logic.ts`（新增，零 Electron 依赖，供单测）：
  - 存储文档 `{ version: 1, entries: [{ origin, username, secret, updatedAt }] }`，`secret` 只存
    `safeStorage.encryptString()` 的 base64；条目上限 64，超出丢最旧。
  - `normalizeOrigin`：只接受 `http(s)`（内置页 / `about:` / `data:` / `file:` 一律拒绝）；
    **回环地址（127.0.0.1 / localhost / ::1）丢弃端口** —— 走本地反向代理时入口端口每次启动都变，
    不丢端口会导致「重启后自动填充静默失效」。
  - 宽容解析：坏 JSON / 脏条目丢弃不抛错；同 origin + 同用户名覆盖，多用户保留（查找取最新）。
- `src/main/credentials.ts`（新增）：`createCredentialStore(file)`
  - 落点 `<data_dir>/credentials.json`（与 `settings.json` 同目录，跟着绿色版走）；
  - `safeStorage.isEncryptionAvailable() === false` 时**拒绝保存**（绝不退化成明文）；
  - 解密失败（数据目录来自另一台设备 / 另一个 Windows 账户）只记日志、**不删文件**，当作没保存过；
  - 原子写（临时文件 + rename）；`clear()` 直接删文件；日志不出现密码。
- `src/main/app-ipc.ts`：新增 `registerCredentialIpc`（`w2a:pwd-lookup` / `-save` / `-forget`）。
  闸门 = **顶层框架** + **内容页 sender**（`deps.isContentSender`）；origin 由主进程从
  `e.senderFrame.url` 推导，渲染进程无法指定；密码长度上限 1024（防御性）。
- `src/main/index.ts`：创建凭据存储（探针隔离到 `%TEMP%/w2a-probe-store`）；新增 `isContentSender`
  （单窗口 = 主窗 webContents，页签 = 任一页签视图）；`clearWebData` 注入 `clearCredentials`。
- `src/main/tabs.ts`：新增 `ownsWebContents(id)`，页签内容视图才能通过内容页闸门。
- `src/main/web-data.ts`：「清除全部浏览数据」一并清 `credentials.json`，文案改为
  「已清除缓存、Cookie、已保存的账号密码等全部浏览数据」。

**渲染侧（两处 preload，隔离世界，无页面桥）**

- `src/renderer/preload.ts` / `src/renderer/tab-preload.ts`：各新增一段**逐字一致**的
  `installPasswordManager()`（沙箱 preload 不能相对 require 共享模块，一致性由
  `test/password-contract.test.ts` 直接比对两段源码）。逻辑：
  - 自动填充：首屏（DOMContentLoaded / `load`）、**URL 变化（主世界 history 钩子，覆盖 pushState）**、
    **DOM 变动（MutationObserver 防抖）**、`focusin` 时按当前页面查凭据，找第一个可见密码框，
    用户名按 `autocomplete` → 同 form 内相邻文本输入 → `name/id` 关键词猜；
    已输入过不覆盖；赋值走 `HTMLInputElement.prototype` 的 value setter 并派发 `input`/`change`
    （React 等受控组件可感知）；**填充成功后右上角提示「密码已自动填充」（4s 自动消失、无按钮）**。
  - 保存：只认 `submit` 且 `isTrusted` + `navigator.userActivation.isActive`；**不 preventDefault**
    （DOM 气泡活不过一次导航，阻止提交再恢复会改站点行为）。**提交只暂存到主进程内存（60s TTL，
    不写盘）**，确认登录成功（新文档无可见密码框 / 本页登录表单消失）才落盘，失败不覆盖旧密码；
    成功后右上角自绘气泡「已保存 <用户名> 的账号密码 / **删除**」8s 自动消失（**按钮语义 = 直接删掉
    该站点凭据**，不用「撤销」）；样式逐项走 CSSOM（严格 CSP 的 `style-src` 不拦 JS 赋值）。
  - 不向页面主世界暴露任何桥（明文只存在于 preload 隔离世界的 DOM 赋值过程；页面脚本无法主动查询）。
  - 内置页（`splash:` / `settings:` / `shell:` / `floaticon:`）与非 http(s) 文档早退。

### 取舍与限制（首版最小集）

- **不做「提交前询问」**：DOM 气泡无法跨导航存活；阻止提交再 `requestSubmit()` 会二次触发站点
  handler（SPA 会双登录）。改为「先保存 + 气泡可删除（直接删掉该站点凭据）」。
- 不做多账号选择（同 origin 取最新）、不做密码更新提示 / 生成、不做凭据管理页。
- 纯 SPA 无 `submit` 事件的登录（按钮 `type=button` + `fetch`）捕获不到；跨源 iframe 内登录框不处理。
- 两壳机制不同：Tauri 是 WebView2 原生气泡，Electron 是自绘 DOM 气泡；**不得在 Tauri 再注入同一段**
  （会双弹窗）。

### 补充（同日）：自动填充触发时机优化

真机反馈：保存 / 填充本身正常，但**必须点了输入框才触发**；「刚保存 → 退出 → 重新登录」还要先刷新页面再点输入框。
根因是原实现只在 `DOMContentLoaded` / `load` / `focusin` 尝试，且 `fillTried` 一旦置位就再不重试：

- SPA 退出登录走 `pushState` / `replaceState` 换路由，**不派发任何事件**，preload 不会重跑；
- 登录框常在首屏后才挂载，首屏那次 `findLogin()` 找不到表单；
- `fillTried` 是文档级永久闩锁，换路由后即使有空密码框也不再填。

改为：

1. **URL 变化即时触发（事件驱动，零轮询）**：`pushState` / `replaceState` 不派发事件，Navigation API
   的 `navigate` 实测也不为它们触发（首版试过，探针 18e2 直接失败），因此在**主世界**用
   `webFrame.executeJavaScript` 打一个幂等的极小 history 钩子（`__web2appUrlHook`，不可枚举 / 不可重定义），
   变化时派发 `__web2app:url-change` DOM 事件通知隔离世界；另有 `popstate` / `hashchange` / `pageshow`
   （bfcache 恢复）。收到即 `syncUrl()` 重置 `fillTried` / 查询缓存并尝试填充。
2. **DOM 变动触发**：`MutationObserver`（`childList` + `subtree`，300ms 防抖）覆盖「登录框后渲染 / 重建」。
3. 保留首屏与 `focusin`；凭据查询结果按 URL 缓存，避免频繁 IPC。
4. 只要页面上存在**空着的密码框**就直接填，不依赖点击；用户已输入（或页面自己填了）不覆盖。

**性能取舍（评审问题：「500ms 轮询是不是影响性能」）**：单次轮询成本只是读 `location.href` 做字符串
比较（微秒级），CPU 可忽略；真正代价是每秒 2 次无谓唤醒、且每个内容页各一份（页签模式会累加），
以及让页面永不完全 idle。故最终版**没有任何常驻轮询定时器**，URL 变化全走事件。
`MutationObserver` 的开销也收敛：`fillTried` 置位后回调只做一次 URL 同步就返回；没存过凭据的站点
查一次即置位，不再反复调度；有凭据的站点填完就停。

探针新增单窗口 18e2（清空输入框 + `pushState` 换路由，3s 内应自动重填）与页签 P13 同项断言。

### 补充（同日·二次）：真机「必须点输入框才填充」的根因与修复

事件驱动改造上线后真机仍复现，于是先用夹具复现了两种真实场景（新增 `/login-late.html`：表单 800ms 后
才插入；`/login-hidden.html`：表单先在 DOM 里但 `display:none`，800ms 后改 style），**两条都失败**：

- 根因 1：`MutationObserver.observe(document.documentElement, …)` —— preload 执行时文档树尚未建好，
  `document.documentElement` 可能为 **null**，`observe(null)` 直接抛错，**整个观察器失效**；
  该抛错发生在函数末尾，前面的 focusin 仍有效 ⇒ 表现就是「只有点输入框才填」。
- 根因 2：即使观察器正常，也只观察了 `childList`；`display:none → block` 只产生 **attributes** 变动，
  不会触发回调。

修复：改为观察 **`document`**（始终可用）+ `attributes`（`attributeFilter: ['class','style','hidden']`）；
`observe` 包 try/catch 并在 `DOMContentLoaded` 重试；另加 **有限次一次性补试**（300/800/1600/3000ms，
每文档 4 个定时器、3s 结束，**不是轮询**）覆盖 CSS / 布局 / 可见性晚于 DOMContentLoaded 的站点；
补 `visibilitychange`（窗口回前台时补一次）。

探针新增 18g 两条（表单后插入 / 隐藏变可见，均不点击、不换 URL）与页签 P13 同项；修复后单窗口
**171/171**、页签 **69/69**，`unit` **212/212**。

### 补充（同日·三次）：复审后的行为修正

复审发现三处会在真实站点踩到的问题，一并修掉：

1. **用户名被站点预填就整表单跳过**（原判断 `pass 非空 || user 非空`）：很多站点会记住账号并预填用户名，
   导致密码永远不填。改为只看密码框：密码非空才停；用户名非空时**若与保存的用户名一致则只补密码**，
   **若不一致（站点预填了另一个账号）则绝不灌入密码**，避免登错账号。
2. **SPA 整块重渲染登录表单后不再填充**：`fillTried` 是文档级闩锁。新增 `filledPass` 引用，
   观察器发现「填过的密码框已断开（`!isConnected`）」时重置并重试；**同一元素只是被清空则不重填**，
   避免与站点互相打架。
3. **IPC 瞬时失败被当成「没存过」**：`lookup` 抛错时现在回滚 `lookupDone`，下一次触发会重试，
   不再整页放弃。
4. 文案收尾：代码注释里残留的「撤销」统一为「删除」。

新增夹具 `/login-prefilled.html`（预填同一账号）、`/login-other-user.html`（预填其他账号）、
`/login-rerender.html`（1.5s 后整块重渲染），探针 18h 三条覆盖。单窗口 **174/174**、页签 **69/69**、
`unit` **212/212**。

### 补充（同日·四次）：登录成功才落盘 + safeStorage 异步化

复审列出的两个待办已落地：

1. **提交只暂存，确认成功才写盘**（修「输错一次密码就覆盖好密码」）：
   - 新通道 `w2a:pwd-stage` / `w2a:pwd-commit`，旧的 `w2a:pwd-save` 删除；
     暂存只在**主进程内存**（`webContentsId → 凭据`，60s TTL，绝不写盘），提交后气泡文案改为
     「登录成功后自动保存账号密码」。
   - 成功信号：新文档 `readyState === 'complete'` 后再等 1.2s 且**没有可见密码框** ⇒ 落盘；
     本页提交后登录表单消失（SPA）⇒ 立即落盘；新页面仍有可见密码框（失败重载 / 多步登录）⇒
     丢弃暂存，**不覆盖**旧密码。归属仍用登录页的 origin（成功跳去别的域名也不改）。
2. **`safeStorage` 改异步 API**：`isAsyncEncryptionAvailable` / `encryptStringAsync` /
   `decryptStringAsync`（Electron 45 起同步版已废弃、日志会刷警告）；解密返回
   `shouldReEncrypt` 时顺手回写新密文，失败不影响本次填充。

探针：新增成功夹具 `/login-success.html`（提交后 80ms 跳 `/login-ok.html`）；18a0「失败不落盘」
与 18a1「暂存提示」；18a 改为确认跳转后才断言写入；18f 删除改走成功页；P13 同步。
单窗口 **176/176**、页签 **69/69**、`unit` **213/213**。

**探针踩坑**：跨页导航后 Chromium 会把焦点恢复到上一个密码框，且 `sendInputEvent` 是异步投递 ——
必须先 `blur()` + 重新聚焦用户名框，并等 ~120ms 再读输入值，否则会读出空串 / 全灌进密码框。

### 探针踩坑（已写进代码注释，避免下次重踩）

1. `HTMLFormElement.requestSubmit()` 的 `submit` 事件 **`isTrusted` 为 true**（浏览器派生，不是脚本伪造），
   不能当「程序化提交」的反向用例；反向用例必须用 `dispatchEvent(new Event('submit'))`。
2. `webContents.executeJavaScript(code, true)` 会附带 **user activation** —— 想模拟「站点脚本自己提交」
   必须传 `false`。
3. 隐藏窗口下的子 `WebContentsView` 收不到面向 DOM 的键鼠输入（`Ctrl+W` 能过是因为它在主进程
   `before-input-event` 处理）；页签探针改用 `executeJavaScript(code, true)` + `requestSubmit()`
   （同样满足 `isTrusted` + 用户激活），单窗口仍用真实键入 + 真实点击覆盖输入管线。

### 补充（同日·五次）：独立复审（复核 + 修 4 处真问题）

对上线版本做一次独立复核（逐条读代码 + 增补运行期断言）。结论：加密 / 落盘 / sender 闸门 /
填充触发时机都对，但**「确认登录成功才落盘」这条链在「同一文档（SPA）」这一半是坏的** —— 探针原先
只覆盖跨文档跳转（`/login-success.html`），所以全绿漏过。

1. **观察器回调无条件提前 `return` ⇒ SPA 同文档登录永不落盘**（功能级）。
   `if (fillTried) { if (!filledPass || filledPass.isConnected) return … }` 挡住了两条最常见的
   SPA 收尾：① 表单只是被 `display:none` / 移除但密码框节点仍在（`filledPass` 连着 DOM）；
   ② 本页没存过凭据（`filledPass` 为 null，登录框在首屏就渲染出来的站点都是这种）。
   两者都会让 `kick` 不再被调度 ⇒ `maybeCommit` 等不到触发点（用户看到的只有「登录成功后自动保存」
   提示，实际什么都没存）。改为**只在 `stagedHere` 为假（不在等待落盘）时早退**。
2. **新文档 1.2s 确认探针会把本页刚提交的暂存丢掉**（功能级）。
   探针带 `hasPasswordField: true` 过去时，主进程按 `still-login` 丢弃暂存 —— 用户若在文档加载后
   1.2s 内提交（自动填充后点一下就是这种情况），这次登录永远存不进去。改为定时器**触发时**重新判
   `stagedHere`：本页有自己的暂存就交给同文档那条路。
3. **重加密回写用旧文档快照**（数据级）。`lookup` 里 `decryptStringAsync` 是 `await`，期间别的页签
   可能已保存新凭据 / 删掉该条目；原先拿开头那份 `doc` 去 `upsertCredential` 会覆盖新值、还会把
   已删除的条目「复活」。改为**回写前重新读盘**，且只在「该条目仍在、密文仍是本次解出来的那份」时才写。
4. 附带：`maybeCommit` 拿到**任何明确答复**（`still-login` / `none` / 写盘失败 / 加密不可用）都置
   `stagedHere = false` —— 原实现只处理 `still-login`，其余分支会让每次 DOM 变动都再问一次主进程
   （重负载站点上是持续的 IPC，且结果永不改变）；两处 preload 文件头的测试文件名笔误
   （`password-preload-contract.test.ts` → `password-contract.test.ts`）一并订正。
5. **「清除全部浏览数据」清不掉待落盘暂存**：清完 `credentials.json` 后，一份仍在 60s TTL 内的暂存
   会在下一次页面事件把文件原样写回来（`清了却还会回来`，与 `web-data.ts` 里反复强调的坑同源）。
   `registerAppIpc` 改为返回「清空暂存」钩子，`clearWebData` 的 `clearCredentials` 里**先清暂存再删文件**。
