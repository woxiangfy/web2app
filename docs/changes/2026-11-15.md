# 2026-11-15 变更记录

## electron-app：多页签「下载页签自动关闭」（对齐浏览器行为）

### 问题

使用者的站点下载逻辑：点击后 `window.open` 开一个新页签指向附件地址，下载完成/开始后浏览器会把
这个只为下载而开的新页签自动关掉、回到点击时的页面。Electron 壳此前不关：下载结束后留下一个
空白页签，用户要手动点 × 才能回到原页面。

根因：Electron 的 `setWindowOpenHandler` 一律 `deny` + `spawnTab(url)`，附件响应
（`Content-Disposition: attachment`）**不提交文档**，页签自建出来就是空白且一直留着。

### 修法

判据只有一条：**发起下载的页签是否提交过文档**（`did-navigate` 之后为 true）。下载响应不产生
文档提交 ⇒「只为下载而开的页签」永远是未提交状态 ⇒ 下载落盘/取消后关掉它；已加载过页面的页签
跳转到附件时**不关**（浏览器同样保留当前页签，关掉会弄丢用户正在看的页面）。

| 位置 | 改动 |
| --- | --- |
| `src/main/tab-order.ts` | 新增纯规则 `shouldCloseTabAfterDownload(hasCommittedDocument)`（零 Electron 依赖，可单测） |
| `src/main/tabs.ts` | `Tab` 新增 `committed` / `opener`；`spawnTab(url, opener)` 记录打开者；新增 `markTabCommitted()` / `closeTabAfterDownload(webContentsId)`（关闭后激活回到打开者） |
| `src/main/tab-spawn.ts` | `window.open` 拦截时把当前页签 label 作为 opener 传入；逐视图挂 `did-navigate` → `markTabCommitted` |
| `src/main/page-behavior.ts` | `attachDownload` 新增可选注入 `DownloadHooks`：`onSaveChoice(webContentsId, saved)`（另存为选择完成后回调）、`pickSavePath`（默认弹模态对话框；探针注入固定临时路径） |
| `src/main/index.ts` | 多页签模式下 `onSaveChoice` → `closeTabAfterDownload`；探针模式注入 `%TEMP%` 落盘路径（否则模态对话框会把断言挂住） |
| `src/main/probe-server.ts` / `probe-tabs.ts` | 新增 `/dl.txt` 附件夹具与 P14 两条成对断言 |
| `test/tabs.test.ts` | 纯规则单测（未提交 → 关；已提交 → 不关） |

### 时序与安全性

`onSaveChoice` 在 `item.setSavePath()` + `resume()`（或 `item.cancel()`）**之后**才回调，避免
在下载项尚未落盘时销毁发起页签。P14 的「附件已完整落盘」断言专门验证这一点：探针实测关闭
发起页签不影响下载本身（文件内容完整）。

## 追加修复（双壳）：`window.open` 被拒 ⇒ 站点兜底造成「一次点击两次下载 / 两个另存为」

### 现象与根因

用户报障：Electron 版点「保存」后新页签关闭了，但**保存框还在**，必须再点一次才下载。

实测（页签探针）确认：页签模式 `setWindowOpenHandler` 返回 `deny`，**页面里的 `window.open()`
拿到的是 `null`**。站点普遍据此判定「弹窗被拦截」，立刻对**同一地址**再做一次
`location.href` 兜底 —— 同一次点击因此产生**两条下载**：一条来自新页签、一条来自原页签。
于是弹两个「另存为」；点掉第一个时新页签按 P14 关闭，第二个对话框还留着，用户必须再点一次。
（下载目录里出现两份文件也是同一原因。）

WebView2 侧同理：`NewWindowRequested` 被 `SetHandled(true)` 收走且未 `SetNewWindow` 时，
`window.open()` 同样返回 `null`，Tauri 壳存在完全一样的问题。

### 两次失败的尝试（都被真机证伪）

1. **按「目标 URL + 打开者 + 3s」事后判重**：在第二次下载到达时取消它。硬伤 ——
   兜底地址常带**每次变化的签名 / 时间戳**（与 `window.open` 的目标不同字 ⇒ 判重不命中），
   3s 窗口也是拍出来的（太短盖不住慢兜底，太长误杀「用户真的又点了一次」）。
2. **`allow` + 建隐藏窗口后立刻销毁**：`window.open()` 确实拿到非 null 了，但站点另一条
   常见判据是 **`w.closed`** —— 隐藏窗口下一拍就被销毁 ⇒ `w.closed === true` ⇒ 站点照样
   `location.href` 兜底 ⇒ 仍是两个「另存为」（真机复现：「点第一次保存文件已下载，点第二次
   保存文件名才是实际的」）。

### 最终修法（Electron）：不再 deny，且隐藏窗口**活到这次下载结算**

| 位置 | 改动 |
| --- | --- |
| `src/main/tab-spawn.ts` | `setWindowOpenHandler` 不 `deny`，改 `allow` + `overrideBrowserWindowOptions{ show:false, skipTaskbar:true }` ⇒ 页面拿到真实 WindowProxy（`if (!w)` 判据失效）；隐藏窗口的存活期覆盖**整次下载**：下载 `done`、它自己提交文档（普通页面弹窗）、或 20s 兜底才销毁。新页签仍承接这次导航与下载（用户报障里那个「应自动关闭的页签」） |
| `src/main/tabs.ts` | 隐藏弹窗登记改为 `registerHiddenPopup(id, cleanup, capMs)` + `attachHiddenPopupToTab(id, tabLabel)`：**绑到承载它的新页签上，页签关闭（下载结算后自动关）时才销毁** —— 早于结算销毁会让页面里的 `w.closed` 变 true；`isHiddenPopup()` 供下载判重（它自己抢先发起的那条直接丢弃，真正弹框的是新页签） |
| `src/main/page-behavior.ts` | `DownloadHooks` 增 `onDownloadStart`（下载一建立就取消隐藏窗口的兜底超时 —— 它要活到结算）；`shouldDropDownload` 仍在 `pause`/弹框**之前**判重并 `cancel` |
| `src/main/index.ts` | 判重：`isHiddenPopup` → 丢弃；`shouldDropPopupFallback`（同地址 + 同打开者 + 3s）留作纵深防御 |

为什么这是「从根上」而不是「事后猜」：站点两条判据（`!w` / `w.closed`）在**整个下载期间**
都为 false，兜底代码根本没有机会执行 —— 不依赖 URL 是否逐字相同、也不依赖时间窗。

### 验证

- 页签探针 **P15 改写为成对断言**：页面执行 `window.open('/dl.txt')` 并自己记录
  「是否走了兜底」，断言 ① 返回值 `!== 'null'`、② 兜底未执行、③ **下载进行中
  `w.closed === false`**、④ 页签数回落、⑤ 附件完整落盘 ⇒ `--probe --tabs` **59/59**。
  ⚠️ 判据不再依赖「下载次数 / 取消计数」这类间接信号（那正是第一版被推翻的原因）。
  ⚠️ 探针模式下 `onSaveChoice` 刻意延后 600ms 关页签，模拟「用户还停在另存为对话框前」，
  否则下载瞬间结算，`w.closed` 断言就没有观察窗口。
- Electron `unit` **188/188**、typecheck / build ✅、单窗口探针不受影响（下载钩子只在页签模式接线）。
- Tauri `cargo test --all` **324 passed / 6 ignored**（lib **249** / proxy 34 / resolve 19 + 22）、fmt/clippy ✅。
- ⚠️ 仍需真机确认：点一次真实附件链接 → **只出现一个**「另存为」，且文件名与该 URL 在
  Chrome 里给出的一致（同一个请求，名字取自同一份 `Content-Disposition`）。
- ⚠️ **已知残留**：`window.open()` 不带 URL、随后由脚本 `w.location = …` 的写法，
  `did-create-window` 拿不到目标地址 ⇒ 退化成「开一个空白页签」。

### Tauri 侧的差异（未做等价改造）

WebView2 要让 `window.open()` 返回非 null，必须用
`ICoreWebView2NewWindowRequestedEventArgs::put_NewWindow` 提供**另一个真实的 ICoreWebView2**
（等于把隐藏窗口那套在 WebView2 上重做一遍：另建 Environment/Controller + 生命周期管理），
改动面与风险都远大于 Electron（Electron 的 `allow` 是一行声明）。故 Tauri 侧**仍按 URL 判重**：
`NewWindowRequested` **同步**登记目标 URL + 打开者（不能塞进建窗线程，晚了就认不出），
`DownloadStarting` 在 `ask_save_path` **之前** `should_drop_popup_fallback`，命中
`SetCancel(true) + SetHandled(true)`；纯判据 `popup_fallback_is_duplicate` 有单测，
`capability_contract` ⑨ 钉住「登记早于建窗、判重早于弹框」的顺序。**局限与第一版相同**
（兜底地址带新签名时失效）—— 是否值得为此在 WebView2 上重做隐藏窗口，待用户按真机反馈决定。

## webview-app（Tauri）：多页签「下载页签自动关闭」（与 Electron 同一行为契约）

### 为什么 Tauri 不能照搬 Electron 的判据

Tauri 没有 `did-navigate` 这类「文档已提交」的窗口级事件可复用：`WebView2` 的
`NavigationCompleted` 对「转成下载」的导航同样会派发（带失败状态），无法区分
「提交了文档」与「这次导航变成了下载」。另外 tab 的**首文档是本地占位页**
（`http://tauri.localhost/index.html`），它本身就是一个真实文档 —— 直接按「有没有文档」
判定会让每个 tab 一建出来就算「已提交」，自动关页签永远不发生。

### 修法（判据：初始化脚本只在真实文档创建时执行）

| 位置 | 改动 |
| --- | --- |
| `src/tab_doc_ready.js`（新增） | 真实文档创建时 emit `web2app:tab-doc-ready`（含 label + 一次性 token）；**本地占位页早退**；只在主框架；桥未就绪时最多重试 ~1s。附件下载不产生文档 ⇒ 脚本不执行 ⇒ 该 tab 永远「未提交」 |
| `src/tabs/state.rs` | `TabInfo` 新增 `committed` / `opener`；新增 `TAB_DOC_READY_EVENT` 与纯规则 `should_close_tab_after_download(committed)`（与 Electron `tab-order.ts` 同一条） |
| `src/tabs/ipc.rs` | 新增 `mark_tab_doc_ready()`（校验 label/token 后置 `committed`）；`open_new_tab_from_request()` 增 `opener` 参数 |
| `src/tabs/window.rs` | `spawn_tab_with_target(app, start, opener)` 记录打开者；建窗 builder 注入 `tab_doc_ready.js`；新增 `close_tab_after_download()` |
| `src/webview_hooks.rs` | `NewWindowRequested` 传 opener；`DownloadStarting`：取消 → 立即关；确认保存/对话框不可用 → `close_tab_when_download_settles()` 等下载到终态再关 |
| `src/lib.rs` | 监听 `TAB_DOC_READY_EVENT` → `mark_tab_doc_ready` |
| `src/contract_tests/capability_contract.rs` | 新增 ⑨：事件名三处一致 + 占位页早退 + 主框架/令牌守卫 + builder 注入 + `DownloadStarting` 接线 |
| `src/tabs/tests.rs` | 纯规则单测（未提交 → 关；已提交 → 不关） |

### 时序安全性

`DownloadStarting` 回调运行在**该 tab 自己的 COM 回调栈**里，就地 `destroy()` 属于
「在自己的回调里销毁自己」。`close_tab_after_download()` 统一切后台线程 +
`run_on_main_thread` 延后到下一轮事件循环，并在排队后**重新校验**（期间用户可能已关掉它
或它已提交文档）。首页那一签与已提交文档的页签一律保留；激活态按 `opener` 回到
「点击时的页面」。

⚠️ **关闭时机不能是「另存为选完就关」**：WebView2 的下载依附于发起它的 webview，窗口销毁会
让进行中的下载以 `UserShutdown` 中断（MSDN：此类中断不支持续传）—— 早关等于把用户正在写
的文件截断。故确认保存后挂 `DownloadOperation::StateChanged`，等 `Completed` /
`Interrupted` 终态再关；取消分支立即关（下载根本没开始）。代价是 Tauri 侧空页签会保留到
下载结束，Electron 侧则在下开始后即关 —— 行为结果一致，时序略有差异。

### 验证

- `cargo fmt --all` ✅、`cargo clippy --all --all-targets` ✅
- `cargo test --all`：**324 passed / 6 ignored**（lib **249** / proxy 34 /
  resolve-core 19 / resolve-tool 22）
- ⚠️ 未做真机验证：本机无 TXT 解析与目标站点环境，Windows 真机需人工点一次
  `window.open` 附件链接确认「另存为选完后空页签自动消失并回到原页面」。

### 文档

- `webview-app/AGENTS.md`：单壳专属脚本清单补 `tab_doc_ready.js`、多页签特性行补「下载页签自动关闭」。
- 根 `AGENTS.md` §3.4.1 单壳专属清单同步。

## 追加修复（同日晚）：隐藏弹窗自己也在下载，且在 Windows 上冒出**第二个「另存为」**

安装版真机取证（`WEB2APP_DEBUG=1`，日志 `%APPDATA%\lcjm\logs\startup.log`）拿到的链路：

```
页签模式拦截到新窗口请求：…/OrderDown/downCertNormal?s=…
隐藏弹窗创建：wc=3 disposition=foreground-tab url=…
下载请求：<文件> wc=4   ← 新页签（这条弹了「另存为」）
下载请求：<文件> wc=3   ← 隐藏弹窗：下载项被丢弃，但**窗口本身仍是可见的第二现场**
忽略重复下载（隐藏弹窗 / 弹窗兜底）：<文件> wc=3
下载：<文件> → …\Downloads\… wc=4
```

- **根因**：`allow` 建出来的隐藏窗口**真的执行了 Electron 替它发起的那次附件导航**，于是它自己
  也跑了一遍下载。`shouldDropHiddenPopupDownload` 只丢掉了下载项，**没能阻止这个窗口存在**；
  Windows 上它以「下载地址」为标题浮在主窗口里（`show:false` 兜不住），并在自己身上弹框 ——
  用户看到的「两个另存为」里，第二个就是这个窗口。
- **修法**（`src/main/tab-spawn.ts` 的 `did-create-window`）：这个窗口的唯一用途是让页面的
  `window.open()` 拿到非 null，因此**不许导航、不许下载、不许冒头** —— `stop()` +
  `loadURL('about:blank')`、`will-navigate` 一律 `preventDefault`（站点 `w.location = 下载地址`
