## v1.60（2026-10-09）

**修复 Android 手动打包后「转圈十几秒 → 白屏、无错误无重试」**（使用者需求：build-custom.yml 打 Android 包，安装后打开直连 HTTPS 站点加载很慢、最终空白）：

- **排查结论（框架/站点侧全部排除）**：
  - 站点正常：目标 `https://ai260926.osfipin.com/...`（122KB 单文件静态页、正文直写 HTML）从本机 curl 稳定 200/0.1s，Android WebView UA 无差别响应、连续 5 次无冷启动抖动，页面零外部子资源；TLS 证书链校验有效。
  - 框架链路正常：wry 0.55.1 Android 的 WebView 设置（JS / DOM storage / database 均开）、自定义协议 workaround 匹配（外链 `https://` 不会被误判为 `http://<scheme>.localhost`）、`shouldOverride` 无 handler 默认不拦截、tauri 2.11.5 导航不重写外链 URL、Manifest 含 INTERNET 权限且 CI 置了 cleartext——逐源码确认。**splash 启动页（转圈可见）本身就证明 JNI / 自定义协议 / Rust 侧在 release 包里工作正常，R8 裁剪嫌疑排除**。
  - 结论：请求在**设备网络路径**上失败（WebView 停在空白错误文档），而壳把这种失败呈现成了白屏。
- **根因（壳侧两个叠加缺陷）**：
  1. `src/loading.js` overlay 模式的就绪轮询在 `CAP_MS=15s` 到点时**无条件 `done()` 淡出**——Android WebView 网络失败停在「空白错误文档」（不像桌面 Chromium/WebView2 会画出带错误码的错误页），淡出后只剩纯白；且 30s 的 `FAIL_MS` 失败卡因 `state==='done'` 被 `toFail` 静默吞掉，用户既看不到原因也没有重试入口。时间线（~8s 慢提示 → ~15s 白屏）与真机现象逐秒吻合。
  2. 壳层在 Android 上拿不到、也不主动探测 WebView 的网络失败原因（wry/tauri 不暴露 `onReceivedError`），只能给固定 30s 通用超时文案。
- **修复 1（`src/loading.js`，双壳单一真源，Tauri/Electron 同步生效）**：CAP 到点时若正文**仍为空白文档**，改为进入失败卡（警示图标 + 具体文案 +「重试」按钮，overlay 重试走 `location.reload()`），不再淡出露白；正文有任何内容的页面仍在检测到的那一拍立即 `done()`，慢页零影响。`fail(title, detail, soft)` API 新增第三个参数：soft 为真且页面已有正文时忽略本次结论。
- **修复 2（`src/bootstrap.rs`，`#[cfg(not(windows))]`）**：导航提交后**并发**一次轻量可达性探测（reqwest + rustls，是非 Windows 既有的代理依赖，零新增 crate；移动端 UA、连接超时 8s / 总超时 20s、只取响应头不读正文、跟随 ≤5 次跳转）。收到任意 HTTP 响应（含 4xx/5xx）即视为传输层可达、不插手；失败则按 **DNS/连接失败 · 超时 · TLS 握手/证书 · 请求构造 · 其它** 五类生成「标题 + 含主机名的详情」，回主线程以 **soft** 方式 eval 给加载层——比 30s 通用超时更早（典型 DNS/拒连在数秒内）给出可看懂的原因；soft 保证探测假阴性（如企业根证书系统信任库认可而 rustls/webpki-roots 不信任）绝不盖住其实已渲染成功的页面。文案只放主机名，不放完整 URL（防代理令牌 / userinfo 泄漏）。
- **测试**：主 crate 106 → **110**（bootstrap +2：五类失败文案含主机名/关键词且标题互异、文案不引入凭据；loading.rs 契约 +2：钉死「CAP 空白文档不得无条件 done」旧字符串不得回归、soft fail API 形状），工作区 **183 通过 / 6 ignored**（resolve-core 19 + resolve-tool 22 + w2a-proxy 32 + 主 crate 110）。`cargo fmt` 0 diff、`cargo clippy --all-targets -D warnings` 0 告警。Android gated 分支本机无 NDK 未本地编译，由 CI 的 Android 流水线把关。
- **交付提示**：① 旧的 Android 打包产物需**重新打包**才生效，新版网络失败时会直接看到具体原因与「重试」按钮；② 若失败卡显示「无法连接服务器 / 连接超时」，请先用手机自带浏览器打开同一网址、并切换 Wi-Fi/移动网络比对——那说明是设备当前网络到该站点不通（内网穿透类域名在运营商网络下常见），而非 App 故障；需要逐字网络错误码时可用 `adb logcat | findstr /i "chromium net::"` 抓 WebView 日志。

## v1.61（2026-10-09）

**纠正 v1.60 的单方面归因：手机浏览器访问同一网址完全正常，「设备网络不通」假设被使用者否定。** v1.60 的静态排查只证明了「框架默认不拦外链、壳侧会把空白错误文档呈现成白屏」，并未取得 WebView 运行时证据；reqwest 探测与 WebView 不是同一网络栈（TLS 实现/信任库/UA 都不同），其结论不能用来给真机现象定性。本次不再猜测根因，改为让 App **自己把现场显示在失败卡上**，一次重打包 + 一张截图即可终结定位。

- **改动（`src/loading.js`，双壳单一真源）**：
  - 新增 `diagText()`：CAP 空白失败卡与壳侧 `fail(t,d,soft)` 接管时，详情区追加多行「现场诊断」——
    - **地址**（`location.href`）：仍是 `http://splash.localhost/` = 导航没离开启动页（壳内导航链问题，与网络无关）；已是目标域名 = 外链文档已开始加载但没渲染出正文；
    - **状态**（`document.readyState` + body 元素总数）：区分「文档没解析」与「解析了但不可见」；
    - **HTTP**（`PerformanceNavigationTiming.responseStatus`，Chromium 123+ 支持，老 WebView 显示 `?`；net 错误为 0）+ 子资源数 + 导航耗时；
    - **UA**（`navigator.userAgent` 全文）：直接暴露 **Android System WebView 真实版本**——无 GMS 的国产 ROM 上 WebView 可能长期不更新，过旧内核在新证书链（TLS 1.3 / 现代根证书）或 HTTP/2 上失败、而独立更新的手机浏览器正常，是「浏览器能开、壳内白屏」的首要嫌疑；
    - **脚本错误**：document-start 起以捕获阶段监听 `error` / `unhandledrejection`，记录最后一条页面侧错误（含资源加载失败），覆盖「文档到了但页面脚本在内核上崩掉」。
  - 详情样式加 `white-space:pre-wrap;word-break:break-word`，保证多行诊断可读；CAP 文案改为中性表述（不再断言「网络无法连接」）。诊断只显示在用户自己的屏幕上，不上报、不外发。
- **取证结论（静态，供后续）**：splash.html 的 body 只有三个 `<script>`；builder 注入的 OVERLAY_SCRIPT 在 document-start 先于内联的 `__web2appLoadingMode='splash'` 执行，故 splash 文档上的加载层实际以 **overlay 模式**运行（SLOW 8s / FAIL 30s / CAP 15s）。直连配置下 `prepare_navigation` 毫秒级完成、导航立即提交，故本次 15s 白屏发生在**外链文档**而非 splash；该模式错配仅在「导航 >15s 未提交」时才有体感影响，暂不改动，先靠诊断卡拿真机结论。
- **测试**：loading.rs 新增契约 `overlay_failure_card_carries_on_screen_diagnostics`（钉住地址/导航时序/responseStatus/UA/换行样式/diagText 拼接六个标记），主 crate 110 → **111**，工作区 **184 通过 / 6 ignored**；`node --check src/loading.js` 通过；`cargo fmt` 0 diff、`cargo clippy --all-targets -- -D warnings` 0 告警。

## v1.62（2026-10-09）

**先修两条「不看网络就能证明」的必然缺陷**（使用者要求：打包太慢，先把确定的问题修掉）。这两条都不是猜测——都能从源码逐行推出来，且都是**静默失败**（编译零警告、CI 全绿、只在真机上以「白屏 / 点了没反应」现形）：

- **缺陷 1：启动页的加载层跑在错误模式（overlay 语义）**。
  - 加载层的模式由 `window.__web2appLoadingMode` 在脚本执行前决定。`loading.js` 经 **document-start** 注入（WebView2 `AddScriptToExecuteOnDocumentCreated`），而 `splash.html` 里那行内联的 `__web2appLoadingMode='splash'` 在 `<body>` 里 —— **永远晚于注入脚本，来不及生效**。此前只有 `tabs.rs::create_tab_window` 注册了模式标记前置脚本，`lib.rs::build_main_window`（单窗口主窗）**漏了**。
  - 后果：启动页被当成「目标页」跑 —— SLOW 8s / FAIL 30s，并且装上 overlay 的空白文档硬上限 `CAP_MS=15s`。启动页 body 只有三个 `<script>`（`bodyEmpty()` 恒真）⇒ **导航若超过 15s 未提交，到点必然弹出「页面长时间为空白」失败卡**，把一次正常但偏慢的启动（DNS/TXT 往返 + 代理起停）误报成加载失败。v1.60 之前的表现更糟：CAP 分支无条件 `done()` 淡出 ⇒ 用户只看到「转圈十几秒 → 纯白」且 30s 失败卡被 `state==='done'` 吞掉（v1.61 记录过这段，当时判断「暂不改动」，本次修掉）。
  - **修复**：`lib.rs::build_main_window` 在 `loading::OVERLAY_SCRIPT` **之前**注册模式标记（照 `tabs.rs` 抄，判据换成启动页形态）：`location.hostname === 'splash.localhost' || location.protocol === 'splash:' ? 'splash' : 'overlay'`。启动页由此恢复 splash 语义（SLOW 5s / FAIL 40s「启动超时 + 重试」、不装就绪监听），与 Electron 侧行为对齐（Electron 的 preload 对内部页面整体跳过注入，只跑内联脚本，顺序恰好成立 —— 同一个缺陷因此只在 Tauri 壳上现形）。
- **缺陷 2：启动页「重试」是条死路**。
  - wry 的 `custom_protocol_workaround::apply_uri_work_around` 在 **Windows 与 Android 都把** `splash://localhost/` 改写成 `http://splash.localhost/`（`use_https_scheme` 默认 false，本项目未开）⇒ 页面里 `location.protocol` 是 `http:`，旧写法 `location.protocol === 'splash:'` **恒不成立**，重试落到 `location.reload()`。
  - 而 `location.reload()` 只重载 `/`，**只有 `/retry` 才触发 bootstrap**（Tauri `loading.rs::handle_splash` 与 Electron `protocols.ts` 都按 pathname 判 `/retry`）⇒ 一旦停在启动页失败卡（如 DNS/TXT 解析失败、代理启动失败），点多少次「重试」都只是刷新这张启动页，**永远起不来**（Windows 同样中招）。同时 `RETRY_URL` 原本是绝对 URL `splash://localhost/retry`，协议被改写后内核不认识该 scheme，导航会直接失败。
  - **修复（`src/loading.js`，双壳单一真源）**：抽出 `isSplashDoc()`（`protocol === 'splash:'` **或** `hostname === 'splash.localhost'`，兼容未改写与已改写两种形态），`RETRY_URL` 改为**相对路径** `/retry`（按当前文档 origin 解析，两种形态都落到 `<origin>/retry`）。
  - ⚠️ 两条缺陷是**互补**的：修完缺陷 1，启动页才会（在正常偏慢时）显示「启动超时 + 重试」卡；若不修缺陷 2，那张新卡上的按钮会照样点不动。所以必须同批修。
- **测试（+2，主 crate 111 → 113）**：
  - `loading::tests::retry_uses_relative_path_and_rewritten_hostname`：钉死 `RETRY_URL === '/retry'`、不得再出现 `splash://localhost/retry`、`onRetry` 必须走 `isSplashDoc()` 与改写后的 hostname 判据。
  - `contract_tests::loading_mode_contract::main_window_registers_mode_marker_before_overlay`：跨平台静态守卫，用 `include_str!("lib.rs")` 断言主窗的**模式标记注册位置早于** `.initialization_script(loading::OVERLAY_SCRIPT)`；针取**注入语句本体**（`window.__web2appLoadingMode = (location.hostname === '` + `splash.localhost'`，两段 `concat!` 拼接）而不是裸 hostname —— 后者会命中紧邻的说明注释，守卫就咬不动了。**两条新守卫均做了反向对照**（改坏 → 期望 FAILED → 还原后 4 个源文件 sha256 与基线逐字吻合）。
- **门禁（2026-10-09 实跑）**：`cargo fmt --all -- --check` 0 diff、`cargo clippy --all-targets -- -D warnings` 0 告警、`cargo test --all` **186 通过 / 6 ignored**（resolve-core 19 + resolve-tool 22 + w2a-proxy 32 + 主 crate 113）。改动**不含** `#[cfg]` 分叉（模式标记注入与守卫都是跨平台代码），故本机覆盖完整；Android 侧仅 §「未验证」= 未在真机跑通。
- **仍未验证 / 需要真机**：这两条修的是「确定的缺陷」，**不等于**已解释使用者遇到的「打开很慢 → 空白」——那仍需 v1.61 的诊断卡真机证据（本次未改动诊断卡）。真机复现时：失败卡首行「地址」= `http://splash.localhost/` ⇒ 命中启动阶段（本次两条修复直接受益）；= 目标域名 ⇒ 是外链文档层（看 HTTP / UA / 脚本错误三行分流）。旧打包产物不含任何本次修复，**必须重新打包**。

的是**直连 URL** 配置（普通 https 地址、无代理、无域名数组）⇒ 启动期**一次网络都不做**，
`prepare_navigation` 毫秒级返回。这条信息直接推翻了「启动期卡在 DNS/代理」的假设，把矛头指回
「导航这一步静默没发生」。

- **本轮关键结论（从 wry 源码逐行得到，解释了整张卡）：Android 上壳层对主框架加载失败必然失明。**
  - `wry/src/android/mod.rs::load_url` 与 `eval` 都是「把消息投给 main pipe 后**直接 `Ok(())`**」
    ⇒ Tauri 的 `window.navigate()` / `wv.eval()` 在 Android 上**恒返回 Ok、永不报错**。于是
    `bootstrap.rs::navigate_main` 里那条 `Err(e) => show_error("无法打开页面：{e}")` 在 Android 上
    是**死代码**，永远走不到。
  - `wry/src/android/kotlin/RustWebViewClient.kt::onReceivedError` 只对 `ERROR_CONNECT` 做
    「自定义协议重定向」特例（`stopLoading` + 重发 `loadUrl`），其余一律 `super.onReceivedError(...)`，
    **不向壳层透出任何网络错误**（wry 没有暴露该回调）。
  - ⇒ 主框架加载失败时 WebView **把启动页留在屏幕上**（不提交新文档、也不画错误页），壳侧一无所知，
    最后只剩 `loading.js` 的 40s `FAIL_MS` 兜底卡 —— 与真机截图（「启动超时」+ 一句通用文案 +
    重试按钮、**无任何诊断行**）逐字吻合。
  - 这个根因在 wry 上游（需上游暴露 `onReceivedError`，或壳侧自建 JNI 回调）。**本轮修的不是它，
    而是「现场不透明」这条信息黑洞** —— 顺带发现并修掉 4 条独立缺陷。
- **修复 1（`src/loading.js`）：40s 兜底卡是唯一不带诊断的失败卡。**
  CAP 卡与 `fail()` 卡都拼 `diagText()`，唯独 `FAIL_MS`（splash 40s / overlay 30s）不拼 ⇒
  真机上拿不到任何现场。现在补上 `diagText()`，并在「地址仍是 splash」时加一句判读提示
  「仍停在启动页：目标地址的导航没有提交」——地址行是最短判据：仍是 `splash.localhost` ⇒
  导航未提交（上述 Android 失明的既定后果）；已是目标域名 ⇒ 文档层问题（HTTP 状态 / UA / 脚本错误分流）。
- **修复 2（`src/loading.js`）：挂载完成前的壳侧调用被静默吃掉。**
  加载层在 `mount()` 完成前挂的是**纯 no-op 桩**，于是「壳在挂载前推来的错误」直接消失 —— 而直连配置
  的启动只需毫秒级就完成，它的失败推送**必然**落在挂载之前（这条通路是 Tauri 侧唯一的错误出口；
  Electron 侧另有烤进 HTML 的 `__web2appPendingFail`，两条并存互不干扰）。现在桩改为**缓冲队列**
  （`pending`），`mount()` 后 `drainPending()` 回放（失败 / 慢提示 / 补充信息三类）。
- **修复 3（跨 `loading.rs` + `loading.js` + `bootstrap.rs`）：壳侧没有「阶段进度」通路。**
  - `loading.rs` 新增 `show_note()`（eval 调 `window.__web2appLoading.note(line)`，**不改变卡片状态**），
    与 `show_error` 共用 `eval_on_loading()` 统一包 try/catch；`loading.js` 新增 `note` API 与
    `notes` 容器 —— `toFail` 会把 `notes` 拼进详情，所以它们**不会被后来的兜底卡覆盖**
    （`notes` 单独存一份的原因：兜底卡 40s 才渲染，而壳侧结论常在几秒内到达）。
  - `bootstrap.rs` 在四个节点推进度：`正在解析目标地址（N 个域名）…`、`正在打开 <host>…`、
    `正在启动本地反向代理…`、**`已发起导航，等待页面响应…`**（最后一条是区分「根本没导航」与
    「导航了但没提交」的唯一线索）。全部经局部助手 `bootstrap::note()` 转主线程（`eval` 必须回主线程，
    而 `prepare_navigation` 跑在 `std::thread::spawn` 里）。
- **修复 4（`src/bootstrap.rs`）：可达性探测只报坏消息，不报好消息。**
  探测成功时原来**什么都不推** ⇒ 最需要的那条判据（「Rust 侧能连通、WebView 却没渲染」）恰好被丢掉。
  现在新增 `ProbeOutcome::Reachable { status, ms }` 与纯函数 `probe_ok_message()`，成功时也推一行
  「可达性探测：<host> 已连通（HTTP 200，812ms），但页面未渲染 —— 问题多半在本机 WebView 内核
  （版本过旧 / TLS 协商 / 渲染），不在网络」。另把失败推送改走统一的 `failCard()`：**已有卡片时把
  结论追加成一行**（而不是丢弃），避免「兜底卡先出现」这个时序差别把探测结论吃掉。
- **修复 5（`src/bootstrap.rs`）：解析阶段没有时间上界，且失败原因被吞。**
  域名数组配置下 `resolve_url_from_domains` **串行**遍历域名，每个域名 hickory 默认
  `attempts=2 × timeout=5s × 每个 nameserver` ⇒ 3 个域名最坏 30s+（可超过 40s 兜底卡），表现为
  「静默卡住」。现在加 `RESOLVE_BUDGET_SECS = 25` 总预算（`tokio::time::timeout`；为此给
  webview-app 的 tokio 补 `time` feature），并把 `.map_err(|_| "服务器连接失败…")` 改为
  `解析目标地址失败：{e}` —— 「读系统 DNS 配置失败 / 查询某域名失败 / 全部密文解不开 / 预算超时」
  都是唯一能指导下一步的信息。

## v1.64（2026-10-09）

**真机拿到新证据 → 定位到根因（不是「没提交」，而是「被覆盖」）。** 使用者传来装了新包的截图：40s
「启动超时」卡上**已经出现页面自产的诊断行**（`地址 / 状态 / HTTP / UA` 四行），但**四条阶段进度
一条都没有**。这两件事合在一起把范围收窄到了链路本身。

### 截图给出的三条事实

| 卡上所见 | 含义 |
| --- | --- |
| `地址: http://splash.localhost/`、`状态: complete，元素 3`、`HTTP: 200，资源 1，125ms` | **启动页本身完全正常加载完了**（本地协议页，125ms） |
| `UA: … Android 16 … Chrome/143.0.7499.192` | **内核很新**，排除「系统 WebView 过旧」（v1.61 的首要嫌疑） |
| **零进度行**（没有「正在打开 …」「已发起导航…」） | 壳侧推送**一条都没送到** —— 与 v1.63 的缓冲桩无关，缓冲桩压根没装上 |

### 根因（从 wry 源码逐行推出，可复现、非猜测）

`wry/src/android/main_pipe.rs` 是壳侧与 WebView 之间**唯一**的通路，两条关键消息在目标未就绪时
**静默丢弃**：

```rust
WebViewMessage::Eval(script, callback) => {
  if let Some(webview) = get_webview(activity_id) { … }   // ← 取不到就什么都不做
}
WebViewMessage::LoadUrl(url, headers) => {
  if let Some(webview) = get_webview(activity_id) { … }   // ← 同上
}
```

而那个 webview 只在 `CreateWebView`（建窗时发出）**处理完之后**才写入 `ACTIVITY_PROXY`。
更关键的是**初始 splash 导航是异步排队的**：

- `CreateWebView` 内部的初始导航走 `load_url(…, main_thread = true)` →
  Kotlin `loadUrlMainThread`（`RustWebView.kt`：`post { loadUrl(url) }`，排到**视图消息队列尾**）；
- 之后 `navigate` 走的是**同步** `loadUrl`（`main_thread = false`）。

直连配置下 `prepare_navigation` 只需毫秒级（无域名解析、无本地代理）⇒ 「导航」几乎必然**先于**那条
post 出去的 splash 加载执行，随后 **splash 加载把导航整体覆盖** ⇒ 页面永远停在启动页。这解释了
「地址仍是 splash」而不是「导航没发」。同一时刻那几条进度 `eval` 落在 splash 文档的
document-start 脚本**之前**，`window.__web2appLoading` 尚未定义 ⇒ `try{window.__web2appLoading&&…}`
静默短路 —— 这解释了「零进度行」。

⇒ **两个症状、一个机制：Android 上壳侧的一切操作都发得太早。**

### 修复（`bootstrap.rs` / `lib.rs`）

Android（非 Windows）启动期**先等首个文档加载完成**，再做解析 / 推送 / 导航：

- 新增 `BootReady`（label → 是否已完成过一次页面加载）与 `wait_first_page_ready()`（后台线程轮询，
  预算 `SPLASH_READY_BUDGET_MS = 5000`）。
- 就绪信号来自 `on_page_load`：wry Android 的 `ON_LOAD_HANDLER` 由
  `RustWebViewClient.onPageStarted / onPageFinished` 驱动，且 `tauri-runtime-wry` 里
  `with_on_page_load_handler` 是**无条件**接的 ⇒ Android 上这个信号真实可用（这是本壳在 Android 侧
  唯一可靠的「文档已就绪」判据；轮询 URL 不行——`GetUrl` 同样走 main-pipe）。
- ⚠️ `Started` 必须**清**标记：`/retry` 会重新加载启动页，沿用旧标记会变成「首启修好了、重试仍卡死」。
- ⚠️ **超时不阻断启动**：拿不到加载事件就退化成旧行为，只在卡片上留一行
  「启动页未在 5000ms 内报告加载完成（页面加载事件缺失），按原流程继续」—— 绝不把启动卡死，
  而且这一行本身就说明「页面加载事件在真机上没送达」。
- Windows 完全不加（WebView2 的注入/导航时序由 wry 自己保证，凭空等待只会推迟启动），故新增代码
  全部 `#[cfg(not(windows))]`。

**本修复自带诊断价值**：若下一版装到真机上仍然卡住，卡上必然出现进度行（说明走到哪一步）；
若连进度行都没有，那一行「页面加载事件缺失」会直接指出等待超时 —— 两种情况都比现在多一条判据。

### 修复：导航后的落点校验 + 有限重发（仅非 Windows）

`bootstrap.rs` 新增：

- **`is_splash_url(url)`** —— 判据**同时认两种形态**：`splash://`（`loading::splash_url()` 构造）

- **`ensure_navigation_committed(app, label, target)`** —— 导航后隔 `NAV_COMMIT_CHECK_MS = 500`
