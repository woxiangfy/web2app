## v1.68（2026-10-10）：电脑端悬浮窗三条「静默失败」缺陷——销毁降级为隐藏 / 开了悬浮窗退不掉程序 / 重启后悬浮窗不出现

### 起因

使用者要求：「检查下电脑端悬浮窗功能相关代码，并修复」。v1.67 交付的悬浮窗（Tauri + Electron 双壳）
在本地门禁（`cargo test` / `pnpm run unit` / 探针）里**全绿**，故本轮按「先取证、再动手」的方式逐条复核，
抓出 **3 条运行期缺陷**（全部属于「编译零警告、单测全绿、只在真机上以『点了没反应 / 退不掉 / 少了个窗口』现形」）。
三条都有**独立取证**（源码级 + 可执行脚本实测），并各自补了静态契约守卫 **+ 反向对照**。

### 缺陷 ①（Tauri）：设置里取消勾选 = 「销毁」实际只等于「隐藏」

**现象**：设置页取消勾选「启用桌面悬浮小窗」并保存后，窗口并未销毁 —— 它只是被藏起来了，
托盘菜单「悬浮窗」或设置页「立即显示悬浮窗」仍能把它唤回来，与 v1.67 写定的契约
（「设置开关取消 = 销毁」）自相矛盾。

**根因（源码级确证，两条通路不是同一条）**：`floatwin::destroy_float_window` 用的是 `WebviewWindow::close()`，
而 `close()` 在 Tauri 里**不走销毁**：
- `close()` 派发 `WindowMessage::Close`，`tauri-runtime-wry 2.11.4`（`src/lib.rs`）
  把它**直接**交给 `on_close_requested`（**与 Alt+F4 / 系统关闭同一入口**）；于是 `lib.rs` 里
  「`label == float` ⇒ `api.prevent_close()` + `hide_float_window()`」那段把它整个吞掉，
  `on_window_close` 永不执行 ⇒ **窗口永远不销毁**；
- `destroy()` 派发 `WindowMessage::Destroy`，直接 `on_window_close`、**不发任何事件**
  （tauri 文档原文：*does not emit any events and force close the window instead*）。

**修复**：`destroy_float_window` 改用 `w.destroy()`。这与本仓库既有的正确写法同款 ——
`tabs.rs::close_tab_inner` 早就用的 `destroy()`（注释里也写着「强制销毁窗口」），当时只有悬浮窗这一处走偏。

**顺带（同一函数域内的健壮性）**：`hide_float_window` 补 `moving.store(false)`
（拖动途中被隐藏 —— 悬浮条「—」/ Alt+F4 —— 时 `pointerup` 不会再来，残留的 `moving=true`
会让下一次悬停展开 / 移开缩回**永久失效**，因为事件都被「拖动中」早退挡掉）。

### 缺陷 ②（Electron）：开着悬浮窗就退不掉程序

**现象**：悬浮窗存在时，托盘菜单「退出」/ 系统退出会「关一半」—— 主窗关闭、悬浮窗只剩隐藏、
**进程仍然活着**（任务管理器里还有 electron 进程；若未启用托盘则用户完全看不到窗口）。

**根因（实测复现）**：`float-window.ts` 的 `close` 处理器默认 `e.preventDefault()` 转「隐藏」（这是对的），
但 Electron 的语义是 **`close` 被 prevent 会取消正在进行的 `app.quit()`**（`tests/float-quit-check.cjs`
双向实测：改前 `calling quit() → main close allowed → float close PREVENTED → STILL ALIVE`；
放行后 `→ float close ALLOWED → will-quit reached` 且进程正常结束）。
模块里的 `allowClose` 只覆盖「设置里关掉开关 / 主动销毁」，**管不到 app 级退出**。

**修复**：`FloatWindowDeps` 新增 `isQuitting: () => boolean`，入口 `index.ts` 接 `() => quitting`
（`quitting` 由 `before-quit` 与 `requestQuit()` 置位）；`close` 处理器改为
`if (allowClose || deps?.isQuitting()) { persistGeometry(win); return }`。
同时 `hideFloatWindow()` 补 `moving = false`（与 Tauri 侧同一条健壮性修复）。

### 缺陷 ③（Electron）：冷启动不建立进程级副作用 —— 重启后悬浮窗（与托盘图标）不再出现

**现象**：设置里勾选「启用桌面悬浮小窗」保存后悬浮窗出现；**重启应用后悬浮窗不再出现**（Tauri 壳会）。

**根因（脚本实测）**：入口的冷启动调用是 `settingsCtl.applySettings(loadedSettings.settings, { persist: false })`，
而控制器里托盘 / 悬浮窗都是「**变化才动**」的 diff（`next.x !== deps.getSettings().x`），
`runtimeSettings` 又已经在模块初始化时就等于**同一份** `loadedSettings.settings` ⇒ diff **恒为 false**，
两个副作用一个都不会建立。实测 `electron tests/float-startup-check.cjs`：
`before(applySettings): calls=[]`（**副作用调用数 0**）→ `after(applyInitialSettings): calls=["showFloat"]`
→ `after(all-off): calls=[]`。
（同一根因对**托盘图标**同样成立：启用托盘后重启，图标也不会出现。v1.67 之前的探针只走
「设置页勾选 → 保存」这条**变化**路径，所以一直没暴露 —— 又一次「取证方法选错 ⇒ 结论错」。）

**修复**：控制器新增 `applyInitialSettings(next)`，语义 =「**从默认态切换过去**」
（`applySettings(next, { persist: false }, DEFAULT_SETTINGS)`，`applySettings` 因此多一个可选的
`prevOverride` 形参），入口冷启动改调它；两处「变化才动」的比较基准由 `deps.getSettings()`
改为函数开头的 `prev`（否则 `prevOverride` 会被绕过）。与 Tauri 侧 `lib.rs` setup 里
「按 `initial_settings` 显式建托盘 / 建悬浮窗」同语义。

## v1.69（2026-10-10）：悬浮形态纠正——「悬浮小窗」整版废弃，改为**桌面悬浮图标（悬浮球）**：单击球调出原来的主窗口

### 起因（使用者原话）

> 「完全做错了！！悬浮窗是悬浮的图标，点击可以显示窗体（原来的窗体），不是所谓的悬浮窗体（没有任何意义的功能）。」

使用者明确否定：桌面上悬浮的应是一个**图标（球）**，它唯一的点击语义是**把原来的主窗口调出来**，
而不是再开一个加载网页的窗。v1.68 修的三条静默失败（销毁 / 退出 / 冷启动副作用）作为机制保留，

## v1.70（2026-10-10）：悬浮球「几乎不可用」综合修复——按下点锚点拖动协议 + 悬停防抖 + 边界钳制 + 隐形边框 + 显现时序

### 起因

使用者反馈 v1.69 悬浮球「很多问题，几乎不可用」。本轮先做静态根因分析，再用**合成指针真机 harness**
（`tests/float-v170-harness/`，驱动真实 Electron 球窗 + 真实 floaticon.html，不入库）逐条取证：
首轮 14 项检查 9 项红，按反馈修到 **15/15 全绿**；期间 harness 抓出两个纯静态分析没料到的真缺陷
（按下点锚点记在第一帧 move、已展开态再 enter 不取消排队缩回）。

### 缺陷与修复（双壳同改，页面为双壳单一真源）

1. **P0 拖动协议错误：增量被窗口自身位移抵消 → 半速跟手 / 抖动 / 首帧纹丝不动**。
   v1.69 页面上报相对球窗视口的 `clientX/clientY` **增量**，而主进程每帧都在 `set_position/setBounds`
   移动窗口，下一帧增量被窗口自身位移吃掉。v1.70 改为**屏幕绝对坐标**协议：
   - 新增 **`down`** 事件：`pointerdown` 立即把 `screenX/screenY` 报给主进程，只暂存「按下点」
     （`FloatState.press` / 模块态 `press`），**不展开吸附态、不置 moving**；
   - 第一帧 `move` 取走按下点：半隐藏态**先展开、后取偏移**（展开的 28px 平移不变成球离手跳动），
     之后每帧 `窗口位置 = 光标 − (按下点 − 展开后原点)`，IPC 丢帧 / 晚到都能自愈；
   - harness 首轮实锤：锚点若在首帧 move 才用**当前光标**记录，第一帧目标坐标 == 当前原点，
     球在第一次拖动时纹丝不动（这是比「半速」更严重的形态，纯代码评审没覆盖到）。

### 起因

v1.70 交付后进入真机目视，使用者两诉求：① **单击球要能隐藏主窗**（v1.69/v1.70 单击只「显示」，
主窗可见时点球没有反应）；② 球内要显示**软件自己的图标**。真机取证第一天球窗甚至**完全不出现**，
且没有任何 panic / stderr / 日志——本轮先修「球建不出」，再逐条闭环两诉求，过程中还抓出
**取证脚本自身的一个假 FAIL**（它一度把调查引向「点击事件到不了 Rust」的错误方向）。

### ① Tauri 真机：球窗静默建不出——默认 WebView2 用户数据目录（UDF）不可写

**现象**：debug 包冷启动后主窗正常，悬浮球窗 HWND 不存在；`on_page_load` 不触发、
v1.70 的 1s 兜底 `show()` 打在空壳上，stderr / panic / dlog **全部空白**。

**判别实验**：启动前设 `WEBVIEW2_USER_DATA_FOLDER` 指向工作区内可写目录，球窗**立刻出现**
（125% DPI 下宿主 170×70 物理、活柱椭圆 `0,0-69,69`）；实证 wry 回落的默认 UDF
`%LOCALAPPDATA%\com.example.web2app\EBWebView` 在当前受控终端写探针文件被 `Access denied`。

**机理（源码级）**：球窗 builder 省略数据目录时，wry 给第二个 WebView2 环境另起默认 UDF；
目录不可写 ⇒ 环境创建失败，`tauri-runtime-wry 2.11.4` 仅以 `log::error!` 记录
（**本仓未接任何 log 后端，错误无处可去**），而 `WebviewWindowBuilder::build()` 仍乐观返回
`Ok`：调用方拿到一个 HWND 永远不会出现的「窗口」。主窗 / tab 窗从不踩坑，是因为它们在
`lib.rs` / `tabs.rs` 里显式调了 `.data_directory(config::data_dir(app))`——唯独 v1.69 新建的
球窗漏了（v1.69 契约还把 `data_directory` 列为**禁用词**，当时的理由是「球不碰会话数据」，
属于把「不读不写网页会话」与「不需要可写的 WebView2 环境」混为一谈）。

**修复（`src/floatwin.rs` 建窗处，`builder.build()` 之前）**：

```rust
let builder = match crate::config::data_dir(app) {
    Some(dir) => builder.data_directory(dir),
    None => builder,
};
```

与主窗 / tab 窗完全同构（`config::data_dir` 进程内解析一次并缓存，必然同源；`None` = 判定
不可写、沿用框架默认的回退分支）。修复后不带任何环境变量连续冷启动，球窗稳定出现。
球页只有内置 HTML 与图标 PNG，共用主窗 UDF 不引入隐私面（多个 tab 窗共用同一 UDF
早已真机验证）。模块头文档同步补写整条静默失败链。

**契约**：`contract_tests.rs::float_window_contract` 里 v1.69 的 `data_directory` 禁令**反转**
为两条 `has_code_line` 正向守卫（钉 `let builder = match crate::config::data_dir(app) {` 与
`Some(dir) => builder.data_directory(dir),`，附根因注释）。**反向对照**：把该行改坏成
`Some(_dir) => builder`，`float_loads_builtin_local_page_and_never_navigates` 如期在
1228 行 FAILED（消息「必须与主窗 / tab 窗同构显式设置 WebView2 数据目录」），还原后 25/25 复绿。

### ③ WebView2 最小内容宽度与「活柱」（Tauri，真机取证）

WebView2 运行时把控制器宿主 HWND 宽度强制撑到约 **131 逻辑像素**（200% DPI 实测 262 物理、
125% 实测 170 物理），任何 `set_size` 都被立刻弹回；高度不设限。56 逻辑的球窗因此顶着一个
131+ 逻辑宽的透明宿主，矩形命中区挡桌面、外观也错位。应对（`src/floatwin.rs`）：

- **接受宿主实际宽度**，用 Win32 `SetWindowRgn` + `CreateEllipticRgn` 把窗口的**可视 + 命中**
  区域裁成一个落在 56 逻辑「活柱」内的**圆形**（物理像素，随 DPI 缩放、下限 32）：
  右吸附活柱贴宿主右边（保证半球露在右缘），左吸附 / 自由态贴左边；区域外——被撑宽的宿主
  部分与球的四角——**系统级不绘制也不接收鼠标**（含 WebView2 子窗），圆形内、球本体外的
  环带由 `.transparent(true)` 透出桌面（Tauri 2 在 Windows **无需额外 cargo feature**：
  tao 走 DWM blur-behind、wry 把 WebView2 背景置为全透明）。
- `Resized` / `ScaleFactorChanged` **幂等重裁**（宿主宽度迟到——初始化后才被撑到最小宽；
  跨 DPI 显示器拖动），只裁区域 / 重定位，不反馈触发 Resized。
- 全部几何（拖动 / 吸附 / 钳制 / 落盘 / 恢复）一律以**活柱矩形**为准，宿主实际宽度只用于
  算活柱偏移（`live_px` / `live_offset`，均有单测）；页面侧由 `push_state` 下发
  `anchor: 'l'|'r'`，`floaticon.html` 把球摆进对应活柱。
- **Electron 同类问题的另一种形态**：frameless + transparent 窗在出屏 / 负坐标移动后，
  `getBounds()` 报的宽逐次漂移（合成指针 harness 实测 **56→58→60**，半球落点被带到
  −30/−32）。`placeFloat` 收归为**唯一**定位入口、始终携带完整固定 56×56 `setBounds`
  （当场纠正漂移）；拖动 / 落盘 / 悬停几何一律不读 `b.width`，与 Rust 固定常量语义一致。

### ⑤ 调查插曲：「点击事件到不了 Rust」是取证脚本的假 FAIL

球窗能出现后，硬件合成点击（`SetCursorPos`+`mouse_event`）连续多轮报 toggle FAIL、
Rust 日志无任何事件，调查一度沿「IPC/ACL/token」方向深入（读完 tauri 2.11.5 的
`is_local_url` / `on_message` ACL 判定与 `__TAURI_INTERNALS__` 注入链）。**最终证伪**：

1. **Rust 侧主动 eval 探针**（on_page_load 后 6s 绕过 pointer 直接 `invoke('plugin:event|emit',
   'web2app:float-click')`）：主窗如期隐藏 ⇒ IPC / ACL（`float-icon.json` 的
   `core:event:allow-emit` + Local origin）/ token / `toggle_window` 全链路正常；
2. 加事件入口文件日志 + 页面加载即发一次事件的探针后冷启动：日志清晰出现
   `cancel`（页面脚本自证执行）、硬件点击的 `down`→`click`、token_len=32、零拒绝；
3. **真因在脚本**：debug 构建是控制台子系统，同进程有个可见的 `ConsoleWindowClass`
   控制台窗（1239×647）；脚本按「可见且宽 > 500」找主窗，**主窗被点击真隐藏后匹配落到
   控制台**，误报「主窗仍在」。加 `Class -eq 'Tauri Window'` 过滤、并把点击点从宿主中心
   改到**椭圆活柱中心**（宿主中心在被撑宽部分、SetWindowRgn 外，本就点击穿透）后，
   两次独立冷启动各 hide→show 共 **4/4 PASS**。

教训（与 v1.68「取证方法选错 ⇒ 结论错」同源）：**取证脚本自身的窗口匹配条件必须排除
同进程干扰窗（控制台 / 隐藏热键窗）；对区域裁剪窗，合成点击必须打活柱几何中心**。
全部临时探针（`PROBE-TEMP` / Rust eval / 页面加载 emit）取证后逐字节删净，grep 零残留。
