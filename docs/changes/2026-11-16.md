# 2026-11-16 变更记录

## 修「一次下载、两个『另存为』」的真正根因：`item.pause()` 挡不住 Electron 自带的保存框

延续 `2026-11-15.md` 的「下载页签自动关闭」与「隐藏弹窗」排查。用户真机（NSIS 安装版）反馈
点一次下载出现两个「另存为」：第一个标题栏是 `另存为`，第二个标题栏是**下载地址本身**，
两个框的文件名、目录、类型都相同。

**定位方式（本机可复现）**：给探针临时去掉 `pickSavePath` 桩，让真实对话框弹出，再用
Win32 `EnumWindows` 列出所有 `#32770`：

```
# 修复前（两处 savePath 都没设）
pid=10232 class=#32770 visible=True title=另存为
pid=10232 class=#32770 visible=True title=http://127.0.0.1:54517/dl.txt   ← Electron 自带
# 修复后（同步先设占位 savePath）
pid=8908  class=#32770 visible=True title=另存为
```

**根因**：`will-download` 处理器是异步的（要等用户选文件名）。`item.pause()` **不能**阻止
Electron 在事件返回后自己弹保存框 —— 它只看「这个 item 有没有 `savePath`」。没有 → 弹它自己的
（标题 = 下载 URL、按住下载的窗口、类型随扩展名）。于是同一次下载出现两个框；点掉第一个后
第二个才露出来，看起来就像「要点两次保存」。

**修法**（`src/main/page-behavior.ts::attachDownload`）：在 `will-download` 里**同步**先
`item.setSavePath(join(app.getPath('temp'), name))` 占位，再 `item.pause()` + 弹我们自己的
`saveDialogOptions`（标题固定 `另存为`）；用户选完后 `setSavePath(用户路径)` + `resume()`，
取消则 `item.cancel()`（半成品落在临时目录，随取消丢弃）。

**验证**：`--tabs` 探针 **60/60**（含 P15 隐藏弹窗「不导航 / 不显示」直接判据）、`unit` **188/188**、
`typecheck` / `build` ✅；真实对话框 A/B 如上（修复前 2 个 `#32770`，修复后 1 个）。

**同批收敛的另外两处**（详见 `2026-11-15.md` 追加段）：

- 隐藏弹窗只当「`window.open()` 返回非 null 的句柄」：`stop()` + `about:blank` + `will-navigate`
  全拦 + `hide()`，不再自己下载、不再冒头；
- 诊断开关 `--debug` → `--w2a-debug`（Electron 45 会把 `--debug` 转给 Node 22，`DEP0062` 后秒退、
  日志一行不写）。

**排障用的常驻日志（DEBUG 时开）**：`新建窗口 wc=… show=… title=…`、`弹出另存为 #N：…`、
`下载请求：… wc=… url=…`。判断「两个框」时看 `#N` 编号与 `#32770` 标题即可一次定性。

## 追加：占位 `savePath` 落在临时目录会让下载「看起来没保存成功」

上一条修好后真机反馈「只有一个弹窗了，但没保存成功」。取证：文件确实下完了，但落在

```
%TEMP%\BdPhSVEArwnr6wzjNU0E7KqDbPOgocY5JaM-i0xmU105y4lKE57sIz5GSpKfeQYH   108 字节
```

—— 也就是占位点。原因是 `item.setSavePath()` 文档上只保证在 `will-download` **内**生效，用户选完
之后那次调用被忽略，文件就留在占位点，所选路径为空。三条修正（`page-behavior.ts::attachDownload`）：

1. **占位点落在系统下载目录**（`downloads/<name>`），不再是临时目录 —— 选默认位置的人结果天然正确；
2. **顺序改为先 `setSavePath` 再 `pause()`**（反过来会让 Electron 的框照弹，且 item 被「设 savePath」
   顺手唤醒，小文件在用户选完前就写完）；
3. `done` 时若 `item.getSavePath() !== 用户所选`，**自己搬**（`rename`，跨盘退化 `copyFile` + `unlink`），
   并在日志里留 `已按所选路径落盘` / `已复制到所选路径` / `落到所选路径失败`。

验证：`unit` **188/188**、`--tabs` 探针 **60/60**、typecheck / build ✅。

## 再追加：占位点不能落在下载目录（否则「点了取消，文件却也下好了」）

占位点改成下载目录后真机又出现：保存时提示「已存在，要替换吗」，点取消文件却也已经下好。原因
是占位写入与用户的选择是**两件独立的事** —— 占位点与目标同名时，占位那次写入本身就是「文件已存在」
的来源，用户取消只取消了「替换」这个动作。

最终形态：占位点放私有临时子目录 `%TEMP%\w2a-pending\<时间戳>-<文件名>`（用户看不见、也不会撞名），
用户选完 → `setSavePath(所选)` + `resume()`；下载结束时若实际落点与所选不一致则**搬过去**；取消/中断
则删除占位残骸。这样三种结局都干净：落对位置 / 用户取消不留文件 / 临时目录不留垃圾。

## 再追加：`pause` 与 `setSavePath` 的顺序不能反（否则「保存后文件没有下载」）

把顺序改成「先 `setSavePath` 再 `pause`」后真机变成「保存了但目标位置没有文件」。原因：一旦 item 有了
落点，8KB 的文件会在用户选完之前就下完，`done` **早于**用户选择触发，那时 `chosenPath` 还是 null，
搬移分支直接跳过 ⇒ 文件留在 `%TEMP%\w2a-pending\`。

定稿：**先 `pause()` 再 `setSavePath(占位点)`**；收尾收成一次幂等的 `finalize()`，由 `done` 与
「用户选完」两端各调一次 —— 谁先到都不会漏（下载先结束 ⇒ 选完补搬；先选完 ⇒ 等 `done` 再搬）。

A/B（用 `if (name === '\u0000never')` 把晚到那次 `setSavePath` 强制变空，复刻真机「被忽略」的情形）：

```
[web2app] 已按所选路径落盘：…\Temp\w2a-pending\1794836445641-probe-dl.txt → …\Temp\w2a-probe-probe-dl.txt
[probe] ===== 60/60 通过 =====
```

两条分支都验过：晚到生效（直接落所选）与被忽略（`done` 后搬）。`unit` **188/188**、`--tabs` **60/60**。

## 复查（同日）：下载收尾的三处收口 + 一处探针假红

逐行过了一遍 `attachDownload`，修掉三处会「偶发 / 静默」的问题：

1. **搬两次**：`finalize()` 由 `done` 与「用户选完」两端各调一次，而搬完之后 `item.getSavePath()`
   仍指向占位点 ⇒ 第二次必然 `rename`/`copy` 失败并打红日志。加 `moved` 幂等标志（失败时回滚标志）。
2. **取消留残骸**：极快完成的下载可能在用户点取消前就写完了占位点 ⇒ 两个取消分支都调 `cleanupPending()`。
3. **探针假红**：P15 里 `w.closed` 的样本只由 300ms 定时器写入，一旦下载结算后页签被关，回调所在的
   上下文就没了 ⇒ 标志永远停在 `pending`，断言偶发 FAIL（实测出现过一次 59/60）。改为「`window.open`
   返回时立刻取一次样本 + 300ms 复采」，语义不变、不再依赖定时器存活。连跑两次 **60/60**。

复查确认无问题的点：`pause()` 在占位 `setSavePath` 之前（不会提前下完）；判重早于 `pause`/弹框；
`done` 用 `item.getSavePath()` 拿真实落点决定是否搬；取消统一 `item.cancel()`（不静默改存别处）。

已知未处理边界：同一毫秒并发下载同名文件时占位文件名可能相同（概率极低）；网络中断时若文件已
部分落到用户所选位置，可能留半截文件（Chromium 通常自清）。

## 三追加：真机「保存了但没有文件」的两个真因（有日志/文件为证）

真机日志（`%APPDATA%\lcjm\logs\startup.log`）：

```
12:30:32 弹出另存为 #1
12:30:50 下载结束（completed）：… wc=4     ← 用户还没点保存就完了（pause 被 setSavePath 解除）
12:31:01 下载已取消（另存为 #1）           ← 用户点取消
12:31:10 下载（另存为 #2）→ Downloads\…
12:31:29 下载结束（cancelled）：… wc=6     ← 保存后我们把承载下载的页签关了，下载一起被掐
12:31:46 下载（另存为 #3）→ Downloads\…
12:31:59 下载结束（completed）：… wc=8     ← 但 Downloads 里没有该文件
%TEMP%\w2a-pending\ 下 4 个 108 字节文件   ← 第 3 条的落点：搬移被跳过
```

1. **保存后立刻关页签 = 取消下载**：多页签模式下 `onSaveChoice` 在 `resume()` 后立即关掉下载页签，
   `webContents` 一销毁 Electron 就把下载标成 `cancelled`（与 Tauri/WebView2 `UserShutdown` 同类）。
   修法：`onSaveChoice` 移到 `done` 里 —— **下载结算后**再关页签（取消/中断也关，那个页签本就是为它开的）。
2. **搬移用 `item.getSavePath()` 作来源判断不可靠**：下载结束后它可能为空 / 仍指占位点，于是整段
   搬移被跳过，文件留在 `%TEMP%\w2a-pending\`。修法：**以文件真实存在为准**（`existsSync`），
   占位点存在就搬占位点，否则搬 `getSavePath()` 指向且存在的那个。

另注：`pause()` 会被紧随其后的 `setSavePath()` 解除（日志 12:30:50 早于用户选择），所以下载可能
先写进占位点 —— 这对用户不可见、也不浪费流量（同一份数据搬移），因此不再强依赖 pause 的时序。

验证：`unit` **188/188**、`--tabs` **60/60**、typecheck / build ✅。

## 四追加：启动清空占位目录（防残留堆积）

正常路径下占位文件都会被搬走或删除，只有**进程被强杀 / 崩溃**时才会留在 `%TEMP%\w2a-pending\`
（真机上积了 4 个）。新增 `page-behavior.ts::cleanPendingDownloads()`，在 `attachDownload` 之前
调用一次：启动阶段没有进行中的下载，清空安全。实测跑完一轮探针后该目录为 **0 个文件**。

## 修「页签模式下 `window.web2appExtra` 恒为 undefined」

**现象**（用户真机截图）：`tabs_enabled: true` 的构建产物（`lcjm`，配置里 `extra` 非空：
`{"version":"w2a-0.0.1"}`）在 DevTools 控制台敲 `window.web2appExtra` 得到 **`undefined`**；
而同一份配置在单窗口模式下探针 `PASS window.web2appExtra 已注入`。

**证据链**（三条各自独立成立）：

1. 解包 `tests/pack/electron-local-*/win-unpacked/resources/app.asar` 的 `out/config.json`：
   `"extra": { "version": "w2a-0.0.1" }` —— 配置**非空**，排除「打包时没传 extra」。
2. `src/main/tabs.ts::spawnTab` 的 `new WebContentsView({ webPreferences })` **没有 `preload` 字段**
   —— 页签内容页不跑任何 preload，`contextBridge.exposeInMainWorld('web2appExtra', …)` 无从执行。
3. 单窗口路径走的是主窗 `preload.js`（`index.ts` 的 `TABS_MODE ? shell-preload : preload`），
   所以只有单窗口模式正常 —— 与现象一一对应。

**跨壳不一致**：Tauri 的页签是 `webview-app/src/tabs/window.rs` 里
`initialization_script("window.web2appExtra = {};")`，**页签模式下有**；Electron 侧漏了。
`docs/packaging-config.md` 的「全平台、前端读 `window.web2appExtra`」在 Electron 页签模式下不成立。

**修法**（新增内容页最小 preload，不碰安全基线）：

| 文件 | 改动 |
| --- | --- |
| `src/renderer/tab-preload.ts`（新增） | 只做 `contextBridge.exposeInMainWorld('web2appExtra', …)`；空对象不暴露（与单窗口 preload 同一判据）；`window.self === window.top` 早退；**不含**任何窗口桥 |
| `src/main/tabs.ts` | `TabsOptions` 增 `tabPreload?`，`WebContentsView.webPreferences` 带上 `preload` |
| `src/main/app-ipc.ts` | 新增同步通道 `w2a:tab-extra`（`registerTabExtraIpc`）；只做顶层框架闸 |
| `src/main/index.ts` | `tabPreload: preloadPath('tab-preload.js')` |
| `test/tab-preload.test.ts`（新增） | 锁「装配」：只暴露 extra、无桥、无相对 require、tabs.ts 真传、index.ts 真装配、通道真注册 |
| `src/main/probe-tabs.ts` | 新增 P2b 两条**成对**断言（能读到 extra ‖ 内容页仍无 `window.web2app` 桥） |

**为什么不让内容页直接用 `preload.js`**：那套会往页面注入自绘标题栏与加载层，而页签模式的标题栏
属于壳页面 `shell.html` —— 挂上去就是「两条标题栏」。所以另起一个只注入数据的最小 preload，
`window.web2app` 桥在页签内容页**依旧不存在**（P2b 第二条断言把它钉住，防后来人「顺手放宽」）。

**为什么另起一条 IPC**：页签内容页的 webContents 不是主窗（`expectedSenderId` 只认主窗），
`web2app:bootstrap` 的 sender 闸不适用；而它只要 extra 一份数据，不该为此同步拉约 81KB 注入脚本。
`extra` 本身就是要注入远程页面的公开配置、不涉及任何窗口能力，故闸门只到「顶层框架」。

**验证**：`unit` **194/194**（原 188 + 新增 6）、`--tabs` 探针 **62/62**（原 60 + P2b 两条）、
单窗口探针 **157/158**（既有 `Shift+F1` 被占用项，与本次无关）、typecheck / build ✅。

**反向对照**（项目铁律，逐条做过）：把 `index.ts` 的 `tabPreload` 临时改坏 ⇒
`test/tab-preload.test.ts` 如期 `✖ index.ts：TabManager 装配了 tab-preload 路径`（fail 1 / pass 5）、
`--tabs` 探针如期 `FAIL P2b 内容页读到 window.web2appExtra ← 实际 null`（61/62，退出码 1）；
还原后三个文件 sha256 与改前**逐一相同**，再跑 unit **194/194**、`--tabs` **62/62**。

**出包核对**（asar 实读）：`electron-builder --win --dir` 出的包内
`/out/renderer/tab-preload.js` **在**、`probe*` 与 `tabs-probe-preload.js` **不在**（`prune` 生效），
条目 49。⚠️ 本机 `pnpm run pack` 有两条环境坑（与本次改动无关）：① electron 二进制下载
600s 超时 ⇒ 必须带 `ELECTRON_MIRROR` / `ELECTRON_BUILDER_BINARIES_MIRROR`，或
`--config.electronDist=node_modules/electron/dist`；② 沙箱的删除垫片挡住 electron-builder 清空
`release/win-unpacked/resources`（`[safe-delete] … trash operation`）⇒ 用
`--config.directories.output=<全新目录>` 绕开，别让它去删旧产物。

**给使用者的提醒**：本次核对用的 `electron-app/config.json` 里 `extra` 是 `{}`（空对象）——
空 extra 在 Electron 侧**故意不定义**该全局，所以「重打包后仍是 `undefined`」要**先看打包用的
JSON 里 extra 是否非空**，再怀疑代码。
