### 关键经验教训
1. **OpenSSL 3.x 的 `pkeyutl -sign` 不能直接对原始数据做 PKCS#1 v1.5 签名**：默认要求输入是 digest，会报 `invalid digest length`。`-rawin -pkeyopt digest:none` 在 3.5 也不支持（`Can't set parameter digest:none`）。正确做法是用已 deprecated 但可用的 `openssl rsautl -sign -inkey private.pem`（产出类型 1 签名块，`00 01 FF..00 M`），或 `openssl rsautl -encrypt -inkey`（类型 2 加密块）。
2. **PKCS#1 v1.5 签名（类型 1）是确定性的**：填充全 0xFF 无随机性，同一明文多次加密结果完全相同。需要随机密文必须用类型 2 加密块。`resolve.rs` 的 `strip_pkcs1_v1_5_padding` 已同时兼容类型 1/2。
3. **Windows `nslookup` 会误报 NXDOMAIN**：对 Cloudflare DNSSEC 托管域（如 mygit.top）查 TXT 时，Windows nslookup 可能误报 "Non-existent domain"，而 `dig` 和 hickory-resolver 都能正确查到（NOERROR + ANSWER）。**排查 DNS 时不要轻信 nslookup 的 NXDOMAIN 结论，要用 dig 或直接上 hickory-resolver 验证**。
4. **DNS 传播有延迟，且分层环境（Docker/代理内网 DNS 172.18.0.2）缓存更久**：记录刚设置时，系统 DNS 可能返回 "no records found"（NOERROR + 0 answers），几分钟后才同步。hickory-resolver 用 `read_system_conf` 走系统 DNS，会受这个缓存影响。验证时用 hickory-resolver 显式指定公共 DNS（8.8.8.8/223.5.5.5）可绕过内网缓存。
5. **hickory-resolver 0.26 API 备忘**（写诊断代码时踩坑）：`ResolverConfig::new()` 不存在，用 `ResolverConfig::from_parts(None, vec![], ns)`；`NameServerConfig` 字段是 `ip` + `trust_negative_responses` + `connections`（非 `socket_addr`/`protocol`），构造用 `NameServerConfig::udp_and_tcp(ip)`；`ResolverBuilder` 无 `.options()` 方法（有 `options_mut`）。

## 加密方案重构：类型 2 随机填充（每次加密不同）

用户明确需求：**每次加密结果必须不同、解密结果相同**，否则设计无意义；且密文尽可能短。

### 根因
之前用 `rsautl -sign` / `pkeyutl -sign` 产出的是 **PKCS#1 v1.5 类型 1（签名块）**，填充全 `0xFF`，是**确定性**的——同一明文加密结果固定不变。

### 新方案
改用 **PKCS#1 v1.5 类型 2（加密块，随机填充）**，方向仍是"私钥加密 → 公钥解密"（`c = m^d mod n`）：
- 明文块 = `0x00 || 0x02 || 随机非零PS || 0x00 || URL`
- PS 每次 `os.urandom` 生成 → **密文每次不同**
- 客户端 `m = c^e mod n` 剥类型 2 填充 → 解密结果相同

### 关键结论
- **客户端 `resolve.rs` 无需改逻辑**：`strip_pkcs1_v1_5_padding` 早已同时兼容类型 1/2。只更新了注释 + 加了一个测试 `e2e_type2_random_padding`（验证三组密文互不相同但解密一致）。
- **新增服务端加密脚本 `tools/encrypt_url.py`**：用 `cryptography` 库 `pow(m, d, n)` 做私钥模幂 + 类型 2 随机填充。**不要用 openssl 的 sign 命令**（那是类型 1 确定性）。
- **密文"尽可能短"的物理边界**：RSA 密文固定 = 模数长度。RSA-2048 = 256 字节 = 344 base64 字符，短 URL 无法再压（这是 RSA 固有下限）。DNS TXT 单条上限 255 字节，344 字符需拆两条 TXT。若要单条放下（≤255 字符）只能降级 RSA-1024（密文 172 字符），但安全性下降——这是可选的权衡，尚未实现。

## 安全模型梳理 + 填充严格校验补强

用户澄清安全目标：**公钥即使泄露、DNS 权限即使被攻破，攻击者也无法伪造 TXT 密文把客户端劫持到恶意网址**；最坏情况只能是破坏 TXT 导致"无法访问"（DoS），影响比劫持小。

### 安全结论（方案合理）
- 方向是"私钥加密 c=m^d、公钥解密 m=c^e"，安全性等价于 RSA 签名不可伪造性。
- 攻击者想构造 `c` 使 `c^e ≡ m_evil (mod n)` = 求 e 次方根 = 需要私钥 d，做不到。
- 公钥 `(e=65537, n=2048)` 泄露无害；e 是标准值 65537（非低指数 3），堵死立方根攻击。
- 唯一能做的防御补强：**严格校验 PKCS#1 v1.5 填充**（之前只找分隔符 0x00，没校验 PS）。

### 补强内容（`strip_pkcs1_v1_5_padding`）
- PS 长度必须 ≥ 8 字节；
- 类型 2 的 PS 每字节必须非零；类型 1 的 PS 每字节必须为 0xFF。
- 新增 3 个负面测试：短填充拒绝、类型2含零字节拒绝、类型1非0xFF拒绝。
- 测试总数 16 → 19。

## 方案替换：RSA → Ed25519 签名 + AES-256-GCM（最终定稿）

用户否定了"非标准用法"（RSA 私钥加密/公钥解密），要求用标准方案。经过几轮讨论+实测，最终**整体替换**为：

**Ed25519 签名（防篡改，硬保证）+ AES-256-GCM 对称加密（隐藏网址，软保证）**。

### 为什么这个方案更优
1. **密文短**：约 130~150 字节 → base64 约 180~200 字符，**单条 DNS TXT 可放下**（vs RSA-2048 的 344 字符需拆两条）。
2. **全标准库 API**：ed25519-dalek 验签 + aes-gcm + hkdf + sha2，无手动模幂/填充。
3. **每次加密不同**：Nonce(12B) + 随机盐(8B) 每次随机。
4. **防重放**：Payload 内嵌 Unix 时间戳，客户端校验 ±48h 窗口。

### 核心洞察（这是几轮争论的关键结论）
- "隐藏明文 + 客户端仅持公钥可解密"在**标准加密语义下是数学矛盾**：ECC 加解密不对称（解密必须私钥），标准签名不隐藏明文。之前 RSA 能"私钥加密/公钥解密"是因为 RSA 的 e/d 模幂对称（唯一有此性质的算法）。
- 突破点：把"加密"和"签名"**拆成两个正交操作**——隐藏用**对称加密**（密钥由客户端内置 Secret + Nonce 经 HKDF 派生，双方共享），防篡改用 **Ed25519 签名**（私钥签名、公钥验签，标准方向）。这样绕开了"公钥解密"的死结。
- **Secret 的安全定位必须诚实**：Secret 内置客户端、可被反编译还原，故"隐藏网址"这一层**只防公网批量爬取，不防反编译客户端**。真正的安全边界是 Ed25519 验签（防篡改）。

### 数据格式（服务端 tools/encrypt_url.py 与客户端 src/resolve.rs 必须一致）
```
Payload   = URL || 0x00 || ts(8B大端) || 0x00 || salt(8B)
Signature = Ed25519.sign(Payload)                       # 64B
Key       = HKDF-SHA256(ikm=Secret, salt=Nonce, info="web2app-resolve")  # 32B
Cipher    = AES-256-GCM.encrypt(Key, Nonce, Payload || Signature)  # +16B tag
TXT       = base64( Nonce(12B) || Cipher )
```
常量：SECRET=`web2app-fixed-secret-2026`、HKDF_INFO=`web2app-resolve`（两端硬编码一致）。

## ttl 有效期字段 + resolve-tool 工具 + resolve-keys.yml workflow（commit 255e9c9）

用户三个新需求：① workflow 加手动生成密钥对功能；② Rust 加独立工具用私钥生成 TXT 密文并接入 workflow 手动生成；③ 有效期问题澄清。用户决策：**有效期时长由服务端生成时指定（ttl 字段随密文下发），非客户端硬编码**；工具形态选 **Cargo bin**；密钥输出选**上传 artifact**。

### 数据格式扩展（ttl）
Payload 从 `URL||0x00||ts(8B)||0x00||salt(8B)` 扩展为 `URL||0x00||ts(8B)||ttl(8B)||0x00||salt(8B)`（尾部从 17 字节→25 字节）。语义：`ttl>0` 客户端校验 `now-ts<=ttl`；`ttl=0` 永不失效。`parse_payload` 校验逻辑相应从固定 ±48h 改为按 ttl 判断。

### 新增 resolve-tool（src/bin/resolve-tool.rs，Cargo bin）
- `genkey [--out DIR]`：生成 Ed25519 密钥对，**手动构造 48 字节纯私钥 PKCS#8 DER**（`302e020100300506032b657004220420<32B seed>`），与 Python `cryptography` 完全互通。
- `encrypt <key.pem> <url> [--ttl 秒]` / `encrypt --batch <key.pem>`：签名+加密生成 TXT 密文。
- `load_signing_key` 手动解析 PEM body 的 DER 定位 `04 20` 取 32B seed（兼容纯私钥 + RFC 8410 两种格式）。
- resolve.rs 新增服务端函数：`build_payload`/`sign_and_encrypt`/`generate_keypair`/`pem_encode`；`lib.rs` 的 `mod resolve` 改 `pub mod resolve` 供 bin 访问。

### 关键踩坑（本轮新踩）
1. **ed25519-dalek 2.2 默认不启用 `rand_core`/`pkcs8` feature**：`SigningKey::generate`、`Signature::as_bytes()`（应为 `to_bytes()`）都会因缺 feature 报错。最终只用 `rand_core`；`rand = "0.8"` 也需显式加依赖。
2. **dalek 的 `to_pkcs8_pem` 输出 83 字节 RFC 8410 格式（私钥+内嵌公钥），Python 读报 "extra data"**。改手动构造 48 字节纯私钥 DER 解决，实现 Rust↔Python 双向互通。
3. **workflow 里 `run: |` heredoc 内容不能顶格**，否则破坏 YAML 块标量缩进（报 "could not find expected ':'"），内容统一加 10 空格缩进。
4. **cargo clippy 偶发 ICE（exit 101，`encode_metadata` panic）是增量缓存损坏**，非代码问题；清 `target/debug/incremental` 即恢复。但 `cargo clean` 在 Windows 上删 5.9G target 会卡死（14 分钟+），**只删 incremental 子目录即可**（用 PowerShell `Remove-Item -Recurse -Force`，比 bash `rm -rf` 快且不触发安全删除确认）。
