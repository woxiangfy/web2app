## 滚动条穿过标题栏（使用者截图反馈）· 修复

截图现象：纵向滚动条从窗口最顶端开始画，露出在标题栏右侧那条 15px 缝里。

根因：标题栏是 `fixed;top:0;left:0;right:0` —— **fixed 的 left/right:0 只到 clientWidth（不含滚动条）**，
而滚动条属于视口、从 y=0 画。实测 400×340 窗口：`innerWidth=399 / clientWidth=384 / scrollbarW=15`，
`left+right:0` 与 `width:100%` 都只有 384，只有 **`width:100vw` = 399** 能盖住。

修：`titlebar.js` 标题栏改 `width:100vw`；`loading.js` 遮罩同步改 `100vw/100vh`（原 right/bottom:0 右侧底部各漏 15px）。
两壳共用一份脚本，WebView2 的 overlay 滚动条不占布局 ⇒ 对 Tauri 版无副作用。

**更值得记的一点**：探针原断言 `标题栏宽 == clientWidth` 且注释写「差一个滚动条宽是正常行为」——
**把缺陷固化成了期望值**。已改成 `== innerWidth`，并加前置断言「该页确有纵向滚动条」防恒真。

新增 `npm run shot`（`scripts/layout-shot.cjs`）：注入 titlebar.js → 打印宽度对照 → `capturePage()` 出 PNG
到 `%TEMP%\w2a-layout-shot.png`，退出码即判定。改布局后 5 秒看结果，不必打包双击。

验证：`npm run probe` **99/99**（新增 1 条）；`npm run shot` → `titlebarW=519 == innerWidth=519`，PNG 人眼确认滚动条已从 38px 才开始。
文档：`electron-app/README.md` 新增「自绘标题栏与页面滚动条」一节；`PLAN.md` §8.9。
记忆：`MEMORY.md` 整体瘦身 17698→8043 字符（Tauri/Electron 细节分别指向 topics/ 两份详版）。

## 第二轮：那条缝的**真**根因（上一轮的结论是错的）

使用者反馈「你给的截图很明显还是没有解决」+ 提示「是不是框架层面问题」—— 是对的。

### 我上一轮错在哪

```
右边缘 (x=1655, y=0..100) 恒为 rgb(252,252,252)
```

### 真根因（框架层，不是 CSS 问题）
**Chromium 把视口滚动条绘制在所有 DOM 内容之上** —— 标题栏 `z-index` 拉到 2147483647 也压不住。
所以「标题栏盖住滚动条」在「注入 DOM」架构下**物理上做不到**：
布局宽度确实到 828，但那 15px 在**绘制**阶段被滚动条覆盖。

决定性证据（`scripts/titlebar-diag.cjs`）：
```
probe.fixed100vw = 828   ← 100vw 就是 innerWidth，宽度单位没问题
elementAt[812] = BUTTON.w2t-btn
elementAt[813..827] = null   ← 那 15px 里任何 DOM 元素都命中不到
HTML: w=813, overflow=auto
```

### 解法（`scripts/scrollbar-lab.cjs` 四模式对照实测）
| 配置 | clientWidth | 命中区止于 |
|---|---|---|
| 默认（经典滚动条） | 813 | 812 ✗ |
| `--enable-features=OverlayScrollbar` | 813 | 812 ✗ **该开关在 Electron 44 已失效** |
| `--enable-features=FluentOverlayScrollbar` | 813 | 812 ✗ 同上 |
| **`html{scrollbar-width:none}`** | **828** | **827 ✓** |

改动：`webview-app/src/titlebar.js`（两壳共用真源）加两条 CSS ——
`html{scrollbar-width:none!important}` + `html::-webkit-scrollbar{width:0!important}`。
代价：页面不再显示滚动条，但 `canScroll` 仍为 true（滚轮/键盘/触摸板照常）。
若将来必须保留可见滚动条，唯一出路是**换架构**（Electron: `BaseWindow`+两个 `WebContentsView`；
Tauri 2: 同窗口多 webview），让滚动条天然被裁在页面 view 内。

## 第四轮：从「藏掉滚动条」改成「换滚动根」（使用者一句话点醒）

使用者原话：「被你气笑了，现在滚动条没了。滚动条不应该强制隐藏，只是不要超过菜单栏而已」。
—— 上一轮 `scrollbar-width:none` 把缺陷消灭了，但**把使用者的功能也一起消灭了**。
「看不见问题」≠「满足需求」，这是本项目第三次栽在同一个思维定式上（C.8/C.9）。

### 重新定性
需求不是「滚动条别盖住标题栏」，而是**「滚动条要看得见，且不能进标题栏那 38px」**。
Chromium 的视口滚动条几何固定 = 视口右边 × **整个视口高度**，且绘制在所有 DOM 之上 ⇒
「让滚动条变短」在 CSS 里无解。**唯一出路是换滚动根**：让 `body` 当滚动容器，
它的滚动条天然只在 body 盒内绘制 ⇒ 物理上不可能越过 38px。

### 七模式对照（`scripts/scrollbar-lab.cjs` v2 实测）
| 配置 | 结果 |
|---|---|
| 原生 | 穿过标题栏 ✗ |
| `--enable-features=OverlayScrollbar` | Electron 44 已失效 ✗ |
| `--enable-features=FluentOverlayScrollbar` | 同上 ✗ |
| `::-webkit-scrollbar{border-top:38px}` | border 不参与滚动条部件布局 ✗ |
| track `border-top:38px` | 同上 ✗ |
| `scrollbar-width:none` | 隐藏 —— **使用者拒绝** ✗ |
| **`html{overflow:hidden}` + `body{margin-top:38px;height:calc(100vh-38px);overflow-y:auto}`** | **✓** |

**未查到底（不当结论）**：挂住的根因。原推测「缓存目录按下载地址哈希、镜像失效后去敲 github」，
但 github / npmmirror / registry.npmmirror 几种地址形态的 sha256 都**对不上**
`%LOCALAPPDATA%\electron\Cache\d69c2445…` ⇒ 推测不成立，搁置。

**顺带发现（与 pnpm 无关，也该修）**：`package.json` 里脚本互相调用写的是 `npm run sidecar && npm run build`
（`probe`/`pack`/`dist`）。**主命令换成 pnpm 后内层 `npm` 会走 PATH 落到 WSL 桩上直接失败** ⇒ 应统一改 `pnpm run`。

**结论**：结构上可行，需改 4 处 —— ① 新增 `pnpm-workspace.yaml` 的 `allowBuilds: electron: true`；
② 镜像从 `.npmrc` 挪成真环境变量（`ELECTRON_MIRROR`/`ELECTRON_BUILDER_BINARIES_MIRROR`）；
③ 内层 `npm run` → `pnpm run`；④ `package-lock.json` 让位（两个 lockfile 并存会让 electron-builder 落到 env 回退判断）。
**反方理由（很实在）**：本项目 **0 个生产依赖**（全在 devDependencies），pnpm 唯一实打实好处只是省磁盘
（electron 158MB 二进制硬链接共享）；收益 < 上面这些新风险。

**残留物**：`%TEMP%\pnpm-mirror-probe` / `pnpm-buildscript-probe` / `pnpm-electron-probe`，及数个挂住的 node 进程。

### ⚠️ 修订（同日，联网核查后）：结论从「不建议」改为「**可以换**」

用户要求「网上搜索下可不可以」。检索后确认：**我上面的第 6 条不是 pnpm 的固有缺陷，而是「没设镜像环境变量」这个经典失败模式**
（社区记录得非常清楚），我把它当成了"装不上"。

- **根因被检索证实**：不设 `ELECTRON_MIRROR` 时 install.js 去连 GitHub Releases，
  国内网络下"中途夭折/挂死" —— 与我观测到的"手动跑 install.js 挂住不返回"完全吻合。
  标准解法：`$env:ELECTRON_MIRROR="https://npmmirror.com/mirrors/electron/"` + `node node_modules/electron/install.js`。
  （矢量多篇中文来源均写"**必须用环境变量**、不能靠 .npmrc" ⇒ 与我的第 3 条实测互相印证。）
- **配置键确实是 `allowBuilds`**：pnpm 10 用 `onlyBuiltDependencies`（列表），**pnpm 11+ 改成 `allowBuilds`（映射）**，
  官方设置页称旧设置已被取代 ⇒ 与我的第 5 条实测一致。
- **"Already up to date 不补" 也是已知行为**：即使配好 `onlyBuiltDependencies`/`allowBuilds`，
  **也只有全量删除 `node_modules` 后重装才会触发**。社区为此专门写兜底脚本（如 `postinstall-electron.cjs`：
  检测 `dist/electron.exe` 不存在就重跑 install.js）。
- **electron-builder + pnpm 官方支持，但历史上有坑**：pnpm 10.29.3 曾因 `pnpm ls --json` 把重复节点标 `deduped`
  截断输出，导致 collector 漏依赖（issue #10601），**electron-builder 26.8.2 修复**；本项目 **26.15.3 已含修复**。
  更老的版本需要 `shamefully-hoist=true` / `node-linker=hoisted` 才能打对包（旧 README #6389）。
  ⚠️ 但**本项目 `files` 只含 `out/**` + `package.json`、且 0 生产依赖** ⇒ 这条风险在我们这里几乎不存在。
- 一篇中文实践直接给"方案 1：Electron 项目就用 npm（推荐）" —— 与本项目「收益只有省磁盘」的判断不冲突，
  但**不能再说"不行"**。

⇒ **最终结论：可以换**，按上面 4 处改 + 设 `ELECTRON_MIRROR` 环境变量即可；npm 仍是更省事的选择。

### 实测踩到的坑（按发生顺序，都已在 README 固化）

1. **registry 被限速**：直连 `registry.npmjs.org` 只有 ~5 KiB/s，tarball 大面积 timeout，
   `pnpm install` 爬了 6 分钟没完。加 `registry=https://registry.npmmirror.com/` 后 33 秒装完 271 个包。
   ⇒ registry 是 pnpm **自己**读的配置（不是脚本透传），所以 `.npmrc` 这行对 pnpm 有效 —— 与 electron 镜像那条正好相反。
2. ⚠️⚠️ **默认 isolated 布局装不起来**：`Failed to create symlink at …/.pnpm/node_modules/<pkg> … os error 2`，
   两次分别停在 `color-name` / `source-map`（**包名会变** ⇒ 像竞态），但目标目录确实存在（事后检查成立）。
   ⇒ 改 `nodeLinker: hoisted`（electron-builder 官方 README 对 pnpm 的既有指引）绕开这步，一次通过。
3. ⚠️ **pnpm 12 会把"未决定"的构建脚本当错误**：`electron`（需要）之外，连
   `electron-winstaller`（electron-builder 的传递依赖，只服务 Squirrel 目标）也会让安装中断。
   ⇒ 必须显式 `false` 拒绝，**不能不写**。
4. ⚠️ **pnpm 会往 `pnpm-workspace.yaml` 里自动追加 `allowBuilds` 占位行**
   （`electron-winstaller: set this to true or false`），与手写的键**撞成 duplicate mapping key** ⇒
   它会自己制造 YAML 解析失败，需要手工删掉那行。
5. ⚠️⚠️ **`pnpm run <script> -- <args>` 会把字面量 `--` 一起传给脚本**（npm 不会）。
   实证：`pnpm run build -- --version` 打印 `$ tsc "--" "--version"`，tsc 因为收到多余的 `--` 而不打版本号。
   后果：`pnpm run probe -- --no-sandbox --in-process-gpu` 里参数落到 Electron 的 `--` 之后 ⇒ **等于没加**，
   表现为"探针稳定崩在 `FATAL: GPU process isn't usable`"，白排查两轮。
   **正确写法不带 `--`**：`pnpm run probe --no-sandbox --in-process-gpu`。
   自检透传用 `pnpm run build --version`（应打印 `Version 7.0.2`）。

### 调研结论（网上）
1. Electron 侧视图 API 已换代：`BrowserView` 自 Electron 30 废弃 → `WebContentsView`；多视图窗口用 `BaseWindow`。
   官方明示：`BaseWindow` 自身无 `webContents`；挂上去的 `WebContentsView` **不会自动销毁**（不管即泄漏）；
   `WebContentsView` 默认白底（`BrowserView` 透明）；`setAutoResize` 没了，改自行监听 `resize` 后 `setBounds`。
2. Tauri 2 的单窗口多 webview（`Window::add_child`）**仍是不稳定特性**（需 `features=["unstable"]`，
   官方 PR 自述 API 未完成，tauri#10420 子视图定位仍有 bug，wry#583 Windows 同步命令死锁）
   ⇒ 本项目 `tabs.rs` 走「多窗口伪装 tab」是合理选择，**两壳 tabs 必然不同构，不要移植 tabs.rs 的形态**。
3. Windows 上父窗口移动时子窗口不跟随（官方文档），且 `-webkit-app-region: drag` 区域内的 DOM
   收不到鼠标事件（系统限制，electron#29891）——这两条决定了方案 B（多 BrowserWindow）没有省事的余地。

### 本地实测（Electron 44.4.1，本机 DPI 200%，探针在 %TEMP%\w2a-tabs-spike\）
| 项 | 结果 | 影响 |
| :-- | :--- | :--- |
| `BaseWindow.webContents` | `undefined` | 事件/钩子必须逐视图挂（最大重构面） |
| `BrowserWindow.contentView.children` | `0`，不含自身视图 | 否决「保留 BrowserWindow 只换内容」的省事变体 |
| 窗口几何 API | `getBounds/isMaximized/isFullScreen/setPosition` 齐全 | `window-state.ts` 零改动复用 |
| `setBounds`/`getBounds` 坐标系 | 设读完全一致 ⇒ **DIP** | **不需要** DPI 换算，也不需要 `place_tab` 闭环校准 |
| `setVisible`/`getVisible` | 双向生效可读 | 页签切换首选它 |
| `addChildView(view,index)` | 可用；重复添加会抬到顶层且 children 不增 | z-order 可显式控制 |
| 视图 `ready-to-show` | **未触发**（窗口 `show:false`，待复测） | 首帧时序需准备替代方案 |
| 页签标题 | `page-title-updated` 直接收到 | **无需注入脚本**（Tauri 侧要 `tab_title.js`+IPC） |
| `webContents.close()` 后 | children 3→2，自动摘除 | 不必手动 `removeChildView`，但引用要自清 |

### 设计要点
- 方案 A：`BaseWindow` + 壳视图（`shell://` → `shell.html` **零改动**，新增 `shell-preload.ts` 复用
  `settings-preload.ts` 的 `__TAURI_INTERNALS__.invoke` 白名单垫片）+ N 内容视图（`y=38` 起）。
- **内容视图只注 `loading.js`，不注 `titlebar.js`** ⇒ `window.__web2appChromeH` 自动 undefined
  ⇒ `loading.js:191` 按 `h=0` 满铺 ⇒ **`loading.js` 一行不用改**。
- 页签模式下 `applyChromeFit`/`ensureScrollRoot`/`shimWindowScroll` **整套不需要**（滚动条在视图内，结构性消失）。
- **两处必炸点（已定位到行）**：
  1. `index.ts` 的 `registerWindowIpc` 用 `BrowserWindow.fromWebContents(e.sender)`，页签模式下 sender 是
     壳视图、恒返回 `null` ⇒ **窗口按钮静默全失效**（项目最忌的失败形态）。

2. ⚠️ **get_tabs 契约错位**：tabs.ts 的 list() 返回对象数组 `{label,title,active}`，但 shell.html
   用 `list.map(([label,title,active]) => …)` **元组**解构（对齐 Tauri `Vec<(String,String,bool)>`）——
   对象数组解构得 `[undefined,undefined,undefined]`，标签栏渲染空白。修法：拆出 `listForIpc()`
   返回 `[label,title,active][]` 元组数组供 get_tabs IPC；`list()`（对象）保留给 pushToShell 的 render。
   **教训**：双壳单一真源下，同一份 shell.html 有「两套消费形态」——render() 吃对象、get_tabs 吃元组，
   不能混用。

### 新踩坑（3 个，通用且有价值）
1. ⚠️ **P10 断言首次 FAIL 是「时序断言」错，不是代码 bug**：window.open 触发后，spawnTab 一开头
   count 就 +1，但 activate（置激活）在 onSpawn（loadURL）完成之后。若只看 count 变化就去读
   tabs.active 的 URL，会读到「还没激活」的旧页签（tabs-b.html），误判 path 未保留。
   修法：waitUntil 等「active 换成新 label 且其 URL path 已落到 /opened.html」，别只看 count。
   教训：**「计数变化」≠「状态就绪」**，异步 spawn 的完成要等「可观测终态」而非中间计数。
2. ⚠️ **打包产物 exe 退出码 9 的真凶是 `ELECTRON_RUN_AS_NODE=1`**（沙箱宿主给所有子进程注入）：
   打包 exe 不经 launch.cjs（它负责 delete 这个变量），直接继承后以纯 Node 身份启动即崩。
   修法：PowerShell 里 `Remove-Item Env:ELECTRON_RUN_AS_NODE` 再 Start-Process；Bash 的 `VAR=` 前缀
   在本沙箱 Bash 环境损坏（dirname/tail 命令都找不到）下不可靠。**这是之前「续五」里退出码 9
   的真正根因**，当时 A/B 对照只定性为「环境突变」，现在落到具体变量上。
3. ⚠️ **electron-builder 打包必须 `--config.electronDist=node_modules/electron/dist`**：否则走
   「解压 %LOCALAPPDATA%\electron\Cache 的 zip」慢路径，6 分钟卡死在 "unpacking default Electron
   distribution" 不返回。加 electronDist 后 9 秒完成（复用 node_modules 已解压的 dist）。
   注意参数语法是 `--config.electronDist=...`（`-c.electronDist=` 会被当成配置文件路径报 ENOENT）。
   另：electron-builder 会先跑 `pnpm --workspace-root exec pwd`（Windows 无 pwd ⇒ code=1），
   这是非致命探测、可忽略。
