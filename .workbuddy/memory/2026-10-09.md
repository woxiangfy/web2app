## Android 手动打包后「转圈十几秒 → 白屏」根因分析（第三轮，本轮新发现 3 条）

背景：使用者再问 build-custom.yml 打的 Android 包「打开很慢 → 空白」。v1.60/v1.61 已定位的
「CAP_MS 无条件 done() → 白屏」**仍在工作区未提交**（`git status`：`webview-app/src/loading.js`
`bootstrap.rs` `loading.rs` 均为 M）⇒ CI 只 checkout commit ⇒ 用户手里那个 APK 根本没带修复。
本轮另外挖到三条独立缺陷：

1. ⚠️ **主窗启动页缺「模式标记」先导脚本**（新发现，必然触发）：
   `lib.rs::build_main_window` 只注册 `OVERLAY_SCRIPT`，而 `tabs.rs::create_tab_window`
   **先**注册 `window.__web2appLoadingMode = (location.hostname==='tauri.localhost' …) ? 'splash':'overlay';`
   —— 这份先导脚本主窗漏了。于是 splash 页里内联在 `<body>` 的 `='splash'` 永远晚于
   document-start 注入 ⇒ splash 页的加载层以 **overlay 模式**运行 ⇒ `CAP_MS=15s` + `startReadyWatch()`
   生效；而 splash 的 body 只有 3 个 `<script>`（`bodyEmpty()` 恒真）⇒ **15s 必然 CAP，与网络无关**。
   这解释了「~8s 慢提示 → ~15s 白」的精确秒数，也解释了「手机浏览器正常」为何不矛盾。
   修法：照 tabs.rs 抄一份先导脚本，判据用 `location.hostname === 'splash.localhost'`（见 2）。

2. ⚠️ wry/tauri 在 Windows/Android 把自定义协议改写成 `http://<scheme>.localhost`
   （`wry::custom_protocol_workaround`，`use_https_scheme` 默认 false，本项目未开；tauri
   `manager/webview.rs` 同口径）⇒ 页面里 `location.protocol` 是 `http:`，`splash:` **永不成立**。
   由此 `loading.js::onRetry` 的 `IS_SPLASH && location.protocol === 'splash:'` 是**死分支**：
   落到 `location.reload()` 只重载 `/`，而 `handle_splash` **只有 `/retry` 才触发 bootstrap**
   ⇒ 停在启动页（如 DNS/TXT 解析失败后的失败卡）点「重试」= 无限重载启动页、永远起不来。
   Windows 同样中招（v1.60 的 CAP→失败卡改动把这个死路暴露得更明显）。
   修法：按 hostname 判定 + `location.href = '/retry'`（相对路径，走同一自定义协议源；
   绝对 `splash://localhost/retry` 在内核里不可用）。

3. ⚠️ `proxy.rs:354` `rb.send().await.map_err(|_| StatusCode::BAD_GATEWAY)?`：**丢弃 reqwest 错误、
   无日志、空 body 502** ⇒ WebView 渲染一个**空白文档**。非 Windows 用 rustls + **webpki-roots**
   （Mozilla 内置根证书），与手机浏览器的**系统信任库不是同一套** ⇒ 代理模式下「浏览器能开、
   壳内白」有结构性解释（上游 TLS/连接一失败就空体 502 → 空白 + 无法诊断）。
   修法：代理自造**带可见正文的错误页**（含错误分类）+ `dlog!` 记录被丢弃的错误。

待办（按优先级）：①提交现有 v1.60/v1.61 修复；②补主窗先导模式脚本 + 修 onRetry；③代理错误页 +
错误日志；④重打包后读诊断卡（地址行 = splash.localhost ⇒ 命中 1；= 目标域名 ⇒ 网络/UA/脚本层）。

## 真机回归：安装新包后出现「启动超时」卡（第四轮分析）

前置事实：`940e6e4`（=1009d2）已提交并推送（=origin/main，含 v1.60/v1.61/v1.62 与 bootstrap 可达性探测）。
真机截图：**「启动超时」+「应用初始化耗时过长，请检查网络后重试。」+ 重试按钮**，无诊断行。

判读结论（高置信，全部可由源码逐行推出）：
1. 该文案只出自 `loading.js` 的 `FAIL_MS`（splash 分支，40s）兜底卡 —— 它是**唯一不拼
   `diagText()` 的失败卡**（CAP 卡与 `fail()` API 卡都拼）⇒ 真机只得到一张"零信息"卡。
2. 出这张卡 = splash 文档存活满 40s，且期间 bootstrap **既没导航成功、也没推失败态**
   ⇒ 是「**卡住**」而不是「报错」。若是 DNS 直接失败/DNS 配置读不出来，会显示具体文案
   （「服务器连接失败…」「无法与 host 建立连接（域名解析失败或网络不可达）…」）。
3. ⚠️ **「旧包 / 新包」的判别法（本轮新增，可复用）**：该文案在旧包 `a8533b9` 里**逐字相同**
   ⇒ 单看截图分不出包。但 wry Android 的初始化脚本有**两条**路径，且**两条都早于**
   `splash.html` `<body>` 里的内联标记 `__web2appLoadingMode='splash'`：
   · 支持 `addDocumentStartJavaScript` → document-start 注入；
   · 不支持 → `inject_scripts_into_html()` 把脚本 **prepend 到 `<head>`**（`wry/src/inject_initialization_scripts.rs`）。
   ⇒ 旧包的启动页**必然**跑 overlay 语义，只会出现 **15s 的 CAP 卡（且带诊断行）**；
   ⇒ **真机出现 40s「启动超时」卡 ⇒ 装的确实是含 v1.62 模式标记的包**（前提：初始化脚本注入成功）。
4. 启动期只有两处同步网络动作：hickory TXT 解析（仅 `app_url` 为**域名数组**时）与
   `proxy::start_proxy`。`start_proxy` 只 `TcpListener::bind` + `Client::build()`，不阻塞
   ⇒ **启动期卡住的第一嫌疑是 DNS**。`resolve_url_from_domains` **串行**遍历域名，每个域名
   hickory 默认 `attempts=2 × timeout=5s × 每个 nameserver` ⇒ `tests/json/osfipin.note.json`
   那种 3 域名配置最坏可 >40s，**正好落在这张卡的阈值上**（真机症状「打开很慢」吻合）。
5. ⚠️ 两条**静默丢错误**的通路（Tauri 侧缺 Electron 那个 `__web2appPendingFail` 缓冲）：
   ① `loading.js` 挂载前只装 **no-op 桩**（`fail: function(){}`），此时推错误 = 静默丢弃；
   ② `wv.eval()` 落在"启动页文档还没建立"时 `window.__web2appLoading` 为 `undefined` ⇒ 同样静默丢弃。
   ⇒ 任何"太早"的失败都会退化成 40s 兜底卡，把真因吃掉。
6. 代理模式的两个既有问题（v1.60 备注的 P1，本轮再确认）：`spawn_reachability_probe` 探的是
   `nav.url` = **127.0.0.1:port（自己）**，探不出真因；且 proxy 的 reqwest client
   **完全没有超时**（`proxy.rs::start_proxy`）⇒ 上游不通时 WebView 请求被无限挂住。
7. `dlog!` 默认关（`debug:false`）⇒ Android 上没有 logcat 日志可看；拿证据只能靠
   「配置 `debug:true` 重打包」或「让失败卡自带信息」。

待办（优先级）：① 启动页 FAIL 卡补 `diagText()` + 解析/代理**阶段进度**文案；
② 给 DNS 阶段加**总预算**并改**并发**查询（把 40s 级卡住变成秒级明确失败）；
③ 站早失败不再被静默吞（stub 缓冲 pendingFail）；④ 代理 connect 超时 + 可见错误页 +
探针改探真实上游。

## v1.64：真机新证据 → 定到 Android 启动卡住的**根因**（本轮最有价值的结论）

使用者传来装了新包的截图：40s「启动超时」卡上**已有页面自产的地址/状态/HTTP/UA 四行**，
但**四条阶段进度一条不见**；UA 显示 Android 16 / Chrome 143（内核很新，排除老内核）。

**根因（读 wry 源码逐行确认，非猜测）**：Android 上壳侧一切操作走 `wry/src/android/main_pipe.rs`：
- `WebViewMessage::LoadUrl` / `Eval` 的处理体都是 `if let Some(webview) = get_webview(activity_id) { … }`
  ⇒ **webview 未就绪就静默丢弃**（它只在 `CreateWebView` 处理完才写入 `ACTIVITY_PROXY`）；
- **初始 splash 导航是异步的**：`CreateWebView` 内走 `load_url(main_thread = true)` →
  Kotlin `loadUrlMainThread` = `post { loadUrl(url) }`（排到 UI 队列尾）；而后续 `navigate` 走
  **同步** `loadUrl`。直连配置下 `prepare_navigation` 毫秒级完成 ⇒ 导航先执行，随后**被那条
  post 出去的 splash 加载整体覆盖** ⇒ 地址恒为 `splash.localhost`；
- 同期进度 `eval` 落在 splash 文档 document-start **之前**（`window.__web2appLoading` 还没定义）
  ⇒ `try{…&&…}` 短路 ⇒ 零进度行。**两个症状是同一机制**。

**修复**：非 Windows 启动期**先等首个文档加载完成**再解析/推送/导航 —— `bootstrap::BootReady`
+ `wait_first_page_ready`（预算 `SPLASH_READY_BUDGET_MS = 5000`），就绪信号取建窗时注册的
`on_page_load`（wry Android `ON_LOAD_HANDLER` ← `RustWebViewClient.onPageStarted/onPageFinished`；
`tauri-runtime-wry` **无条件** `with_on_page_load_handler` ⇒ Android 可用）。
⚠️ `Started` 必须**清**标记，否则 `/retry` 重载启动页后沿用旧标记 ⇒「首启修好、重试仍卡死」。
⚠️ 超时**不阻断启动**，只在卡片留一行「页面加载事件缺失」自证。
Windows 不加（WebView2 时序由 wry 保证）⇒ 新增代码全 `#[cfg(not(windows))]`。

主 crate 122→124、工作区 195→**197** 通过 / 6 ignored；2 条新守卫均做反向对照（改坏调用点 → FAILED
→ 还原 sha256 吻合）；cfg 盲区用**互换**验证（8 处 `not(windows)`→`all()`，`cargo check --all-targets`
退出码 0，随后逐字节还原）。

⚠️ 本轮可复用经验：
1. **「导航发了」与「导航生效」是两件事** —— `navigate()` 在 Android 上恒 `Ok(())`，它只是
   「把消息塞进队列」；判定必须看**页面侧的 `location.href`**，不能看返回值。
2. **`cfg` 盲区的验证套路**（可复用）：把**新增**项的 `#[cfg(not(windows))]` 逐行翻成 `#[cfg(all())]`
   （用「前一行恰是 cfg + 本行前缀匹配」的脚本精确命中，别全局 sed，否则会去动既有的 Windows/非
   Windows 分支，报一堆无关的 `cannot find function`），`cargo check --all-targets` 过后从备份还原 +
   `sha256sum` 核对。**备份必须在修改前就做，且要分「改动前/改动后」两次**，否则还原时会把自己的改动一起抹掉。
3. **守卫的反向对照要改「生产代码」而不是改断言** —— 改断言只能证明断言可失败，证明不了它盯着真实代码。
