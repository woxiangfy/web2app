## Android gradle 构建真正失败的根因：gradle.properties 被粘行（commit 8e92af8）
- 用户把完整日志 `android-build.log` 发来后看清楚了——之前猜测的「SDK 平台版本不匹配」**不是**根因（日志里根本没有 "Failed to find Platform SDK"）。
- **真因**（日志第 50 行）：`Cannot parse project property android.nonFinalResIds='falseorg.gradle.stacktrace=all' as boolean`。即**上一轮为定位失败而加的「开启 gradle 错误栈」步骤自己把构建搞挂了**：往 `gen/android/gradle.properties` 追加 `org.gradle.stacktrace=all` 时，原文件 `android.nonFinalResIds=false` **末尾没有换行**，`echo >>` 把新内容直接粘到了同一行，gradle 把 `falseorg.gradle.stacktrace=all` 当成 `android.nonFinalResIds` 的布尔值去解析 → 失败。
- **修复**：追加前用 `tail -c1` 检测末尾是否换行，无则先 `printf '\n' >>` 补一个，保证新行独立。本地模拟「原文件无末尾换行」场景已验证：两行分处两行、可正确解析。
- **可复用教训（写文件/追加配置务必牢记）**：凡是 `echo "x" >> file` 往**已有文件**追加，若不确定该文件末尾是否带换行，必须先补换行，否则极易把内容粘到上一行尾、破坏 key=value 这类格式（gradle.properties / .env / ini 都中招）。或者干脆读取后统一 `printf '%s\n'` 重写。
- 顺带：`>> "$GITHUB_ENV"` 不用担心，runner 管理的 GITHUB_ENV 总是换行结尾。
- 现状：Rust 编译（.so → jniLibs）早已通过，gradle 配置期这一步修复后理论上能继续到 assemble；是否已出可用 APK 待用户重跑确认（仍失败则下载 `android-build-log` artifact 即可定位）。

## 新增 workflow：generate-config.yml（生成手动打包配置 JSON）
- 需求：做一个专门 workflow，手动填表单产出「可直接喂给 build-custom.yml」的配置 JSON。用户选定：仅产出 JSON(artifact)，签名做成可选输入项，文件名 generate-config.yml。

## 本机无 JDK 时用 openssl 生成 Android 签名 keystore（真实签名 JSON 交付）
- 需求：用户质疑 generate-config.yml 产出的签名 4 项为空——他要的是"真的生成签名"。本机无 keytool/JDK/Android Studio（仅 openssl 3.5 + base64）。
- **方案**：openssl 生成 PKCS12 keystore（CI build-custom.yml 的签名命令是 `apksigner sign --ks <file>`，apksigner/JDK17 自动嗅探格式，**PKCS12 完全兼容**，无需 .jks）。步骤：① `openssl req -x509 -newkey rsa:2048 -sha256 -days 10000 -nodes` 生成自签 cert+key → ② `openssl pkcs12 -export -inkey key.pem -in cert.pem -name <alias>` 打成 keystore。openssl3 默认 AES-256-CBC/PBES2 加密，JDK17 可读。
- **注意**：PKCS12 下 key 口令与 store 口令设为**相同**最稳（apksigner --ks-pass 解锁 store，key-pass 回落同 storepass）；故 JSON 里 `android_key_password` 留空即可（build-custom 回落同 storepass）。
- 交付物放 git 仓库**外** `C:/dev/rust/web-app/signing/`：`release.keystore`(2802B) + `ks.b64` + `secrets.env`(storepass/keypass/alias) + `packaging-config.json`(美化,含真签名) + `packaging-config.single.json`(供 config_json 粘贴)。alias=web2app-release。生成后立即 rm 中间 key.pem/cert.pem（私钥敏感）。
- 密码是随机生成的敏感私钥等价物；这批文件含私钥，绝不可 commit/公开分享。签名与 app_url 无关，用户改 app_url/app_name 后签名仍有效；升级必须始终用同一把 keystore 否则覆盖安装失败。
- 校验：`openssl pkcs12 -info -in <file> -passin pass:<store> -noout` 确认含 Shrouded Keybag(私钥)+Certificate bag；python json.load + b64decode 确认 4 个签名键非空、解码 2802B。

## dnd_polyfill.js 修复：draggable 元素"能拖但不能点"（Windows，未提交待编译验证）
- **症状**：Windows 版嵌入的网页里，若 HTML 元素带 `draggable="true"`，现在**不能点击**（只能拖动）。之前是"能点不能拖"，为恢复页面内 HTML5 拖动而开发了该 polyfill（WebView2 OLE 拖放吞掉 dragover/drop），结果反过来把点击也吞了。
- **根因**（旧代码 `mousedown` 无条件进入拖拽）：只要在 draggable 元素（或其祖先）上按下左键，就**立即** `draggable=false` + clone ghost + `isDragging=true` + 派发 dragstart，即便鼠标根本没移动。造成点击失效的两个机制：① ghost 被 `appendChild` 成 `position:fixed; z-index:1000` 覆盖在源元素正上方 → mouseup 命中 ghost 而非源元素 → mousedown/mouseup 目标不一致 → **浏览器不触发 click**；② 无位移也被判成拖拽并派发 dragstart/drop/dragend，干扰依赖点击语义的逻辑。
- **修复思路（阈值判定，让"点击"与"拖动"并存）**：引入 `DRAG_THRESHOLD`（默认 4px）。`mousedown` 只记录候选 draggable 元素（仍立刻 `draggable=false` 抑制原生 OLE 拖放吞点击）并记起点，**不创建 ghost、不进拖拽**；`mousemove` 累计位移，**只有超过阈值才真正 beginDrag**（clone ghost + 派发 dragstart）；`mouseup` 时——若发生过拖动就 drop/dragend + 清 ghost；若只是轻点则只复位 draggable，不派发任何拖拽事件、不创建过 ghost，**浏览器原生 click 照常触发**。
- **可复用教训**：① ghost 遮挡层一旦创建，无论是否拖动，`endInteraction` 里都必须 `clearGhost()` 移除，否则残留遮挡后续点击；② mousedown/mouseup 落在同一元素是浏览器触发 click 的前提，任何"按下即插入覆盖层"的 polyfill 都会杀死点击，必须把"创建覆盖层/进入拖态"推迟到"位移超阈值"之后；③ 兜底：`mouseleave` + `window blur` 时若仍有 pending/isDragging 就 `endInteraction(false)`，防鼠标按住后移出窗口导致 draggable 卡在 false、ghost 残留。
- **验证**：在 `%TEMP%/dndtest`（临时 npm init + jsdom）跑 jsdom 单测 14 项全过：场景1 轻点(无位移)→无 dragstart/无 ghost/draggable 恢复/click 可触发；场景2 拖动(超阈值)→dragstart/drop/dragend 触发 + ghost 清理；场景3/4 mouseleave 兜底清 ghost 恢复 draggable。jsdom 不会自动合成 click（mousedown/mouseup 不派发 click），故"click 可触发"是手动派发验证 polyfill 未劫持——真机 WebView2 行为需重新编译实测。
- 改动仅在 `src/dnd_polyfill.js`（lib.rs 的 `DND_POLYFILL` 注入方式不变）。**未提交、未编译，待用户真机复验**（能拖 + 可点）。

## dnd_polyfill 彻底重写（用户：拖拽"依然无效"，含并行提交 87cb69c）→ 健壮事件流方案
- 背景：前几轮修到"能拖能点、但放不到位置"（共享 DataTransfer）后用户仍反馈无效。判断此前合成事件方案有**客观硬伤**，全部源自社区的坑：
  1. **`clientX/clientY` 不能塞进 `new Event(type,{clientX})` 的 options**——`EventInit` 不收坐标 → 读到的 `undefined` → 拖放库无法用坐标定位/放置。
  2. **缺 `dragenter/dragleave`**：只发 dragover 且仅目标变化时发一次；库靠 enter/leave 驱动 dropzone 激活态。
  3. **ghost 挡住 `elementFromPoint`**：需 `pointer-events:none`。
  4. **每次事件 new 空 DataTransfer**：需会话级共享。
- 重写方案（已落 HEAD `87cb69c`，381 行）：`buildDragEvent` **优先 `new DragEvent(type, init)`**——DragEventInit 原生收 `clientX/clientY/dataTransfer/screenX`（Chromium 支持），失败才退化 `Event`+手动赋坐标；**优先原生 `new DataTransfer()`**（探测构造+setData+types>0 才用，否则 mock）；完整事件流 `dragstart → [dragenter(进新目标)/dragover(连续)/dragleave(离目标或移出到空白)] → drop → dragend`；ghost 克隆后 `position:fixed; pointer-events:none; zIndex 高位; opacity .7` 并清掉内部 draggable；会话共享 DataTransfer；`DRAG_THRESHOLD=4` 区分拖/点，轻点不劫持保 click；mouseleave/window.blur 兜底复位。事件监听用 capture=true。
- 验证：node --check 过；jsdom 16 断言全过（事件序列、clientX/Y 真实为坐标、drop 读回 dragstart 数据、轻点不触发、enter/leave、ghost pointer-events:none 且被移除）。**测试暴露一个真 bug 并已修**：`updateHover` 里 elementFromPoint 返回 null（移到空白）时旧目标没收到 dragleave → 补"无目标则对 currentOverElement 发 dragleave 并清空"。
- ⚠️ 局限：合成事件 `isTrusted=false`，个别严谨拖放库仍可能拒收；jsdom 无法复刻真实库。**真机仍可能要实测**；用户若再报无效，需其提供嵌入站点/所用拖放库与具体失败表现再定，勿再盲改。

## 真机暴露两个 bug 修复（commit 8e1cc36，推送 origin/main）
- **Bug1：右键「设置」弹出设置窗体后整进程卡死**。根因：WebView2 的 CustomItemSelected/ContextMenuRequested 回调本就运行在【主线程】（wry 把 WebView2 放主线程），而 tauri 的 `run_on_main_thread` 检测到"已在主线程"会【同步内联】执行闭包（tauri-runtime-wry `send_user_message`：`current_thread().id()==context.main_thread_id` 分支直接 `handle_user_message`，不排队）。于是右键点设置时 `open_settings_window` 是在 WebView2 自身 COM 事件分发栈里同步执行——再 build 第二个 WebView2 控制器(settings 窗)需要 COM STA 重入，此上下文无法完成 → 死锁卡死。Shift+F1 从普通事件循环回调调用故正常。
  - 修复：点击处理里先 `std::thread::spawn` 切到后台线程，再从非主线程 `run_on_main_thread` 走 event_loop proxy 排队，等 COM 分发退栈后【下一事件循环轮次】才在主线程建窗（调用上下文与 Shift+F1 等价）。
  - **可复用铁律**：凡是从 wry/WebView2 COM 回调这类"已可能在主线程"的上下文要再跑主线程任务，绝不可直接 `run_on_main_thread`（会同步内联并可能在嵌套 COM 分发里死锁）；要先切后台线程让它走 proxy 排队，或用 async 延后一帧。**写代码时用注释把"为什么"钉死**，否则后来者看到 run_on_main_thread 会"好心改回"而复活 bug。
- **Bug2：窗口有时很小/屏外显示不了，退出重开依旧**。根因：`window_state::apply` 盲目恢复上次保存的 x/y/width/height；若上次位置因显示器拔掉/分辨率/DPI 变化落到屏外，或尺寸退化极小，窗口看不到/很小，且每次重开都恢复同一份坏坐标 → 永远无法自愈。
  - 修复：apply 增加几何校验——上次已最大化直接最大化并 return；用 `win.monitor_from_point(窗口中心点)` 判窗口中心是否落在任一当前显示器上（屏外→丢弃几何直接最大化兜底）；尺寸 `<420x320` 视为损坏同样最大化；几何有效才 set_position+set_size。
  - **可复用要点**：Tauri `Window::monitor_from_point(x,y)` 是纯坐标点查询（与窗口当前位置无关），适合在恢复几何前做"是否屏外"校验；`Monitor::work_area()` 返回 `&PhysicalRect<i32,u32>`（tauri::dpi 重导出，字段 x/y/width/height）。几何存储最好带个 schema 版本/校验，恢复前过一遍显示器可达性。

## 动态解析真实 URL：app_url 数组 + RSA 公钥解密（未提交）
- 需求：手动打包时 `app_url` 可为**域名数组**，运行时依次对每个域名做 DNS TXT 查询，用配置的 RSA 公钥（PKCS#1 v1.5）解密 TXT 值得到真实 URL；单域名失败试下一个，全部失败报「服务器连接失败」。
- 新增 `src/resolve.rs`：`parse_domains`（判断 APP_URL 是否 JSON 数组）、`normalize_domain`（去 scheme/端口/路径/userinfo）、`query_txt`（hickory-resolver 同步 `Resolver::from_system_conf()` + `txt_lookup`）、`rsa_decrypt`（`m = c^e mod n` 公钥方向）+ `strip_pkcs1_v1_5_padding`（兼容类型 1 签名块 / 类型 2 加密块）。
- **关键踩坑**：
  1. RSA「公钥解密」是**非标准方向**（标准是公钥加密/私钥解密）。用户需求是「服务端私钥加密、客户端公钥解密」＝签名方向。`rsa` crate 的 `RsaPublicKey` **没有** `decrypt` 方法，须用 `PublicKeyParts` 拿 `n()/e()` + `BigUint::modpow` 手写 `m = c^e mod n`。
  2. `BigUint::to_bytes_be()` 会**省略前导 0x00**，而 PKCS#1 v1.5 块首位必须是 0x00 → 结果 255 字节（少了首字节）。须补零到模数字节长 `k=(n.bits()+7)/8`。
  3. openssl 生成「私钥加密」密文用 `pkeyutl -sign`（默认 PKCS#1 v1.5 签名，类型 1 填充），不是 `pkeyutl -encrypt`（那是公钥加密）。端到端测试 `e2e_public_key_decrypt` 已固化这组密钥验证。
  4. `normalize_domain` 的 `split('@')` 必须在切 `://` 和 `:` 之前，否则 `user:pass@host` 被误切成 `user`（用 `next_back()` 取最后一段，clippy 要求）。
  5. **GITHUB_ENV 多行值**：`public_key` 是 PEM 多行文本，直接 `KEY=value\n` 会截断成多个环境变量，须用 heredoc 语法 `KEY<<EOF\n...\nEOF`。CI 里还做了 `\n` 字面量→真实换行 + 去 `\r` 的规范化。
- 依赖新增：`rsa = { version="0.9", features=["sha2"] }`（`from_public_key_pem` 需 pkcs8/pkcs1 feature，0.9 默认含；SPKI 头用 `pkcs8::DecodePublicKey::from_public_key_pem`，PKCS#1 头用 `pkcs1::DecodeRsaPublicKey::from_pkcs1_pem`）、`hickory-resolver = "0.24"`（默认 feature 含 system-config+tokio-runtime，同步 `Resolver` 自带内部 runtime）。
- 改动文件：src/resolve.rs(新)、src/lib.rs(加 PUBLIC_KEY 常量 + setup 里数组模式解析)、Cargo.toml、Cargo.lock、build-custom.yml(两处 DEFAULTS 加 public_key + app_url 数组处理 + heredoc 写入)、config.example.json、README.md。
- 验证：`cargo test --lib` 15 个测试全过（含 e2e 公钥解密）；`cargo build --release` 通过；CI 内嵌 Python 脚本干跑验证 heredoc/数组逻辑 OK。**未提交**。
