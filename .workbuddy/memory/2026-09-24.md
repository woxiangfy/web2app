## 第三波（同日）：本地打包入口由 Python 改为 Node（`scripts/pack-local.mjs`）

**来源**：使用者提问「你给的是 python 打包 默认环境没有，用 rust 呢？」（最终选定 **Node**）。

### 步骤（可复用）

1. **先取证「默认环境到底有什么」**，别接受「装了 Python」这种印象：
   - `where python` 命中的是 `~/.workbuddy/binaries/python/3.13.12/`（**会话注入**）；
   - 系统里 `%LOCALAPPDATA%\Programs\Python\*` / `Program Files\Python*` / `C:\Python*` / `py.exe`
     **全部不存在**；
   - 用 PowerShell 读**持久 PATH**（`[Environment]::GetEnvironmentVariable('Path','Machine'|'User')`）
     才拿到真实家底：`~/.cargo/bin`（Rust）、`C:\pf\node-v24.20.0`（Node）、laragon 的 PHP、
     `C:\pf\zig`、PowerShell 7 —— **没有 Python**。
2. **选「打这个包的必要条件」作为 driver 语言**：打 Electron 包必须 `node`（electron-builder 是
   node 程序、`pnpm run sidecar/build/stage` 全是 node 脚本）；打 Tauri 包必须 `cargo` 与 tauri-cli。
   ⇒ Node 对 Electron 是零新增依赖，Rust 则会让「只想打个绿色版」的人被迫装整套工具链。
3. **换语言 = 第二份解析实现 ⇒ 必须先设计护栏再动手**：`--selftest`（把 Python 解析器的
   `_selftest_cases` 逐条移植）+ `--parity`（两侧对同一批 payload 比对**退出码 / `::warning::` 序列 /
   错误文案 / `config.json` 字节**），并把两条接进 CI 的 `config-contract` 作业。
4. **复刻时先穷举「Python 语义 ≠ JS 直觉」的点**，否则 `--parity` 会一条条打回来：
   `str(True)`→`"True"`、`str(None)`→`"None"`、`type(v).__name__`、`repr()` 的引号选择、
   `difflib.SequenceMatcher.ratio()`（**不是** Levenshtein，`electron-app` 的 `nearestKey` 用的是
   另一套算法）、`sorted()` 的逐码位序、`dict` 插入序即输出序。
5. 端到端跑真实产物 + 包内 `out/config.json` 校验 + 备份还原的 sha256 比对。

### 关键结论

- **`--parity` 首次就抓到真实差异**：8 例「错误文案不一致」，实际是本机 Python 的 `print()` /
  `Path.write_text()` 把 `\n` 翻成 `\r\n`（Windows `os.linesep`）⇒ 比对必须**归一化行尾**，
  并把这类差异**降级为一条汇总提示**（CI 是 Linux，两侧都是 LF，逐字节比对）。最终 **39/39 语义一致**。
- Node 版**不落 env 文件**（把 `env` 直接给子进程）⇒ 解析器 `--env-out` 那五个坑天然不存在；
  `config.json` 一律写 **LF**（与 CI 一致；反倒是本机 Python 写 CRLF 与 CI 不一致）。
- 加固项：传给子进程的 env 里**剥掉 `ELECTRON_RUN_AS_NODE`**（本机是 `1`）—— 对普通 node 无害，
  但会让子进程里的 **electron.exe** 退化成 node 模式。
- 端到端实证：产物 `osfipin.test-0.1.0-win-x64.zip`(148M) / `-portable.exe`(97M) 的名字来自 JSON 的
  `app_name`；`check-asar-config.cjs` 通过（24 条目）；包内 `out/config.json` **14 字段**、
  `tabs_enabled` 是真 bool、`debug` 自动补默认值、无 `android_*`；`electron-app/config.json`
  打包后 **sha256 `5b3458db455f` 逐字节还原**。

### ⚠️ 本轮踩的两个环境坑（新）

1. ⚠️⚠️ **`env -u ELECTRON_RUN_AS_NODE node …` 会吞掉 stdout**（exit 0、零输出），
   `node -e "…"` 也一样（连 `console.log('x')` 都不出）。
   ⇒ **不要用 `env -u`**（`ELECTRON_RUN_AS_NODE` 只对 **electron.exe** 有害，普通 node 不受影响），
   且**不要用 `node -e`**，一律写成脚本文件再 `node file.cjs`（`check-asar-config.cjs` 正是这么被调的）。
   判据：**「退出码 0 但无输出」先换写法，再怀疑逻辑**。
2. ⚠️ 产物清理：`electron-app/tests/pack-node/` 348MB，逐文件 `rm` 两轮后只剩 **2 个 `.asar`**
   （281K + 110K）—— 与既有记录一致（垫片在 `.asar` 上恒定失败）。**大文件（zip / 主 exe）第一轮

### ⚠️⚠️ 本轮最重要的教训：不要自己去清输出目录

1. 第一版（原有）：让人工删 ⇒ 违反「JSON 定义行为」。
2. 第二版（我改的）：脚本**先自己清空** `release/`，清了 1000+ 个文件 ⇒ **烧掉本机删除配额**
   （`SAFE_DELETE_BULK_CONFIRM_REQUIRED {"count":50,"threshold":50,"scope":"turn"}`）⇒
   electron-builder 随后连**自己的中间产物** `*.nsis.7z` 都删不掉 ⇒
   **zip / portable 明明已经产出，构建却以「失败」收尾**（`PACK_EXIT=1`）。
   这比原缺陷更坏：把「产物已就绪」伪装成「构建失败」。
3. 第三版（定稿）：**先不管**，让 electron-builder 按常规流程自己清；**只有它被 `safe-delete`
   拦住时**才自动换 `release/local-<时间戳>/` 重试一次（全新目录没东西可清 ⇒ 必然能出包）。
   实现 = `runTee()`（**边跑边透传**输出，同时留 400 行尾部）+ `isDeleteBlocked(tail)`
   （正则 `safe-delete|emptyDir|trash operation`）。同一环境复跑 → **`PACK_EXIT=0`**。

> 通用原则：**「自己先做一遍准备」有时比「不管、失败再补救」更差** —— 它消耗的是
> **共享且有限的环境资源**（这里是全局删除配额），而且失败点会被推迟到别处、伪装成别的问题。

### `--parity` 诊断补强（顺手）

- `spawnSync` 的 `error` 原先被吞 ⇒ 进程起不来时只报「退出码 null」，信息量为零。
  现在分两类：**未能验证**（spawn 失败＝环境限制，退出码 `2`）vs **语义不一致**（退出码 `1`）。
- 实测：**PATH 上那份 `python` 从 Node 里 spawn 恒定 `EBUSY`**（45/45 全败；换成脚本文件复测同样如此。
  `findPython()` 兜底到绝对路径后才跑得起来），连续 spawn 到第 **~37** 次再次 `EBUSY`
  ⇒ 本机 `--parity` 会留 1–2 例「未能验证」。**CI 是 Linux，不受影响**。
