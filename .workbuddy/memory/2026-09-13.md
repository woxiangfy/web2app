# 2026-09-13

## 多页签（tab）模式三个用户反馈问题的根因与修复

用户反馈：① 弹窗（`target="_blank"`）打开的新 tab 永远停在 app_url；② 3 个标签关掉一个后，再关标签整个软件卡死；③ 宿主窗口与 tab 窗口“两个窗体不一致”。

### 根因
1. **弹窗落点（①）**：启用本地反向代理时 WebView 实际 origin 是 `http://127.0.0.1:<port>`，页面里 `window.open(path)` 解析出的主机是 `127.0.0.1`；而 `open_new_tab_from_request` 拿目标主机去比**上游真实主机**（`upstream_host`）→ 恒不相等 → 一律放弃目标路径 → 新 tab 只剩 app_url。
2. **关闭卡死（②，主因）**：`close_tab_inner` 用 `window.close()`；lib.rs 的 `CloseRequested` 分支先 `prevent_close()` 再回调 `close_tab_inner` → 此时该 label 已从列表移除、但守卫 `tabs.len() <= 1` 在“剩余 ≥2 个 tab”时通过 → 再次 `window.close()` → **无限循环**（close → CloseRequested → close_tab_inner → close …），主线程 100% 占用、界面完全无响应。只有“关闭后只剩 1 个 tab”时守卫才提前 return（所以现象与 tab 数相关）。附带后果：所有被 prevent 的关闭都留下**幽灵窗口**（未销毁、不受 relayout 管理、仍占一个 WebView2 渲染进程）。
3. **窗体不一致（③）**：`relayout` 用 `outer_position/outer_size`。宿主 `decorations(false)` 但 `resizable(true)`，Windows 下仍有不可见调整边框（WS_THICKFRAME）→ outer 比客户区大一圈 → tab 窗口比宿主客户区更宽更靠下，右侧溢出宿主边框。

### 修复（主体在 `src/tabs.rs`；`lib.rs` / `tray.rs` / `webview_hooks.rs` 少量接线）
- 新增 `host_content_rect()`：以 **inner（客户区）** 几何 − 标签栏物理高度（`38 × scale`，用 **floor** 避免分数缩放下留缝）作为 tab 目标区域。
- `relayout()`：改用 `host_content_rect()`；tab 侧 `set_size` 设**客户区**尺寸（tao `set_inner_size` 会自行补偿无边框隐藏偏移），`set_position` 设的是**窗口矩形**位置 → 减去 `frame_offset()`（outer − inner）补偿。宿主 `on_window_event` 增加 `ScaleFactorChanged` 触发。
- `close_tab_inner()`：① 先摘登记并快照 label；② **`destroy()` 代替 `close()`**（强制销毁、不派发 CloseRequested，断开重入链）；③ label 不在册＝重复进入 → 直接返回；④ 关最后一个 tab → `close_host_window()` 走宿主关闭语义（托盘最小化 / 退出）。
- `activate_tab()`：按 label 定位索引 + 快照 label 列表，**所有 MutexGuard 都在块内释放**（锁不跨 FFI）；先 relayout 再 show/hide；label 不在册时不清空界面。
- `purge_orphan_tabs()`：销毁所有「label 以 `tab-` 开头但不在册」的窗口（自愈幽灵窗口）。`spawn_tab` 改为**先登记占位再建窗**（避免并发连点“+”时新窗被清理误杀），建窗失败回滚登记。
- `spawn_tab` 增加 `visible(false)` 建窗 + 按宿主内容区给初始尺寸 → 消除首帧 800×600 闪烁。
- 弹窗：新增 `resolve_popup_url()` —— 目标与**入口主机**（代理模式下即 `127.0.0.1:port`）或**上游主机**同源时，把 path/query/fragment 映射到入口地址；跨域外链仅在本地代理模式下直开（无凭据泄漏风险），直连 + userinfo 时维持入口地址。`spawn_tab_with_target(start)` 把目标地址并入**首次导航**，去掉历史“先建窗导航主地址再二次导航”的竞态。
- `set_tabs_visible()` + tray/lib 接线：宿主隐藏到托盘时一并隐藏 tab 窗口（否则桌面残留无标签栏的内容窗口）；恢复时显示当前 tab，若一个 tab 都没有则自动补建。
- `webview_hooks::navigate_webview` 已无调用方 → 删除。

### 可复用教训（Tauri 多窗口叠放伪装成 tab）
- 关闭子窗口一律 `destroy()` 而非 `close()`：只要宿主侧对 `CloseRequested` 做了「prevent_close + 回调关闭逻辑」，`close()` 就会与之互相重入 → 无限循环卡死主线程。
- 窗口几何「内外有别」：定位/尺寸以 **inner（客户区）** 为准；`set_size` = 客户区尺寸，`set_position` = 窗口矩形位置（需用 outer − inner 补偿）。
- 多窗口状态以 **label** 为键（不用索引），且**任何 MutexGuard 都不跨越窗口 API 调用**。
## 修复第二轮：用户反馈"并没有改好，仔细看图"

实测像素扫描两张截图（图 A 285×210 / 图 B 282×249）后定位到：

- **窗体不一致（实测 22 像素凸出）**：根因不在 `outer` vs `inner` 几何，而在 **window style**。
  - 宿主 `.decorations(false) + .resizable(true)` → Windows 仍加 `WS_SIZEBOX` (= WS_THICKFRAME)，每边约 11 物理像素（150% DPI）。`outer = 用户期望`，`inner = outer - thick_frame = 用户期望 - 22`。
  - tab `.decorations(false) + .resizable(false)` → 无 `WS_SIZEBOX`，`outer = inner = 用户期望`。
  - relayout 用 `host.inner_size` 作为 tab `set_size` 输入 → tab inner = 用户期望 = host inner + 22 → tab 凸出 22 像素。
  - **修复**：宿主也改为 `.resizable(false)`。无 WS_SIZEBOX → outer = inner = 用户期望，双方对齐。**副作用**：用户无法用鼠标拖窗边框 resize——但宿主本就是 `decorations(false)` 没边框可拖，调整大小由应用层通过 Rust 命令触发即可。
  - **没改** `relayout` 主体：用 `frame_offset(tab)` 补偿 set_position 的旧逻辑仍正确（tab 当前 outer-inner 偏差会自然反映 WS_THICKFRAME 等）。

- **弹窗新 tab 永远是 app_url**：根因不在 `resolve_popup_url` 同源判断，而在于 **WebView2 controller 时序**。
  - `attach_webview_hooks` 用 `window.with_webview` 闭包调 `core.Navigate(target_url)`。wry 的 WebView2 controller 创建是**异步**的（`CreateCoreWebView2EnvironmentWithOptions`），多页签模式下 Rust 同步建窗→attach 之间经常存在时序差：闭包跑时 `CoreWebView2()` 还没就绪 → 整个函数 `Err` 直接 return → 钩子**全部未注册** + Navigate **未触发** → tab 停在 builder 默认入口 `index.html`（即用户看到的"app_url"，因为 `WebviewUrl::App("index.html")`）。
  - **修复**：
    1. `attach_webview_hooks` 改成**不 Navigate**，只注册事件钩子；`with_webview` 闭包内 `CoreWebView2()` 循环重试（50ms 一档，5s 超时 + 日志），保证钩子必注册。
    2. `navigate_window`/`navigate_main` 在 attach 之后调 `WebviewWindow::navigate(Url)` → wry 内部会等 controller 就绪再触发 WebView2 的 Navigation。

## 可复用教训（Tauri 多窗口叠放伪装成 tab）
- 关闭子窗口一律 `destroy()` 而非 `close()`：只要宿主侧对 `CloseRequested` 做了「prevent_close + 回调关闭逻辑」，`close()` 就会与之互相重入 → 无限循环卡死主线程。
- 窗口几何「内外有别」：定位/尺寸以 **inner（客户区）** 为准；`set_size` = 客户区尺寸，`set_position` = 窗口矩形位置（需用 outer−inner 补偿）。
- 多窗口状态以 **label** 为键（不用索引），且**任何 MutexGuard 都不跨越窗口 API 调用**。
- 叠放式 tab 的窗口可见性必须与宿主联动（隐藏宿主时一并隐藏 tab），否则会留下"孤儿窗口"被误判为卡死。
- **WS_SIZEBOX 不对称 = 必然凸出**：双方必须用**完全相同**的 resizable 设置（都是 `false` 或都是 `true`），否则 outer-inner 偏差不同，inner 几何对齐算法必然错位。
- **wry 的 WebView2 controller 是异步创建的**，Rust 同步调 `with_webview` 经常太早 —— 任何"在 with_webview 闭包里 Navigate"的做法都可能在 controller 未就绪时静默 return 让 Navigate 丢失。正确做法是钩子注册与导航**分离**：闭包只注册事件，导航交给 wry 自己处理（`WebviewWindow::navigate(Url)`）。

### 两个新增的关键机制
1. **最小化同步（`sync_tabs_with_host` + `TABS_SUSPENDED: AtomicBool`）**：tab 窗口是独立顶层窗口，宿主最小化时**不会**跟着最小化 → 桌面上会残留没有标签栏的内容窗口。改为在宿主 `WindowEvent::Resized` 回调里读 `is_minimized() || !is_visible()` 同步 tab 显隐。选 `Resized` 而非自建入口判断，是因为**所有**最小化路径（自绘按钮 / 任务栏右键 / Win+↓）最终都走 Windows `WM_SIZE` → tao 转成 `Resized`。用 `TABS_SUSPENDED` 做状态门控，避免拖拽缩放时高频 `show/hide` 造成闪烁（`set_tabs_visible` 是所有显隐的唯一出口，在其中 store 标志）。
2. **`destroy_all_tabs()`**：宿主「允许关闭」（非托盘隐藏）时的兜底。tab 不是宿主的子/owned 窗口，宿主销毁**不会**带走它们 → 会变成「标签栏没了、内容还在、应用还不退出」（Tauri 要等**所有**窗口关闭才派发 `ExitRequested`）。在 `handle_main_close` 的 else 分支显式 `destroy()` 全部 tab。

### 其他
- `host_content_rect()` 增加 `is_minimized()` 提前返回 `None`：最小化时客户区尺寸会被报成 0，不能拿去 `set_size`（否则 tab 被压成一条缝，恢复后全乱）。

- **无边框（`decorations(false)`）窗口的自绘标题栏必须自己补齐系统按钮**，否则用户只剩托盘/任务栏右键可用。

## 第二轮修复：三个真根因（用户反馈「改了个寂寞」后重新定位）

收到「改了个寂寞」后不再猜，逐条回到依赖库源码核对，找到三个**互相独立**的真根因。

### 1. 弹窗落不到目标页 → `TabManager.navigation` 缓存恒为 None
- 排查路径：跟数据流反查「这份数据谁写的？真的写过吗？」
  → `resolve_popup_url` 的 `nav` 来自 `TabManager.navigation`；写它的只有 `bootstrap_inner`；
  → 多页签模式首 tab 走 `spawn_tab` → `navigate_tab`（缓存空）→ **`bootstrap_for_label`**，它传 `is_first = false`。
- 结论：缓存**从未被写入过**。`resolve_popup_url` 开头 `let nav = ...clone()?` 直接短路 → 恒返回 None → 新 tab 一律落主地址。
- 连锁副作用：每个新 tab 重新 DNS 解析 + 再起一个本地代理，`bootstrap_inner` 开头又 abort 掉旧代理 → 已在用的 tab 断连。
- 修复：`bootstrap_for_label` 也传 `true`；`is_first` 更名 `cache_navigation`（它就是「是否写缓存」）。

### 2. 钩子注册死锁 → `with_webview` 在主线程是内联同步执行的
- 排查路径：读 `tauri-runtime-wry-2.11.4` 的 `send_user_message`
  → 主线程：`handle_user_message(..)` **内联同步**；非主线程：`proxy.send_event` 异步投递。
  → 而 WebView2 controller 创建回调**依赖主线程消息泵** ⇒ 主线程闭包里 `sleep` = 死锁。
- 结论：上一轮加的「5s 轮询重试」不但拿不到 controller，还让启动/建 tab 白卡 5 秒。
- 修复：调度/注册拆开。`attach_webview_hooks` 在**后台线程**循环 `with_webview`（每次只试一次，失败 sleep 50ms 重试，
  5s 上限，用 `Arc<AtomicBool>` 判断闭包是否真跑到注册那步）；注册体移到 `register_webview_hooks`，
  且**不许提前 return**（调用方靠「是否跑完」判断成功，否则会重试导致处理器重复挂载）。

### 3. 窗体不一致 → 客户区内缩只与 DPI 有关，与 `resizable` 无关
- 排查路径：读 `tao-0.35.3` 的 `window_proc` WM_NCCALCSIZE 分支 →
  `util::calculate_window_insets` → `calculate_insets_for_dpi(dpi)`，**函数体里只有 dpi，不读 style**。
- 结论：之前「统一 resizable 让两边一致」是**无效改动**（记忆里其实早写过「与 style 无关」，被自己推翻了）。
- 修复：宿主 + tab 都 `.shadow(false)`（`MARKER_UNDECORATED_SHADOW=false` → NCCALCSIZE 不内缩 → `outer == inner`）；
  `relayout` 改成闭环校准（新增 `place_tab`：设置→读回→补偿 ≤3 轮），删掉 `frame_offset`；
  `activate_tab` 在 `show()` 之后**再补一次** `relayout`（隐藏态读到的几何是占位值）。

### 诊断增强
- `NewWindowRequested` 回调用 `eprintln!` 打印「窗口 <label> 拦截到新窗口请求：<url>」，
  下次可直接区分「钩子没生效」与「目标 URL 是 about:blank / 同源判断错」。

### 可复用教训
- **别用「像素级观察 + 归因」代替读源码**：观察能给出症状（22px），但归因（WS_SIZEBOX）可能是错的；
  `~/.cargo/registry/src/**/` 里有全部依赖源码，几何/时序类问题几乎都能在那里找到确定性答案。
- **先确认「闭包在哪个线程跑」再决定能不能阻塞**；`Send + 'static` 不代表在别的线程执行。
- **排查「一直不对」类问题，优先假设「数据从没被写入 / 分支从没走到」**，而不是「逻辑写错了」。
- 上一轮的修复如果基于错误归因，会在错误方向上叠加复杂度（轮询 → 死锁 + 卡顿），比不改更糟。

- `TABS_ENABLED=true` 与默认两种模式 `cargo clippy --all-targets -- -D warnings` ✅
- `cargo test`：35 passed / 0 failed / 3 ignored ✅

## 19:20 用户反馈「点一次不停的打开新窗口，电脑都被干死机」——是我上一轮引入的回归

### 症状与归因
- 上一轮把 controller 轮询从「主线程闭包内 sleep」改成「后台线程循环 with_webview」后，钩子终于真的注册上了，但**注册了不止一次**。
- 决定性证据（`tauri-runtime-wry-2.11.4/src/lib.rs:235 send_user_message`）：
  ```rust
  if current_thread().id() == context.main_thread_id { handle_user_message(..) }  // 内联同步
  else { context.proxy.send_event(message) }                                     // 异步投递，立即返回
  ```
  即：**从后台线程调 `with_webview` 是异步投递**，调用方发完就返回。所以 5s 重试循环里
  每次 sleep 50ms 都会再投一个闭包，**多个闭包同时在路上**，它们随后逐个执行、**每个都**
  调用 `register_webview_hooks` → 同一窗口挂上多个 `NewWindowRequested` 处理器。
- WebView2 会把**一次**点击分发给**每一个**已注册的处理器 → 一次点击开 N 个新窗口。
- 更糟的是 N 随主线程繁忙程度增长：窗口越多 → 建窗越慢 → 在途闭包越多 → N 越大 →
  正反馈，几十个 WebView2 进程一起启动，整机卡死。这解释了为什么是「不停」+「死机」。
- 排除项：`dist/index.html` 是无害占位页；注入脚本（`loading.js`/`tab_title.js`/`dnd_polyfill.js`）
  里没有 `window.open`；全局 `attach_webview_hooks` 只有 `navigate_main`/`navigate_window` 两个调用点、
  且每个窗口各一次；事件循环里没有「响应窗口事件再建窗」的路径。所以 N 只能是「处理器挂载数」。

### 教训（比上一轮更根本）
- **「重试」和「幂等」必须成对设计**：只要重试的投递是异步的，就无法在投递侧判断
  「后续闭包会不会重复执行」——去重必须做在**真正执行副作用的那一行**（这里是
  `register_webview_hooks` 开头），而不是放在调度层靠标志位猜。
- 我上一轮在 `register_webview_hooks` 上写注释警告「提前 return 会导致处理器重复挂载」，
  却只防住了「提前返回」，没防住「多个闭包同时在途」——**一个已知风险只防了一半，等于没防**。
- **异步投递的 API，别假设「一次调用 = 一次执行」**；这类竞态在负载低时完全不出现（
  主线程空闲 → 第一个闭包立刻执行 → 循环立刻收尾），只在机器忙的时候爆发——正好是用户
  连开几个标签之后。

### 修复

## 晚 · 页签下网页被宿主盖住：tab 未设 owner

用户反馈：点标签栏里**页签右侧的空白拖动区** → 页签下的网页被隐藏；再点一下页签才出来。

### 取证（像素级，无 Pillow 可用）
- 用纯 Python（struct+zlib 手写 PNG 解码）扫用户截图里的红色箭头：尖端坐标 **x=379**，
  而活动页签的右边界是 **x=331**（截图 125% DPI，标签栏 47.5 物理像素高）。
  → 箭头指的是**页签右侧的空白区**（`.tabs` 的 `-webkit-app-region: drag`），不是页签本身。
- 因此排除「点的是 ×」的猜测：若点击关闭，页签会消失，与「点标签才出来」不符。

### 根因
宿主（标签栏）与 tab（网页内容）是**两个互相独立的顶层窗口**，tab 没有设 owner → 在 z-order
上完全平等。点宿主**任何**位置都会激活宿主并把它抬到 tab 之上；宿主客户区在标签栏下方是一大
片空底色，正好整个盖住 tab 的网页。再点页签时 `activate_tab` 里的 `set_focus()` 又把 tab 抬
回来 → 看起来像随机闪烁，实际是确定的 z-order 关系。

### 修复
`spawn_tab_with_target` 中给 tab 建窗时加 `.owner(&host)`（tao `Parent::OwnedBy` → 加 POPUP）。
MSDN：owned window 永远在 owner 之上；owner 最小化时由系统隐藏、销毁时由系统销毁。

源码核对（关键，避免再踩）：
- tao `window_state.rs:321`：`apply_diff` 在 flag 无变化时**直接 return** → `show/hide` 是
  「标志位去重」的；owner 自动隐藏 owned 窗口时 tao 不处理 `WM_SHOWWINDOW`，标志会短暂脱节，
  靠 `sync_tabs_with_host` 在每次 `Resized` 后重设可见性自愈（已写进代码注释）。
- tao `event_loop.rs:2128`：`WM_NCCALCSIZE` 对 undecorated 窗口不走默认处理 → 无 NC 区，
  POPUP 不影响 `outer == inner`，`place_tab` 闭环校准照常收敛。

验证：`cargo fmt` ✅ / `TABS_ENABLED=true clippy -D warnings` ✅ / 默认模式 clippy ✅ / 35 tests ✅。

## 20:5x 单窗口模式：顶部栏与加载动画都不出现（注入脚本 DOM 时机）

用户反馈：①「无多标签时，没有顶部的菜单栏了」②「首次打开的时候，页面需要加载，应该放通用的
加载动画（之前实现过），让过渡丝滑一点」。

### 定位过程（关键：这次先做实验，没有再靠推理）

1. 排除法：`decorations(false)` + 自绘标题栏（`titlebar.js`）自 `2f19085` 起就没动过，注入点
   （`build_main_window` 的 `initialization_script`）也从未变过 → 不是「改动回归」。
2. 横向对照三个注入脚本的写法，发现关键差异：
   - `dnd_polyfill.js`：只 `document.addEventListener`（document 对象在 document-created 时就
     存在）→ **一直正常工作**（用户验证过拖拽修复）；
   - `tab_title.js`：`querySelector` + `DOMContentLoaded` 重试 + 全 try/catch → 正常工作；
   - `loading.js` / `titlebar.js`：**在 document-created 阶段直接 `appendChild` 到
     `document.head || documentElement`**，且无任何等待 → 疑似静默失败。
3. 查 MSDN：`AddScriptToExecuteOnDocumentCreated` 的脚本「runs after the global object has been
   created, **before the HTML document has been parsed**」——即 DOM 树可能根本不存在。
4. **写探针实测（`examples/probe_dom_ready.rs`，不可见窗口 + wry IPC 回传）**，结果：
   ```
   at_created: {de:false, head:false, body:false, rs:"loading"}
   naive_append: "ERR: Cannot read properties of null (reading 'appendChild')"
   ```
   → **`documentElement` 就是 null**，旧代码必然抛错被吞掉。根因确证（而不是推测）。
5. 同一探针验证修复：用 `whenHostReady` 等待宿主后 → `mounted_after_wait: "BODY -> BODY"`，
   `waited_ms: 6` —— **等待只花 6 毫秒**，代价可忽略。

### 修复内容

- `loading.js` / `titlebar.js`：新增 `whenHostReady(fn)` —— 宿主节点已存在则立即执行；否则
  **MutationObserver 观察 `document` 的 childList**（`<html>` 被插入时立刻触发，且**不受隐藏
  窗口的定时器节流影响**，tab 窗口建窗时是 hidden 的）+ `interval(16ms)` + `readystatechange`
  + 3s 硬兜底。挂载后再在 `DOMContentLoaded` 把节点从 `<html>` 搬进 `<body>`。
- `titlebar.js`：安装改为异步；挂载后设 `window.__web2appChromeH = 38` 并派发
  `web2app:chrome-ready`。
- `loading.js`：先挂 no-op API（Rust 随时可能 eval `fail/hide`），挂载后替换为真实实现；
  `bodyEmpty()` 跳过 `#__web2app_titlebar__`（否则标题栏被当成「页面内容已就绪」→ 加载层
  立刻淡出）；按 `__web2appChromeH` 把加载层 `top` 让出 38px，不盖住标题栏。
- `splash.html` / `loading.rs`：**启动页内联 `titlebar.js`** —— 首个文档拿不到
  `initialization_script`（wry 是在 webview 建好之后才注册的），所以「首次打开」这段时间
  窗口顶部本来是空的。
- 新增单测 `injected_scripts_wait_for_dom_host` 锁死「必须等 DOM 宿主」这条约束。
- 新增 `examples/probe_dom_ready.rs` + Windows dev-dependencies（wry/tao），作为可复用的
  注入时机复测工具，不进发布产物。

验证：`node --check` 两个脚本 ✅ / `cargo fmt` ✅ / `TABS_ENABLED=true clippy -D warnings` ✅ /
`cargo test` 36 passed ✅ / 探针实测挂载成功（6ms）✅。

### 经验（已写入 MEMORY.md）

**WebView2 的 `AddScriptToExecuteOnDocumentCreated` 在「HTML 尚未解析」时执行，DOM 树完全不存在
（`documentElement` 为 null）。任何要挂 DOM 的注入脚本都必须先等宿主节点，且优先用
MutationObserver（隐藏窗口下 `setTimeout` 会被节流到 1s 级）。**
