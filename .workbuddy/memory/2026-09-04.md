## 启动过渡体验（loading 过渡层）

为 webview-app 实现「启动 → 首个页面渲染」之间的过渡提示，消除无反馈空白等待。

### 方案：两段接力 + 后台准备
- **splash 阶段**：主窗口创建时即加载本地启动页 `splash://localhost/`（自定义协议，零网络、首帧可见），显示"加载中…"转圈 + 进度条。
- **overlay 阶段**：真实地址就绪后导航过去，`initialization_script` 注入的加载层在 document-created 阶段铺满视口，页面渲染出内容后淡出。
- 两段共用 `src/loading.js` 的同一套视觉/状态机，观感连续（不是两次独立转圈）。

### 新增/改动文件
- `src/loading.js`（新增）：加载层脚本。模式由 `window.__web2appLoadingMode`（splash/overlay）决定。状态机 loading→slow(慢提示)→failed(错误+重试)/done(淡出)。零依赖、try/catch 包裹、ID 选择器 + !important 防宿主样式污染、动画只用 transform/opacity。对外 API：`window.__web2appLoading.{hide,slow,fail,state}`。
- `src/splash.html`（新增）：启动页模板，含 `__WEB2APP_TITLE__`、`__WEB2APP_LOADING_JS__` 占位符。
- `src/loading.rs`（新增）：`SPLASH_SCHEME`、`splash_url()`、`splash_html()`、`handle_splash()`（协议处理器，`/retry` 触发重新 bootstrap）、`show_error()`/`hide()`（Rust 侧 eval 驱动失败态）、`js_str()`（JS 字面量转义）、`html_escape()`。含单元测试。
- `src/lib.rs`（改动）：新增 `mod loading`；注册 splash 协议；setup 里**先建窗加载启动页并立即 show()**，耗时操作（域名解析/启动代理）挪到后台线程 `bootstrap()`；新增 `local_proxy_enabled()`、`Navigation` 结构、`prepare_navigation()`、`navigate_main()`、`SPLASH_BG` 背景色常量。

### 关键设计决策/经验
- **耗时操作从 setup 挪到后台线程**：原来域名解析（可能 DNS 查询、不可控耗时）在 setup 里同步执行，导致窗口都没出来。现在先出窗显示"加载中"，再后台准备。
- **解析失败不再 `std::process::exit`**：改为启动页上显示错误 + 重试按钮，用户能看到发生了什么。
- **重试语义**：splash 阶段重试跳 `splash://localhost/retry` → Rust 重新走完整 bootstrap（重新解析/重启代理），而非简单刷新。`handle_splash` 里 `/retry` 触发 `bootstrap()`，且每次重新生成 HTML（`Cache-Control: no-store`）。
- **WebView2 钩子注册顺序保留**：`attach_webview_hooks` 内部仍"先注册钩子再 Navigate"，避免首批请求漏 Authorization。现在由 `navigate_main` 调用它。
- **背景色**：`tauri::window::Color(0xf7,0xf8,0xfa,255)`，映射为 WebView2 `DefaultBackgroundColor`，消除导航提交瞬间白闪。
- **`use_local_proxy` 抽成 `local_proxy_enabled()`**：setup 建窗参数与 bootstrap 后台准备都要用，避免重复的 cfg 判断逻辑。

## resolve-keys.yml 在 ubuntu CI 报 glib-sys 编译失败 —— 已修复（20:20）

### 问题
`resolve-keys.yml` 在 ubuntu-latest 上跑 `cargo run --bin resolve-tool`，因 `resolve-tool` 是 `web2app` 根 crate 的 `[[bin]]`，编译整个 crate 会拉入 Tauri → Linux `glib-sys` → 需要系统 `glib-2.0` 开发库，runner 没装 → `Package glib-2.0 was not found` 失败。

### 根因
`resolve-tool` 只用到 `generate_keypair` / `sign_and_encrypt`（纯 Rust），但和 Tauri 主 crate 共享依赖图，被 Tauri 的 GUI 依赖链（glib-sys/gtk）拖累。

### 方案（workspace 拆分，彻底切断 Tauri 依赖）
- 新建 `crates/resolve-core`：纯 Rust 加密核心（Ed25519 签名 + AES-256-GCM + HKDF + 密钥对），无 Tauri、零平台依赖。含全部加密/验签/密钥对逻辑与单元测试（13 项，含与 Python 交叉验证）。
- 新建 `crates/resolve-tool`：独立 `[[bin]]`，只依赖 `resolve-core` + `base64` + `ed25519-dalek`。从旧 `src/bin/resolve-tool.rs` 迁移，`web2app_lib::resolve::*` → `resolve_core::*`。
- 根 `Cargo.toml`：加 `[workspace] members`；删 `[[bin]] resolve-tool`；删主 crate 的 `ed25519-dalek/aes-gcm/hkdf/sha2/rand`（下沉到 resolve-core），加 `resolve-core = { path = ... }` 依赖。
- `src/resolve.rs`：只保留 DNS 查询（`query_txt`/`resolve_url_from_domains`，依赖 tauri 异步运行时 + hickory-resolver），其余 re-export 自 resolve-core。
- workflow 命令 `cargo run --bin resolve-tool` → `cargo run -p resolve-tool`；README 同步更新。

### 经验
- `resolve-tool` 的依赖树现在是纯 Rust（base64 + ed25519-dalek + resolve-core），在 Linux CI 上无需任何系统库，`cargo run -p resolve-tool` 直接可用。
- 主 crate 仍直接依赖 `base64`（lib.rs/proxy.rs 用它做 Basic 鉴权）和 `serde_json`，不能移除；只有加密库下沉。

## resolve-keys.yml encrypt 报「私钥 DER 长度异常」—— 已修复（20:40）

### 问题
上一轮把 resolve-tool 拆成独立 crate 后编译已通过，但 encrypt 步骤报「私钥 DER 长度异常」，
私钥本身是合法的 48 字节纯私钥。

### 根因（GitHub Actions 多行输入被 YAML 折叠）
workflow 原写法：`env: PRIVATE_KEY: ${{ github.event.inputs.private_key }}` 直接把多行私钥
内联进 `env:`，GitHub 在 YAML 层面把换行折叠成空格 → PEM 被压成一行
`-----BEGIN ... MC4... -----END ...` → `load_signing_key` 的 `filter(|l| !l.starts_with("-----"))`
把整行过滤掉 → base64 body 为空 → DER 解码 0 字节 < 34 →「私钥 DER 长度异常」。

### 修复
- workflow 改用 `env: PRIVATE_KEY_JSON: ${{ toJSON(github.event.inputs.private_key) }}`：
  `toJSON` 把多行私钥编码成单行 JSON 字符串（换行→`\n` 字面量），绕开 YAML 折叠；
  再到 run 里 `printf '%s' "$PRIVATE_KEY_JSON" | python3 -c 'json.load'` 还原真实换行写文件。
- 加 `grep "BEGIN PRIVATE KEY"` 前置校验，私钥为空/格式错时提前报错。
- `load_signing_key` 的「DER 长度异常」错误信息加强：带上实际解码字节数 + 提示换行折叠排查方向。

### 经验（重要，可复用）
- **GitHub Actions workflow_dispatch 多行输入不能直接 `env: X: ${{ github.event.inputs.x }}` 内联**，
  多行值会被 YAML 折叠成空格。可靠解法是 `toJSON()` 包一层 → 单行 JSON → 用 `python3 -c json.load`
  或 `jq -r` 还原。这是 GitHub 社区公认做法。
- heredoc 在 `run: |` 块里写多行有「定界符必须顶格 vs YAML 块标量要缩进」的冲突，不如 toJSON 方案省心。
- Rust `str::lines()` 会自动剥 `\r`，所以 CRLF 私钥无需特殊处理。

## resolve-tool 支持「同一 URL 生成多份密文」（--count）（21:25）

### 需求澄清
用户澄清「一组多个」的真实意图是【同一个 URL 生成多份密文】——每份用不同随机 Nonce/盐，
密文互不相同，但解密后是同一个 URL，用于把同一地址分发到多个域名/多条 DNS TXT 记录。
（不是之前理解的「多个不同 URL」）

### 实现
- 底层 `resolve_core::sign_and_encrypt` 本就每次用 OsRng 生成随机 Nonce(12B)+盐(8B)，
  对同一 URL 调多次天然产出不同密文，无需改 resolve-core。
- `resolve-tool` 新增 `--count N` 参数（默认 1），`encrypt` 和 `all` 都支持：
  每个 URL 循环 count 次调用 sign_and_encrypt。新增 `parse_count()`（校验正整数）。
- 输出带「第 N 份」标注（仅 count>1 时），便于区分。
- workflow `resolve-keys.yml` 新增 count 输入项（默认 1），encrypt/all 两 job 透传 --count，
  校验 count 为正整数。
- README 同步补 --count 用法和 all 一键命令。

### 验证
- encrypt 单 URL --count 3 → 3 份密文互不相同；all --count 2 → 密钥对 + 2 份密文。
- resolve-core 13 项测试全过（含 e2e_sign_encrypt_roundtrip 对称性），保证多份密文都能解出同一 URL。
- workflow YAML 语法校验通过。

### 经验
- 加密工具的多值语义要先跟用户确认清楚：「多个 URL」vs「同一 URL 多份密文」是两种完全不同的
  需求，前者是 URL 数组轮换，后者是单 URL 分发多域名。用 --count 覆盖后者，位置参数仍支持
  多 URL（两者可叠加）。

## all job 报 exit code 1（tee 目录竞态）—— 已修复（21:30）

### 问题
`resolve-keys.yml` 的 all job，`resolve-tool all` 命令本身成功输出了密钥对和密文，
但整个 step 报 `Error: Process completed with exit code 1`。

### 根因（管道退出码取最后一个命令 = tee）
`cargo run ... all ... | tee "$RUNNER_TEMP/resolve-all/result.txt"` 是一条管道，
bash 管道的退出码默认是【最后一个命令】的。tee 在管道建立瞬间就 open 输出文件，
而 `resolve-all` 目录此时还没被 resolve-tool 的 create_dir_all 创建（首次编译 resolve-tool
要十几秒），tee 打开失败 → 退出码 1 → 管道退出码 1 → step 失败。all 本身早已成功。

本地复现：`echo hi | tee /tmp/noexist/result.txt` → `tee: ... No such file or directory`，退出码 1。

### 修复
all job 的 run 块开头加 `mkdir -p "$RUNNER_TEMP/resolve-all"`，先建目录再 tee。
encrypt job 不受影响（tee 目标在 $RUNNER_TEMP 根目录，天然存在）。

### 经验（重要，可复用）
- **shell 管道 `A | tee outfile` 的退出码取 tee（最后命令）**，不是 A。若 tee 的目标目录
  不存在（尤其目标在「由 A 运行时才创建」的子目录里），会得到 exit 1，掩盖 A 的成功。
- 修复：管道前先 `mkdir -p` 目标目录；或改用 `A > outfile`（退出码取 A）；或用
  `set -o pipefail` + 显式处理。CI 里最省心是「先 mkdir -p 再 tee」。

## 客户端 TXT 解析支持「同域名多条 TXT 任一成功」（21:30）

### 用户确认的两个需求
1. 一个域名可挂多条 TXT 记录（对应「同一 URL 多份密文」）
2. 只要一条 TXT 能解密出有效 URL 就够（不必全部有效）

### 核对结果 + 修复
- 【多域名任一成功】已正确：`resolve_url_from_domains` 本就遍历域名、任一成功即返回。
- 【同域名多条 TXT】原实现有 bug：`query_txt` 只 `return` 第一条非空 TXT，后面的不看；
  单域名解密失败直接放弃整个域名，不会试同域名的第 2/3 条。
- 修复：
  - `query_txt` → 改名 `query_txt_all`，返回 `Vec<String>`（该域名所有非空 TXT）。
  - 抽纯函数 `decrypt_first_valid_txt(&VerifyingKey, &[String])`：逐条解密+验签，任一非空即返回。
  - `resolve_url_from_domains` 对每个域名调 `query_txt_all` → `decrypt_first_valid_txt`，
    全失败再下一域名。
  - resolve-core re-export `SigningKey`/`VerifyingKey`（`pub use ed25519_dalek::{...}`），
    主 crate 通过 `resolve_core::` 拿类型，避免重新加 ed25519-dalek 依赖。
  - 新增单测 `decrypt_first_valid_txt_skips_bad_and_hits_valid`：第1条垃圾/第2条有效/第3条别的公钥，
    验证能跳过垃圾命中第2条。

### 经验
- 主 crate 拆分后已不直接依赖 ed25519-dalek，用 resolve-core 的 re-export 类型而非裸依赖。
- 「任一成功」类逻辑抽成纯函数（不碰 DNS/IO）才好单测。
